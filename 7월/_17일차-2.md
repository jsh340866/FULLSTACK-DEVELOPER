## 2. 클러스터 접속 — `local[*]`에서 `spark://`로

### 01·02 노트북과의 결정적 차이

| 항목 | `local[*]` (01, 02) | `spark://jupyter:7077` (03) |
|---|---|---|
| 실행 주체 | 내 파이썬 프로세스 안의 스레드 | 별도 컨테이너의 executor 프로세스 |
| 클러스터 매니저 | 없음 | 스탠드얼론 마스터 |
| 병렬 단위 | CPU 코어 | 워커 × 코어 |
| 네트워크 | 불필요 | 셔플·블록 전송에 필수 |
| 장애 격리 | 없음 (죽으면 전체 종료) | executor 하나 죽어도 재시도 |

### 코드

```python
from pyspark.sql import SparkSession
from pyspark.sql import functions as F      # col/trim/regexp_extract 등 컬럼 연산 함수 모음

spark = (SparkSession.builder               # 설정을 쌓아올리는 조립대 (메서드 체인)
    .appName("chakhan-price-cluster")       # Spark UI·마스터 UI에 표시될 이름표
    .master("spark://jupyter:7077")         # ★ 스탠드얼론 마스터의 RPC 주소
    .getOrCreate())                         # 기존 세션 있으면 재사용, 없으면 생성

print("master:", spark.sparkContext.master)
print("등록된 executor(driver 포함):",
      spark.sparkContext._jsc.sc().getExecutorMemoryStatus().keySet().toString())
```

### 출력

```
master: spark://jupyter:7077
등록된 executor(driver 포함): Set(5597bfd010a9:33913, 172.18.0.3:34109, 172.18.0.4:43237)
```

### 출력 해석 — 3개는 마스터+워커1+워커2가 아니다

| 출력값 | 정체 | 실제 컨테이너 |
|---|---|---|
| `5597bfd010a9:33913` | **드라이버** (내 노트북 프로세스) | jupyter |
| `172.18.0.3:34109` | 워커1 위의 **executor** | spark-worker-1 |
| `172.18.0.4:43237` | 워커2 위의 **executor** | spark-worker-2 |

`getExecutorMemoryStatus()`는 **메모리를 들고 데이터를 캐싱하는 주체(BlockManager)** 의 목록입니다. 마스터는 자원 중개만 하고 데이터를 1바이트도 만지지 않으므로 이 목록에 등장하지 않습니다.

> 💡 마스터는 `spark://jupyter:7077`이 가리키듯 **jupyter 컨테이너 안에 드라이버와 동거** 중입니다. 같은 컨테이너지만 역할이 다른 프로세스입니다.

### 포트 3종 구분

| 포트 | 용도 | 누가 씁니까 |
|---|---|---|
| `7077` | 마스터 **RPC** — 드라이버가 executor를 요청하는 업무 회선 | `.master()` 에 지정 |
| `8080` | 마스터 **웹 UI / JSON** — 클러스터 상태 조회용 안내 데스크 | 셀 6에서 사용 |
| `4040` | **애플리케이션 UI** — 잡·스테이지·태스크 상세 | 브라우저 |

> ⚠️ 뒤에 붙은 `33913`, `34109`, `43237`은 executor 포트가 아니라 **BlockManager 랜덤 포트**입니다. 재시작할 때마다 바뀌므로 의미를 부여하지 마세요.
> ⚠️ `getOrCreate()`는 이미 세션이 살아있으면 **`.appName` / `.master` / `.config`를 전부 무시**합니다. 설정을 바꾸려면 반드시 `spark.stop()` 후 다시 만들어야 합니다.

## 3. CSV 로드

```python
PATH = "/home/jovyan/work/행정안전부_착한가격업소 현황_20260630.csv"

df = (spark.read
    .option("header", True)        # 첫 줄을 컬럼명으로
    .option("inferSchema", True)   # 타입 자동 추론 (전체 스캔 1회 추가 발생)
    .option("encoding", "UTF-8")
    .option("multiLine", True)     # 셀 안에 줄바꿈이 있는 레코드 대응
    .option("escape", '"')         # 따옴표 안의 따옴표 처리
    .csv(PATH))

df.printSchema()
print("행 수:", df.count())
```

### 출력 (요약)

```
root
 |-- 시도: string ... |-- 메뉴1: string |-- 가격1: string ... |-- 가격4: string
행 수: 12645
```

| 옵션 | 안 쓰면 생기는 일 |
|---|---|
| `header` | 컬럼명이 `_c0, _c1...`이 되고 헤더가 데이터 1행으로 섞임 |
| `multiLine` | 주소·메뉴에 줄바꿈이 있으면 한 레코드가 여러 행으로 쪼개짐 |
| `escape` | `"수제 ""특"" 돈까스"` 같은 값에서 파싱이 어긋남 |

> ⚠️ `inferSchema=True`는 **파일을 한 번 더 통째로 읽습니다.** 파일이 커지면 스키마를 직접 `StructType`으로 명시하는 편이 빠릅니다.
> ⚠️ 이번엔 가격 컬럼이 전부 string으로 추론됐지만, 데이터에 따라 `가격1`은 int, `가격2`는 string으로 **컬럼마다 다르게** 잡힐 수 있습니다. 그래서 다음 단계의 타입 통일이 필요합니다.

## 4. 컬럼명 영문화 + 가격 타입 통일

```python
rename_map = {
    "시도": "sido", "시군": "sigun", "업종": "category",
    "업소명": "name", "연락처": "tel", "주소": "address",
    "메뉴1": "menu1", "가격1": "price1",
    "메뉴2": "menu2", "가격2": "price2",
    "메뉴3": "menu3", "가격3": "price3",
    "메뉴4": "menu4", "가격4": "price4",
}
for old, new in rename_map.items():
    df = df.withColumnRenamed(old, new)

# ★ 4개 가격 컬럼을 강제로 string 통일 → 이후 stack에서 타입 충돌 방지
for c in ["price1", "price2", "price3", "price4"]:
    df = df.withColumn(c, F.col(c).cast("string"))
```

**왜 굳이 string으로 내리는가?**
`stack()`은 같은 자리에 오는 값들의 **타입이 전부 같아야** 합니다. `price1`이 int이고 `price3`이 string이면 `stack` 단계에서 타입 불일치 에러가 납니다. 어차피 다음 단계에서 정규식으로 파싱할 것이므로 **가장 관대한 타입인 string으로 내려서 통일**하는 전략입니다.

> 💡 `withColumnRenamed`를 루프로 돌리면 호출할 때마다 논리 계획이 한 겹씩 쌓입니다. 컬럼이 수십 개면 `df.select([F.col(o).alias(n) for o, n in rename_map.items()])` 한 방이 더 깔끔합니다. 14개 수준에선 차이 없습니다.

## 5. Wide → Long 변환 (오늘의 핵심)

### 무엇을 하는 변환인가

```
[Wide] 업소 1행에 메뉴가 4개 (컬럼 방향)
  돈까스보라 | 수제 돈까스 7000 | 돈까스 정식 8000 | null | null
        ↓ stack(4, ...)
[Long] 메뉴 1개가 1행 (행 방향)
  돈까스보라 | 1 | 수제 돈까스 | 7000
  돈까스보라 | 2 | 돈까스 정식 | 8000
```

분석 단위가 **"업소"에서 "메뉴"로** 바뀝니다. 가격 분포·클러스터링을 하려면 반드시 이 형태여야 합니다.

### 코드

```python
long_df = (df.select(
        "sido", "sigun", "category", "name", "address",
        F.expr("""
            stack(4,                      -- 4묶음을 세로로 쌓겠다
                1, menu1, price1,         -- 묶음당 3개 값 → 3개 컬럼으로 나옴
                2, menu2, price2,
                3, menu3, price3,
                4, menu4, price4
            ) as (menu_no, menu, price_raw)
        """)
    )
    # 메뉴가 비어있는 행 제거 (4칸을 다 안 채운 업소)
    .filter(F.col("menu").isNotNull() & (F.trim(F.col("menu")) != ""))

    # 1) 첫 번째 숫자 덩어리만 추출 (콤마 포함 허용)
    .withColumn("price_str",
        F.regexp_extract(F.col("price_raw"), r"(\d{1,3}(?:,\d{3})+|\d+)", 1))

    # 2) 콤마 제거 후 try_cast → 실패해도 예외 없이 NULL
    .withColumn("price",
        F.expr("try_cast(regexp_replace(price_str, ',', '') as bigint)"))
    .filter(F.col("price").isNotNull() & (F.col("price") > 0))

    # 3) 상식 밖 값 차단
    .filter((F.col("price") >= 500) & (F.col("price") <= 1000000))
    .drop("price_str")
)

long_df.cache()
print("메뉴 단위 행 수:", long_df.count())
```

### 출력

```
메뉴 단위 행 수: 26762
```

| 단계 | 행 수 |
|---|---|
| 원본 (업소 단위) | 12,645 |
| `stack` 직후 (이론상 최대) | 50,580 = 12,645 × 4 |
| 빈 메뉴 제거 + 가격 파싱·필터 후 | **26,762** |

### 정규식 `(\d{1,3}(?:,\d{3})+|\d+)` 뜯어보기

| 조각 | 의미 |
|---|---|
| `\d{1,3}(?:,\d{3})+` | `12,000` `1,234,567` 같은 **천 단위 콤마 표기** |
| `\|` | 또는 |
| `\d+` | `7000` 같은 **콤마 없는 연속 숫자** |
| 순서가 중요 | 콤마 패턴을 앞에 둬야 `12,000`에서 `12`만 뜯기지 않습니다 |
| `, 1` | 1번 캡처 그룹만 반환 |

이 패턴 덕분에 `"7,000원"`, `"7000~8000"`, `"1인 7000"` 같은 지저분한 값에서도 **첫 번째 숫자 덩어리**만 안전하게 뽑힙니다.

### `try_cast`를 쓰는 이유

일반 `cast`는 스파크 3.x의 ANSI 모드에서 변환 실패 시 **잡 전체를 죽입니다.** `try_cast`는 실패를 조용히 `NULL`로 처리하므로, 12,645행 중 이상한 값 하나 때문에 전체가 멈추는 사고를 막습니다.

> ⚠️ **주석과 코드가 불일치합니다.** 주석엔 `10원 미만 차단`이라고 적혀 있지만 실제 코드는 `>= 500`입니다. 500원 미만 메뉴(공중화장실 이용료, 100~300원대 사은품 등)가 조용히 삭제됩니다. 주석을 `500원 미만 / 100만원 초과 차단`으로 고치거나, 하한을 실제 의도대로 낮춰야 합니다.
> ⚠️ `regexp_extract`는 **매치 실패 시 NULL이 아니라 빈 문자열 `""`** 을 반환합니다. 여기선 뒤이은 `try_cast`가 `""`를 NULL로 만들어주고 그걸 필터가 걸러내므로 결과적으로 안전하지만, 이 연쇄를 모르고 쓰면 빈 문자열이 그대로 통과합니다.
> ⚠️ `price_raw`가 결과에 그대로 남아있습니다. 원본 대조용이면 의도적이지만, 저장 단계에서는 `drop("price_raw")`로 정리하는 편이 좋습니다.

> 💡 `cache()`는 이 시점의 결과를 메모리에 붙들어 둡니다. 이후 셀 5·6에서 `long_df`를 반복 사용하므로 CSV 파싱·정규식 연산을 매번 다시 하지 않아도 됩니다. **단, 이 캐시가 뒤에서 분산 실패의 원인이 됩니다 (섹션 6 참조).**

## 6. 분산 처리 증거 ① — 파티션별 실행 호스트 추적 (결과: 실패)

### 원리

```python
def hostname_of_partition(idx, iterator):
    yield (idx, socket.gethostname())      # ★ 이 함수는 executor에서 실행된다
```

이 함수는 드라이버가 아니라 **워커 컨테이너 안에서 실행**되므로, `socket.gethostname()`이 곧 "이 파티션을 처리한 컨테이너 이름"이 됩니다. 증거의 원리는 이 한 줄이 전부입니다.

```python
long_df_repart = long_df.repartition(6)    # 워커 2대보다 넉넉히 6조각으로 재분할

partition_hosts = (long_df_repart.rdd      # DataFrame → RDD (저수준 API 사용 위해)
    .mapPartitionsWithIndex(hostname_of_partition)   # 파티션당 1회 실행
    .collect())                            # 드라이버로 회수 (여기서 실제 실행 시작)

host_df = pd.DataFrame(partition_hosts, columns=["partition_id", "executor_hostname"])
print(host_df["executor_hostname"].value_counts())
```

| 함수 | 실행 단위 |
|---|---|
| `map` | 행마다 1회 |
| `mapPartitions` / `mapPartitionsWithIndex` | **파티션마다 1회** ← 호스트명은 행마다 물을 필요 없음 |

### 출력 — 6개 파티션이 전부 한 호스트

```
   partition_id executor_hostname
0             0      0ccd9210badb
1             1      0ccd9210badb
...
5             5      0ccd9210badb

executor_hostname
0ccd9210badb    6
```

**분산 증거로는 실패했습니다.** 다만 `0ccd9210badb`는 드라이버(`5597bfd010a9`)와 다른 컨테이너이므로, **연산이 드라이버 밖 executor로 나갔다는 것("원격 실행")까지는 증명**됐습니다.

### 왜 한쪽으로 몰렸나 — 3중 콤보

| # | 원인 | 상세 |
|---|---|---|
| 1 | **파티션이 애초에 1개** | CSV 12,645행은 `spark.sql.files.maxPartitionBytes`(128MB) 훨씬 미만 → 읽는 순간 파티션 1개. `long_df`도 1개 |
| 2 | **`cache()`가 블록을 한 곳에 고정** | 1개짜리 캐시 블록이 executor 하나에만 저장됨 |
| 3 | **리듀서 지역성** | `spark.shuffle.reduceLocality.enabled` 기본값 `true` → 맵 출력이 한 executor에 몰려 있으면 리듀스 태스크 6개가 전부 그 executor를 선호 위치로 지정. 게다가 태스크가 밀리초에 끝나 `spark.locality.wait`(기본 3초) 안에 같은 곳이 계속 빈 슬롯을 내줌 |

여기에 워커당 `cores=1`이라 스케줄러가 다른 워커로 넘길 압력 자체가 약했습니다.

### 수정안 A — 세션 재시작 없이 즉시 확인

```python
import socket, time

def who(idx, it):
    time.sleep(2)                # 태스크를 길게 잡아 한 executor 독점을 방지
    yield (idx, socket.gethostname())

# parallelize는 preferred location이 없어 스케줄러가 양쪽에 고르게 offer
hosts = (spark.sparkContext
    .parallelize(range(12), 12)
    .mapPartitionsWithIndex(who)
    .collect())

print(set(h for _, h in hosts))   # 원소가 2개면 분산 확정
```

### 수정안 B — 실데이터로 성립시키려면 세션 재시작 필수

```python
spark.stop()

spark = (SparkSession.builder
    .appName("chakhan-price-cluster")
    .master("spark://jupyter:7077")
    .config("spark.locality.wait", "0s")                       # 지역성 대기 없이 즉시 타 executor로
    .config("spark.shuffle.reduceLocality.enabled", "false")   # 리듀서 쏠림 방지
    .getOrCreate())

# 그리고 읽자마자 분할, cache는 그 뒤에
df = spark.read.option("header", True)....csv(PATH).repartition(6)
```

> ⚠️ 위 두 설정은 **SparkConf 초기화 시점에 읽힙니다.** 세션 생성 후 `spark.conf.set(...)`으로 바꿔도 적용되지 않습니다.
> ⚠️ `.rdd`로 내려가면 Catalyst 최적화가 끊기고 Row 직렬화 비용이 붙습니다. **진단용으로만** 쓰세요.

## 7. 분산 처리 증거 ② — 마스터 REST API로 워커 명단 조회

```python
import urllib.request, json

# 8080은 마스터의 웹 UI 포트. /json/ 은 HTML 대신 상태를 JSON으로 반환
master_state = json.loads(urllib.request.urlopen("http://jupyter:8080/json/").read())

print("alive workers:", master_state["aliveworkers"])
for w in master_state["workers"]:
    print(f"  - id={w['id']}  host={w['host']}  state={w['state']}  cores={w['cores']}  memory={w['memory']}MB")

print("running/completed apps:", len(master_state["activeapps"]), "/", len(master_state["completedapps"]))
```

### 출력

```
alive workers: 2
  - id=worker-20260728054832-172.18.0.4-35295  host=172.18.0.4  state=ALIVE  cores=1  memory=1500MB
  - id=worker-20260728054832-172.18.0.3-43565  host=172.18.0.3  state=ALIVE  cores=1  memory=1500MB

running/completed apps: 1 / 1
```

- `host` 값 `172.18.0.3` / `.4`가 **셀 1의 executor 주소와 정확히 일치** → 같은 워커가 내 앱에 자원을 내줬다는 교차 증거
- `cores=1`이 섹션 6의 쏠림 현상을 설명하는 핵심 수치
- `activeapps 1 / completedapps 1` → 좀비 세션이 자원을 쥐고 있지 않은지 확인 가능

> ⚠️ **셀 6은 "분산 처리" 증거가 아닙니다.** 마스터에게 "직원 몇 명 있어요?"라고 물어본 것뿐이고, **내 잡이 그 워커를 실제로 썼는지는 아무것도 말해주지 않습니다.**

## 8. 증거의 3단계 정리

| 셀 | 증명하는 것 | 비유 | 결과 |
|---|---|---|---|
| 셀 1 | executor 2개가 내 앱에 붙음 | 내 주문에 요리사 2명 배정 | ✅ |
| 셀 6 | 클러스터에 워커 2대 ALIVE | 주방에 요리사 2명 고용 (명단) | ✅ (내 잡과 무관) |
| 셀 5 | 태스크가 실제 실행된 위치 | **정말 둘이 접시를 나눠 만들었나** | ❌ 한 명이 6개 전담 |

앞의 둘은 **자원 확보 증거**, 마지막 하나만 **실행 증거**입니다.

> 💡 가장 표준적인 검증은 Spark UI(4040) → **Executors 탭의 executor별 `Complete Tasks` 수**입니다. 둘 다 0이 아니면 그게 공식 증거입니다. Stage 상세의 태스크별 `Host` 컬럼도 같은 역할을 합니다.

## 11. 오늘 배운 것 요약

1. `.master("spark://호스트:7077")` 한 줄로 실행 주체가 **내 프로세스 → 원격 워커**로 바뀐다. `local[*]`과의 차이는 이 한 줄이다.
2. `getExecutorMemoryStatus()` 목록의 3개는 **드라이버 1 + executor 2**이며, **마스터는 데이터를 만지지 않아 목록에 없다.**
3. 포트는 역할이 다르다 — `7077`(작업 제출), `8080`(상태 조회), `4040`(앱 상세).
4. `stack(n, ...)`으로 wide → long 변환. 이때 **묶음 내 같은 자리 값들의 타입이 반드시 일치**해야 하므로 사전에 `cast("string")`로 통일한다.
5. 지저분한 문자열 가격은 **`regexp_extract`로 첫 숫자 덩어리 추출 → 콤마 제거 → `try_cast`** 3단 조합이 안전하다. `try_cast`는 실패를 NULL로 삼켜 잡이 죽지 않는다.
6. **분산 "구성"과 분산 "실행"은 다른 증거다.** 워커가 2대 살아있는 것과, 내 태스크가 2대에서 돌았다는 것은 별개다.
7. 데이터가 작고 파티션이 1개면 `repartition`을 해도 **캐시 위치 + 리듀서 지역성 + 짧은 태스크** 때문에 한 executor로 쏠린다. `spark.locality.wait=0s`와 `spark.shuffle.reduceLocality.enabled=false`로 강제 분산할 수 있다.
8. `getOrCreate()`는 기존 세션이 있으면 새 설정을 무시한다. 설정 변경 = `spark.stop()` 필수.
