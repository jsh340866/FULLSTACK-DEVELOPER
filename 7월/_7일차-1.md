# TIL: Route 53 도메인 연결 + SSL 인증서 발급 + Jenkins HTTPS 자동배포

> 📅 2026-07-09 1부
> 주제: Route 53에 도메인(jsh340866.store) 연결, Let's Encrypt SSL 인증서를 발급해 Spring Boot에 적용, Jenkins 자동배포가 443(HTTPS)에서 동작하도록 구성

---

## 1. 학습 목표

- 구매한 도메인을 **Route 53 호스팅 영역**에 연결해 EC2를 도메인으로 접근할 수 있게 한다
- **certbot**으로 SSL 인증서를 발급받고, Spring Boot 내장 톰캣이 읽을 수 있는 **PKCS12(keystore.p12)** 형식으로 변환한다
- Jenkins 자동배포 스크립트에 **sudo 권한**을 적용해 443 포트에서도 배포가 동작하는 **HTTPS CI/CD**를 완성한다

---

## 2. Route 53 도메인 연결

### 왜 필요한가?

- SSL 인증서는 IP가 아닌 **도메인**에 대해 발급된다 → HTTPS를 쓰려면 도메인이 먼저 EC2를 가리켜야 한다
- Route 53에 호스팅 영역을 만들고 도메인 등록기관에 네임서버를 등록해야 DNS 관리가 AWS로 위임된다

### 설정 방법

1. AWS 콘솔 → **Route 53** → **호스팅 영역 생성** → `jsh340866.store` 입력
2. 생성된 호스팅 영역의 세부 정보에서 **NS 레코드 4개** 확인

```
ns-30.awsdns-03.com
ns-1675.awsdns-17.co.uk
ns-816.awsdns-38.net
ns-1384.awsdns-45.org
```

3. 도메인 구매처(등록기관) 설정에서 네임서버를 위 4개로 교체 → DNS 위임 완료
4. **A 레코드 생성**: `jsh340866.store` → EC2 퍼블릭 IP `15.165.253.103`

> ⚠️ A 레코드가 없으면 도메인 접속은 물론 다음 단계의 certbot 도메인 검증도 실패한다.
> ⚠️ 네임서버 변경은 전파에 수 분~수 시간 걸릴 수 있다.

## 3. SSL 인증서 발급 (certbot)

### 왜 필요한가?

- HTTPS는 신뢰된 CA가 서명한 인증서가 있어야 동작한다 → **Let's Encrypt**로 무료 발급
- `--standalone` 방식은 certbot이 **임시 웹서버를 80 포트에 띄워** 도메인 소유를 검증한다 → 발급 시점에 80 포트가 비어 있어야 한다

### 발급 과정 (EC2에서)

```bash
certbot certonly --standalone
# 이메일 입력: jsh340866@gmail.com
# 도메인 입력: jsh340866.store
```

```bash
# 발급 위치 확인
find / -name "*jsh340866*"
cd /etc/letsencrypt/live/jsh340866.store
```

| 파일 | 내용 |
|---|---|
| `fullchain.pem` | 인증서 + 중간 인증서 체인 |
| `privkey.pem` | 개인키 |
| `chain.pem` | 중간 인증서 |

> ⚠️ 인증서 폴더명은 **입력한 첫 도메인**을 따른다. 필기에는 `www.jsh340866.store` 경로로 적혀 있었으나 입력 도메인과 불일치 → `ls /etc/letsencrypt/live/`로 실제 폴더명 확인 필요. www 접속까지 지원하려면 발급 시 `-d jsh340866.store -d www.jsh340866.store`처럼 둘 다 넣어야 한다.
> ⚠️ Let's Encrypt 인증서는 **90일 유효** → 만료 전 `certbot renew` + p12 재변환 필요.

## 4. pem → keystore.p12 변환 후 프로젝트에 적용

### 왜 필요한가?

- Spring Boot 내장 톰캣은 pem 파일을 직접 읽지 못한다 → **PKCS12 keystore** 형식으로 변환해야 한다

### 4-1. openssl로 변환 (EC2에서)

```bash
sudo openssl pkcs12 -export \
  -in fullchain.pem \
  -inkey privkey.pem \
  -out keystore.p12 \
  -name ttp \
  -CAfile chain.pem -caname root
# Export Password: 123456
```

> ⚠️ 여기서 입력한 비밀번호는 `application.properties`의 `key-store-password`와 **반드시 일치**해야 한다.

### 4-2. scp로 로컬 다운로드

```bash
# scp는 ec2-user 권한으로 접근 → root 소유 경로에 읽기 권한 먼저 부여
chmod -R o+rx /etc/letsencrypt/live/
```

로컬에서 `DEPLOY_SBONLY.pem` 키 파일이 있는 폴더에서 cmd 실행:

```bash
scp -i DEPLOY_SBONLY.pem ec2-user@15.165.253.103:/etc/letsencrypt/live/jsh340866.store/keystore.p12 .
# 마지막 . = 현재 폴더로 다운로드
```

### 4-3. 프로젝트에 배치 + application.properties 설정

- 다운로드한 `keystore.p12`를 IntelliJ 프로젝트의 `src/main/resources/ssl/` 로 이동 → jar 빌드 시 함께 포함(classpath 방식)

```properties
server.port=443
server.ssl.key-store=classpath:ssl/keystore.p12
server.ssl.key-store-type=PKCS12
server.ssl.key-store-password=123456
```

> 참고: 수업 중 `cp ./keystore.p12 /app/16_DEPLOY_SBONLY` 로 EC2 배포 폴더에 복사하는 단계도 있었으나, 최종적으로 classpath 방식으로 정리되면서 이 복사본은 사용하지 않는다. (외부 파일 경로 방식 → classpath 방식으로 수업 중 변경)
> ⚠️ 443은 HTTPS 기본 포트 → `https://jsh340866.store` 로 포트 번호 없이 접속 가능. 보안 그룹에 **443 인바운드 규칙**도 열려 있어야 한다.

## 5. Jenkins가 443에서 배포할 수 있도록 권한 설정

### 왜 필요한가?

- **1024 이하 포트(443 포함)는 root 권한이 있어야 바인딩**할 수 있다
- Jenkins는 `jenkins` 계정으로 실행되므로, 배포 스크립트의 실행/종료 명령에 sudo가 필요하다

### 5-1. sudoers에 제한적 NOPASSWD 허용

```bash
vi /etc/sudoers   # :se nu 로 줄번호 표시 후 100번대에 추가
```

```
jenkins ALL=(ALL)       NOPASSWD:/usr/bin/nohup
jenkins ALL=(ALL)       NOPASSWD:/usr/bin/java
jenkins ALL=(ALL)       NOPASSWD:/usr/bin/kill
```

- 저장: `:wq!` (sudoers는 읽기 전용 파일이라 `!` 필요)
- 전체 sudo가 아니라 **필요한 명령 3개만** 비밀번호 없이 허용 → 최소 권한 원칙

### 5-2. Post Task 스크립트 수정 (최종본)

**문제**: 443 전환 후 기존 스크립트로 배포하면 내장 톰캣이 권한 부족으로 기동 실패

```bash
#!/bin/bash

JAVA_COMMAND="java -jar"
JAR_PATH="/var/lib/jenkins/workspace/DEPLOY_SBONLY/build/libs/demo-0.0.1-SNAPSHOT.jar"

# pgrep -f: 전체 커맨드라인 기준으로 PID 검색
TARGET_PID=$(pgrep -f "$JAVA_COMMAND $JAR_PATH")

if [ -z "$TARGET_PID" ]; then
    echo "해당 프로세스가 이미 종료되었습니다."
else
    echo "프로세스 $TARGET_PID 종료 중..."
    # 기존 프로세스는 sudo로 실행된 root 소유 → 종료에도 sudo 필요
    sudo kill -9 "$TARGET_PID"

    if ps -p "$TARGET_PID" > /dev/null; then
        echo "프로세스 $TARGET_PID 종료 실패"
    else
        echo "프로세스 $TARGET_PID 성공적으로 종료됨"
    fi
fi

# 443 바인딩을 위해 sudo, 백그라운드 유지를 위해 nohup
sudo nohup java -jar "$JAR_PATH" &
```

> ⚠️ 원본 필기의 개선판 스크립트에는 sudo가 빠져 있었다. sudo 없이 실행하면 ① jenkins 계정은 443 바인딩 불가, ② root 소유 기존 프로세스를 kill 불가 → **kill과 java 실행 두 곳 모두 sudo 필수**.
> ⚠️ 필기의 `DEPLOY_SBLONLY`는 `DEPLOY_SBONLY` 오타로 통일. 초반의 `MY_WEBSERVER_DEPLOY` 경로는 이전 수업 job에서 복사된 흔적.
> ⚠️ `kill -9`(SIGKILL)는 즉시 강제종료라 처리 중인 요청이 유실될 수 있다 → 실서비스라면 `kill`(SIGTERM) 후 대기, 실패 시에만 -9.

## 6. 오늘 배운 것 요약

- SSL 인증서는 도메인 기준으로 발급된다 → **Route 53 호스팅 영역 + NS 위임 + A 레코드**로 도메인이 EC2를 가리키게 하는 것이 선행 조건
- Let's Encrypt pem은 Spring Boot에서 바로 못 쓴다 → **openssl로 PKCS12(keystore.p12) 변환** 후 classpath에 포함
- **1024 이하 포트(443)는 root 권한 필요** → Jenkins에는 sudoers로 nohup/java/kill 3개 명령만 제한적 NOPASSWD 허용
- sudo로 띄운 프로세스는 root 소유 → **재배포 시 kill에도 sudo가 필요**하다 (배포 스크립트에서 놓치기 쉬운 지점)
