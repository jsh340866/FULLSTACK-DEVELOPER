# TIL: Jenkins Docker 전환 + Docker Compose 배포 환경 구축

> 📅 2026-07-09 (2)
> 주제: systemd로 직접 설치했던 Jenkins를 중단하고, Docker 컨테이너 기반 Jenkins로 전환. Docker + Docker Compose를 설치하고 저장소의 compose 구성으로 기동

---

## 1. 학습 목표

- 기존에 EC2에 직접 설치한(systemd) Jenkins를 정리하고 **Docker 컨테이너로 Jenkins를 운영**하는 방식으로 전환한다
- Jenkins 컨테이너 안에서 빌드/배포에 필요한 **Docker CLI, AWS CLI를 포함한 커스텀 이미지**를 Dockerfile로 정의한다
- **Docker Compose**로 배포 구성을 코드화해 `docker-compose up` 한 번으로 환경을 띄운다

---

## 2. 기존 Jenkins(systemd) 중단

### 왜 필요한가?

- 어제~오전까지 쓰던 Jenkins는 EC2에 직접 설치되어 systemd로 관리되는 방식
- Docker 기반 Jenkins와 **포트/역할이 겹치므로** 기존 서비스를 중지하고 부팅 시 자동 시작도 꺼야 한다

```bash
# 부팅 시 자동 시작 해제 + 현재 실행 중인 Jenkins 종료
sudo systemctl disable jenkins
sudo systemctl stop jenkins
```

> ⚠️ 필기에는 sudo가 빠져 있었는데, root 세션(`sudo su`)이 아니라면 sudo가 필요하다.

---

## 3. EC2에 Docker + Docker Compose 설치

### 3-1. Docker 설치 (Amazon Linux)

```bash
sudo yum update -y
sudo yum install docker -y
sudo systemctl start docker
sudo systemctl enable docker

# ec2-user가 sudo 없이 docker 명령을 쓸 수 있도록 docker 그룹에 추가
sudo usermod -aG docker ec2-user
```

> ⚠️ 필기의 `Systemctl`(대문자 S)은 오타 — 리눅스는 대소문자를 구분하므로 command not found가 난다.
> ⚠️ `usermod -aG` 그룹 추가는 **재로그인해야 반영**된다. 필기의 "재시작"은 EC2 재부팅이 아니라 **세션 재접속**(나갔다가 ec2-user로 다시 로그인)을 의미.

### 3-2. Docker Compose 설치

```bash
DOCKER_COMPOSE_VERSION="v2.27.1"
sudo curl -L "https://github.com/docker/compose/releases/download/${DOCKER_COMPOSE_VERSION}/docker-compose-$(uname -s)-$(uname -m)" \
  -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose

# /usr/bin 에서도 찾을 수 있도록 심볼릭 링크
sudo ln -s /usr/local/bin/docker-compose /usr/bin/docker-compose

# 설치 확인
docker-compose version
```

- `$(uname -s)-$(uname -m)` → 현재 OS/아키텍처(Linux-x86_64)에 맞는 바이너리를 자동 선택

## 4. Jenkins 커스텀 이미지 (Dockerfile)

### 왜 필요한가?

- 공식 `jenkins/jenkins:lts` 이미지에는 **docker, aws 명령이 없다**
- Jenkins 컨테이너가 빌드 과정에서 도커 이미지를 만들고 AWS(ECR 등)에 접근하려면 CLI 도구가 이미지에 포함돼야 한다

### Dockerfile (저장소 `DEPLOY_DOCKER` 내부)

```dockerfile
FROM jenkins/jenkins:lts

# 패키지 설치는 root 권한 필요
USER root

# 필수 유틸리티 설치 (--no-install-recommends 로 최소 설치, 캐시 삭제로 이미지 경량화)
RUN apt-get update && apt-get -y install --no-install-recommends \
    curl \
    unzip \
    gnupg \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# Docker 설치 (공식 스크립트 — CLI뿐 아니라 docker-ce 전체가 설치됨)
RUN curl -fsSL https://get.docker.com | sh

# AWS CLI v2 설치
RUN curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip" && \
    unzip awscliv2.zip && \
    ./aws/install && \
    rm -rf awscliv2.zip aws

# 보안을 위해 다시 jenkins 사용자로 복귀
USER jenkins
```

> ⚠️ 컨테이너 안에서 Docker 데몬을 새로 띄우는 게 아니라, compose에서 호스트의 `/var/run/docker.sock`을 마운트해 **호스트 Docker를 빌려 쓰는 구조(DooD)** 가 일반적. 컨테이너 안에는 클라이언트(CLI)만 있으면 충분하다.
> ⚠️ 필기 주석은 "Docker CLI 설치"였지만 get.docker.com 스크립트는 엔진 전체를 설치한다 → 동작에는 문제없으나 이미지가 커지는 트레이드오프.

## 5. 로컬 검증 → push → EC2에서 동일하게 기동 (오늘의 핵심 흐름)

```
[내 PC — 개발/검증]
  VS Code에서 yml + Dockerfile 작성
  → docker-compose -f docker-compose-local.yml up
     (jenkins 포함 5개 전체 기동 — 오늘 bn-container 로그를 본 실행)
  → git push origin

[EC2 — 실서버]
  Docker/Compose 설치 → git clone
  → docker-compose up (기본 yml 자동 인식 → 앱 스택 4개 기동)
  → jenkins는 -f docker-compose-local.yml 로 별도 부트스트랩
     (이후 Jenkins Job이 기본 yml로 앱 4개를 반복 배포하는 것이 다음 단계)
```

같은 yml이 내 PC에서도 EC2에서도 동일하게 돈다 — **"내 컴퓨터에서는 됐는데요?" 문제를 없애는 것**이 Docker의 존재 이유이고, 오늘 그것을 로컬→서버로 직접 실습했다.

### 5-1. compose 파일 2벌: "누가 실행하느냐"로 나뉜다

| 파일 | 서비스 구성 | 실행 주체 / 방법 |
|---|---|---|
| `docker-compose-local.yml` | db, redis, bn, fn + **jenkins** (**5개**) | **사람**이 수동 실행 — `docker-compose -f docker-compose-local.yml up` (부트스트랩, 오늘 실습에서 돌린 파일) |
| `docker-compose.yml` | db, redis, bn, fn (**4개**, jenkins 없음) | **Jenkins Job**이 자동 실행 — `docker-compose up -d` (기본 파일명이라 옵션 없이 자동 인식) |

- 나누는 기준은 로컬/서버 위치가 아니라 **실행 주체**: 사람이 최초 1회 띄우는 전체 환경(jenkins 포함) vs Jenkins가 배포 때마다 갈아끼우는 앱 스택(jenkins 제외)
- **기본 이름을 앱 스택에 준 이유**: 자동화(Jenkins Job)가 칠 명령을 `docker-compose up -d` 한 줄로 최소화. `-f` 타이핑의 번거로움은 어차피 한 번만 치는 사람 쪽에 몰아줌
- **기본 yml에 jenkins가 없는 것은 누락이 아니라 핵심 설계**: 배포 대상 compose에 jenkins가 들어 있으면 Jenkins가 배포 중 자기 자신을 내려버린다

### 5-2. EC2 기동 명령

```bash
# 재로그인 (docker 그룹 반영)
# ec2-user 로그인 → sudo su

git clone https://github.com/jsh340866/DEPLOY_DOCKER.git
cd DEPLOY_DOCKER/04_DOCKER_COMPOSE_DEPLOY

docker-compose up        # 기본 docker-compose.yml을 읽어 이미지 빌드 + 컨테이너 기동
```

- `up` 한 번에 **yml 읽기 → 각 폴더(./DB, ./BN…)의 Dockerfile로 이미지 빌드 → 컨테이너 기동**이 전부 일어난다 (별도 `docker build` 불필요)
- yml은 컨테이너 안에 들어가는 게 아니라 `up` 시점에만 읽히는 **주문서** → yml을 수정해도 돌던 컨테이너는 안 바뀌며, `up -d`(설정 변경) 또는 `up -d --build`(코드/Dockerfile 변경)로 재반영해야 한다

### 5-3. 앱 스택 구성 (양쪽 파일 공통 4개)

| 서비스 | 컨테이너명 | 포트(호스트→컨테이너) | 역할 |
|---|---|---|---|
| db | db-container | 3330→3306 | MySQL (볼륨 `db-data`로 데이터 보존) |
| redis | redis-container | 6380→6379 | Redis |
| bn | bn-container | 8080→8080 | Spring Boot 백엔드 |
| fn | fn-container | 3000→80 | 프론트엔드(웹서버) |

- 전 컨테이너가 커스텀 브리지 네트워크 `custom-network`(172.30.0.0/24)에 소속 → **컨테이너 이름/서비스명이 곧 호스트명**(DNS)으로 풀림
  - 예: bn의 DB 접속 URL = `jdbc:mysql://db-container:3306/testdb`, Redis는 `SPRING_REDIS_HOST: redis`
- **기동 순서 보장**: `depends_on` + `healthcheck` 조합
  - db가 healthy(`mysqladmin ping`) → bn 기동 → bn이 healthy(`/actuator/health`) → fn 기동

### 5-4. jenkins 서비스 (docker-compose-local.yml에만 존재)

```yaml
jenkins:
  image: jenkins
  build:
    context: ./JENKINS          # 4번 섹션의 커스텀 Dockerfile로 빌드
  container_name: jenkins-container
  ports:
    - "9090:8080"               # 0708에 열어둔 보안 그룹 9090 재사용
    - "50000:50000"             # Jenkins 에이전트 연결용 포트
  volumes:
    - jenkins-data:/var/jenkins_home            # 설정/플러그인/Job 영속화 → 재생성해도 유지
    - /var/run/docker.sock:/var/run/docker.sock # 호스트 Docker를 빌려 쓰는 DooD 연결 통로
  networks:
    - custom-network
```

**기본 yml(배포 대상)에서 jenkins를 빼고 -local에만 두는 이유** — 앱 스택(db/redis/bn/fn)은 배포 때마다 내렸다 올리는 대상이지만, Jenkins는 그 배포를 시키는 주체라 수명이 다르다. Jenkins Job이 다루는 기본 yml에 jenkins가 섞여 있으면 배포 중 자기 자신을 내리게 되므로, jenkins는 사람이 수동으로 다루는 -local 쪽에만 둔다.

**부트스트랩 개념** — 자동화 도구(Jenkins) 자체는 자동으로 못 띄우므로, **최초 1회만 사람이 수동으로 기동**하고 이후에는 Jenkins가 앱 스택을 반복 배포한다. jenkins 서비스에 `restart: always`를 넣어야 EC2 재부팅 후에도 "1회 수동" 약속이 유지된다.

> ⚠️ `up`(포그라운드) 상태에서 Ctrl+C는 컨테이너를 정지시키지만, `logs -f`에서의 Ctrl+C는 구경만 중단 — 같은 키라도 어디에 붙어 있느냐로 결과가 다르다. 운영은 `up -d`(백그라운드) + `logs -f`(관찰) + `down`(종료).
> ⚠️ 터미널의 `bn-container | ...` 로그는 compose가 여러 컨테이너 출력에 이름표를 붙여 보여주는 것 — 터미널은 "창", 실행 주체는 Docker.
> ⚠️ `MYSQL_USER: dbconn`을 만들어 두고 bn은 `root`로 접속 중 — 동작은 하지만 계정 불일치. 실서비스라면 dbconn 사용 권장.
> ⚠️ DB(`db-container`)는 컨테이너명, Redis(`redis`)는 서비스명으로 참조 — 둘 다 동작하지만 표기 통일이 바람직.
> ⚠️ 각 컨테이너의 `ipv4_address` 고정 IP는 실제 통신(DNS 기반)에 안 쓰임 — 학습용 장치.
> ⚠️ DB 비밀번호가 yml에 평문 → 실서비스는 `.env` 파일로 분리 대상.

## 6. 오늘 배운 것 요약

- 직접 설치(systemd) Jenkins → **Docker 컨테이너 방식**으로 전환, 공식 이미지에 없는 docker/aws CLI는 **커스텀 Dockerfile**로 추가 (`USER root` 설치 후 `USER jenkins` 복귀)
- **로컬 검증(-f docker-compose-local.yml) → push → EC2 clone → up** — 같은 yml이 어디서든 동일하게 도는 것이 Docker의 핵심 가치
- compose 2벌의 기준은 **실행 주체**: `-local`(jenkins 포함 5개)은 사람이 `-f`로 수동 부트스트랩, 기본 `docker-compose.yml`(앱 4개)은 Jenkins Job이 옵션 없이 자동 배포
- 배포 대상 compose에서 jenkins를 **분리** — 배포 주체가 배포 대상에 섞이면 자기 자신을 내리게 된다. Jenkins만 **최초 1회 수동 기동(부트스트랩)** 후 앱 스택을 반복 배포
- 컨테이너 안에서 Docker를 쓰는 방식은 호스트의 **docker.sock을 마운트하는 DooD 구조**가 기본
- compose에서 **같은 네트워크의 컨테이너는 이름이 곧 주소**(DNS)이고, `depends_on` + `healthcheck`로 DB → 백엔드 → 프론트 기동 순서를 보장한다
- `usermod -aG docker`는 **재로그인해야 반영** / `systemctl`은 대소문자 구분 — 즉석 필기에서 놓치기 쉬운 부분
- 오전(HTTPS 배포)까지가 "직접 설치형" 파이프라인의 완성이었다면, 오후는 같은 파이프라인을 **컨테이너 기반으로 다시 쌓는 출발점** — 다음 단계는 사람이 치던 `up -d --build`를 Jenkins Job(push → 자동배포)으로 대체하는 것
