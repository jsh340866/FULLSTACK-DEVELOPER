# TIL: 로컬 Jenkins ↔ GitHub ↔ EC2 자동배포 파이프라인 구축

> 📅 2026-07-10
> 주제: 기존 Docker 리소스(컨테이너/이미지/볼륨)를 전부 정리하고 `docker-compose-local.yml`로 클린 재기동, Jenkins Job에 GitHub 저장소를 연결하고 Execute Shell에서 EC2로 SSH 배포하는 스텝을 추가해 **Build Now 클릭 한 번으로 GitHub → EC2까지 이어지는 자동배포**를 완성. 오후에는 FN(Nginx) 컨테이너가 SSL을 직접 종단하도록 `docker-compose.yml`도 함께 수정.

---

## 1. 학습 목표

- 이전 실습에서 꼬인 Docker 리소스(컨테이너/이미지/볼륨)를 **전부 삭제하고 클린 상태**에서 다시 시작한다
- **VSCode 터미널**에서 `docker-compose-local.yml`을 재기동해 db/redis/bn/fn/jenkins 5개 컨테이너를 다시 띄운다
- Jenkins Job에 **GitHub 저장소 연동**(Source Code Management)을 설정한다
- **Execute Shell** 빌드 스텝에서 pem 키로 EC2에 직접 SSH 접속해, EC2가 `git pull` 후 `docker-compose up -d --build`로 재배포하도록 만든다
- FN(Nginx) 컨테이너가 Spring Boot 대신 **HTTPS 종단점** 역할을 하도록 `docker-compose.yml`/`nginx.conf`를 정리한다

---

## 2. 기존 Docker 리소스 전체 삭제

### 왜 필요한가?

- 어제(0709) 여러 번 컨테이너를 새로 만들고 지우고 하면서 **이미지/볼륨이 꼬인 상태**였음
- 특히 `jenkins-data` 볼륨에 예전 설정(플러그인, Job, 크리덴셜)이 남아있으면 오늘 처음부터 다시 구성하는 실습과 뒤섞여 원인 추적이 어려워짐 → **컨테이너, 이미지, 볼륨을 전부 지우고** 완전히 새로 빌드

```bash
# 실행 중/정지된 컨테이너 전체 삭제
docker rm -f $(docker ps -aq)

# 이미지 전체 삭제
docker rmi -f $(docker images -aq)

# 볼륨 전체 삭제 (jenkins-data, db-data 포함)
docker volume rm $(docker volume ls -q)
```

> ⚠️ `jenkins-data` 볼륨을 지우면 Jenkins의 플러그인/Job/크리덴셜이 전부 초기화된다 → 오늘은 Jenkins Job(GitHub 연동, Execute Shell 배포 스텝)을 **처음부터 다시 설정**해야 했다.
> ⚠️ `db-data` 볼륨도 함께 삭제되므로 DB 데이터도 초기화된다 — 학습용 환경이라 문제없지만, 운영 환경이라면 절대 이렇게 지우면 안 되는 명령.

## 3. VSCode 터미널에서 `docker-compose-local.yml` 재기동

```bash
docker-compose -f docker-compose-local.yml up -d --build
```

- `db / redis / bn / fn / jenkins` **5개 컨테이너**가 이미지 빌드부터 새로 진행되며 기동
- Jenkins가 볼륨까지 초기화된 새 컨테이너라 최초 접속 시 **Unlock Jenkins** 화면부터 다시 진행

```bash
# 초기 관리자 비밀번호 확인
docker exec jenkins-container cat /var/jenkins_home/secrets/initialAdminPassword
```

- `http://localhost:9090` 접속 → 비밀번호 입력 → **Install suggested plugins** → 관리자 계정 생성까지 재실행

> ⚠️ 어제 만들어둔 sudoers/443 관련 설정은 **EC2 쪽** 설정이라 이번 로컬 Jenkins 초기화와는 무관 — 초기화되는 건 로컬 Jenkins 컨테이너 내부 설정뿐이다.

## 4. Jenkins Job 생성 — GitHub 연동

### 왜 필요한가?

- Jenkins가 배포할 최신 코드를 어디서 가져올지 알아야 함 → **Source Code Management**에 GitHub 저장소를 등록

### 설정

1. Jenkins 대시보드 → **새로운 Item** → Freestyle project 생성
2. **Source Code Management** → Git 선택
   - Repository URL: `https://github.com/jsh340866/DEPLOY_DOCKER.git`
   - Branch: `*/main`
3. **Build Triggers**: 오늘은 GitHub Webhook 같은 자동 트리거 없이, **사람이 "Build Now"를 직접 눌러서** 파이프라인을 시작하는 방식으로 진행
   - 대신 Build Now 한 번으로 **checkout → (필요시 로컬 빌드/테스트) → EC2 배포 스텝**까지 전부 자동으로 이어짐

> ⚠️ 웹훅 기반 완전 자동 트리거(push하면 자동 빌드)는 오늘 범위에 포함되지 않음 — "빌드 버튼 클릭"이 트리거, 그 이후 단계가 자동화된 것.

## 5. Execute Shell — SSH로 EC2 배포

### 왜 필요한가?

- 로컬 Jenkins 컨테이너가 GitHub에서 최신 코드를 가져와도, 실제 서비스는 **EC2**에서 떠 있어야 함
- 오늘은 별도 플러그인(Publish Over SSH 등) 없이, **Execute Shell 빌드 스텝 안에서 pem 키로 직접 `ssh` 명령을 실행**하는 방식으로 구성
- EC2가 이미지를 pull 받는 레지스트리 경유 방식이 아니라, **EC2 자신이 `git pull` 후 `docker-compose up -d --build`로 직접 재빌드**하는 방식 (0709 학습 때 EC2에 직접 clone해뒀던 `DEPLOY_DOCKER/04_DOCKER_COMPOSE_DEPLOY` 흐름의 연장)

### Execute Shell 빌드 스텝

```bash
ssh -i /var/jenkins_home/keys/DEPLOY_SBONLY.pem -o StrictHostKeyChecking=no ec2-user@15.165.253.103 << 'EOF'
cd DEPLOY_DOCKER/04_DOCKER_COMPOSE_DEPLOY
git pull origin main
sudo docker-compose up -d --build
EOF
```

> ⚠️ pem 키를 Jenkins 컨테이너 안에서 사용하려면 `docker-compose-local.yml`의 jenkins 서비스에 키 파일을 볼륨으로 마운트해두거나 컨테이너 안에 직접 복사해둬야 한다 — 정확한 마운트 경로/방식은 필기가 유실되어 확정 못 함. 위 경로(`/var/jenkins_home/keys/...`)는 일반적인 패턴으로 적어둔 것이라 실제 Job 설정과 대조 확인이 필요하다.
> ⚠️ pem 키 파일은 `chmod 400`이 아니면 ssh가 `Permissions 0644 for ... are too open` 에러로 접속을 거부한다 — 컨테이너 안에 키를 넣을 때 권한도 함께 맞춰줘야 한다.
> ⚠️ `docker-compose up -d --build`는 **EC2 자신의 docker 데몬**에서 실행된다. 로컬에서 빌드한 이미지를 옮기는 게 아니라, EC2가 git pull로 받은 최신 Dockerfile/소스로 **자체 재빌드**하는 구조 — 7/9일차에 사람이 손으로 치던 `up -d --build`를 오늘 Jenkins Job이 대신하게 된 것.
> ⚠️ `StrictHostKeyChecking=no`는 최초 접속 시 `Are you sure you want to continue connecting?` 프롬프트가 Jenkins 비대화형 셸을 막는 것을 피하기 위한 옵션 — 실서비스라면 known_hosts를 사전에 등록하는 편이 더 안전하다.

## 6. FN(Nginx)이 HTTPS를 직접 처리하도록 배포 구성 변경

### 왜 필요한가?

- 어제(0709)까지는 Spring Boot 내장 톰캣이 443에서 직접 SSL을 처리했다
- 오늘은 배포 구조를 Docker Compose 기반으로 옮기면서, **Nginx(FN 컨테이너)가 SSL을 종단하고 내부적으로 Spring Boot(bn)에 프록시**하는 일반적인 구조로 변경

### `nginx.conf` — HTTP→HTTPS 리다이렉트 + HTTPS 서버 블록 추가

```nginx
# HTTP(80) → HTTPS(443) 리다이렉트
server {
    listen       80;
    server_name  www.jsh340866.store;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
    location / {
        return 301 https://$host$request_uri;
    }
}

# HTTPS(443) 메인 서버
server {
    listen 443 ssl;
    server_name www.jsh340866.store;

    ssl_certificate     /etc/letsencrypt/live/www.jsh340866.store/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/www.jsh340866.store/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    # React 정적 파일 (SPA 라우팅)
    location / {
        root  /usr/share/nginx/html;
        index index.html;
        try_files $uri /index.html;
    }

    # /api 등은 Spring Boot(bn) 컨테이너로 프록시
}
```

### `docker-compose.yml` — 포트/볼륨 변경

```yaml
fn:
  image: fn
  build:
    context: ./FN
  container_name: fn-container
  ports:
    - "80:80"          # HTTP → HTTPS 리다이렉트용
    - "443:443"        # HTTPS 메인
  volumes:
    - /etc/letsencrypt:/etc/letsencrypt:ro   # 호스트 인증서 → 컨테이너
    - /var/www/certbot:/var/www/certbot      # 갱신 챌린지용

bn:
  # ports:
  #   - "8080:8080"     # 외부 노출 제거 — fn(nginx)이 내부 네트워크로만 프록시
```

> ⚠️ 처음 작성한 diff에는 `volumes`가 `vloumes`로 오타가 나서 인증서 마운트가 적용되지 않는 문제가 있었고, 바로 다음 커밋에서 오타를 수정했다.
> ⚠️ `bn`(Spring Boot)의 `8080:8080` 포트를 주석 처리한 것은 **외부에서 직접 접근을 막고 fn(nginx)을 통해서만 접근**하게 하려는 의도 — 같은 `custom-network`에 있으므로 fn → bn 프록시는 `bn-container:8080`으로 계속 가능하다.
> ⚠️ `EXPOSE 80 443`으로 Dockerfile도 함께 수정 — `EXPOSE`는 문서화 목적이라 없어도 포트 매핑엔 영향 없지만, 컨테이너가 실제로 443을 리스닝한다는 걸 명시하는 관례.

## 7. 오늘 배운 것 요약

- 꼬인 Docker 상태(컨테이너/이미지/볼륨)는 **전부 삭제 후 클린하게 재기동**하는 것이 가장 확실한 해결책 — 단, `jenkins-data`를 지우면 Jenkins 설정이 초기화된다는 트레이드오프를 인지해야 한다
- Jenkins Job의 **Source Code Management**로 GitHub 저장소를 연결하면, Build 시점마다 최신 코드를 checkout한다
- 별도 플러그인 없이도 **Execute Shell + pem 키 SSH**로 EC2에 명령을 실행시킬 수 있다 — EC2가 `git pull` 후 자체적으로 `docker-compose up -d --build`를 실행하는 방식으로 재배포
- 즉 오늘 완성된 흐름: **로컬에서 코드 push → Jenkins Build Now 클릭 → GitHub checkout → SSH로 EC2 접속 → EC2가 git pull + docker-compose 재빌드** — 7/9일차 예고("사람이 치던 `up -d --build`를 Jenkins Job으로 대체")가 실제로 구현된 단계
- 배포 구조가 Docker Compose 기반으로 바뀌면서 SSL 종단 지점도 **Spring Boot 내장 톰캣 → Nginx(FN 컨테이너)**로 이동 — 8080은 내부 전용, 80/443만 외부에 노출
- 완전 자동(웹훅 기반 push-to-deploy)까지는 아니고, 오늘은 **Build Now 클릭이 트리거, 그 이후 단계가 자동화**된 반자동 파이프라인 단계

> ⚠️ 이 문서는 원래 작성해두었던 상세 필기가 유실된 뒤, git 커밋 diff와 이전 날짜(7일차) 흐름, 사용자 확인 답변을 바탕으로 재구성한 내용이다. Jenkins Job의 정확한 화면 설정값(pem 키 마운트 경로, 크리덴셜 등록 방식 등)은 실제 Job 설정과 다를 수 있어 추후 대조 확인이 필요하다.
