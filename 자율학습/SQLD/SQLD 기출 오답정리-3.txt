
1. 다음 SQL문에 대한 설명으로 올바른 것은?

SQL
SELECT *
FROM SQLD_33
WHERE EMP_NAME LIKE 'A%'
① 테이블의 EMP_NAME이 A 또는 a로 시작하는 모든 ROW

② 테이블의 EMP_NAME이 A로 시작하는 모든 ROW

③ 테이블의 EMP_NAME이 A로 끝나는 모든 ROW

④ 테이블의 EMP_NAME이 A 또는 a로 끝나는 모든 ROW

### 정답 : 2

특정 문자로 시작하는 것을 조회하기 위해서는 LIKE문을 사용해야 한다. 그리고 'A%'는 A로 시작하는 것을 조회한다.

💡 핵심 콕콕 해설
1. SQL 명령어 vs 데이터의 대소문자 구분
- SQL 키워드(SELECT, FROM, WHERE 등)나 테이블명, 컬럼명은 대소문자를 구분하지 않아요.
- 하지만 작은따옴표(' ') 내부에 들어가는 실제 데이터 값은 대소문자를 철저하게 구분합니다.
- 따라서 LIKE 'A%'는 소문자 'a'는 제외하고, 오직 대문자 'A'로 시작하는 데이터만 찾아냅니다. (정답 ②번)

2. LIKE 연산자 와일드카드 기호 (%) 위치 기억하기
- 'A%': A로 시작하는 문자열 (예: Alice, Allen)
- '%A': A로 끝나는 문자열 (예: LINDA, JESSICA)
- '%A%': 위치 상관없이 A를 포함하는 문자열 (예: AMAZON)

3. 사원 테이블에 사원번호는 기본키로 설정되어 있다. SQL문으로 사원번호 1번을 검색하는데 사원 테이블에는 하나의 ROW만 저장되어 있다. 이때 유리한 스캔 방식은 무엇으로 판단되는가?

① Unique Index Scan
② Non-Unique Index Scan
③ Index Full Scan
● Table Full Scan

###
정답 : 4

하나의 데이터(행)를 읽기 위해서는 인덱스를 사용하지 않고 테이블을 FULL SCAN하는 것이 효율적이다. 즉, 검색되는 행이 1건이므로 굳이 인덱스를 읽지 않고 바로 테이블을 검색해야 한다.

🛠️ 두 방식의 실제 작동 과정 비교
데이터베이스가 하나의 데이터를 찾기 위해 움직이는 단계를 비교해 보면 왜 4번이 정답인지 확 와닿으실 거예요.

1️. Unique Index Scan을 할 경우 (총 2번 접근)
- 인덱스 블록에 먼저 접근해서 사원번호 1번이 어디 있는지 주소(ROWID)를 찾습니다.
- 알아낸 주소를 바탕으로 실제 데이터가 있는 테이블 블록으로 가서 데이터를 읽습니다.
💥 결과: 총 2번의 블록 I/O(접근) 발생!

2. Table Full Scan을 할 경우 (총 1번 접근)
- 인덱스를 거치지 않고, 테이블에 데이터가 1건밖에 없으니 테이블 블록을 그냥 바로 읽고 끝냅니다.
💥 결과: 총 1번의 블록 I/O(접근) 발생!

4. 다음 중 DEPT 테이블에 존재하지 않는 부서의 사원을 삭제하는 SQL은? (단, DEPTNO은 PK이다.)

① DELETE FROM EMP WHERE DEPTNO NOT IN (SELECT DEPTNO FROM DEPT);
② DELETE * FROM EMP WHERE DEPTNO != ALL (SELECT DEPTNO FROM DEPT);
● DELETE FROM EMP WHERE NOT EXISTS DEPT.DEPTNO = EMP.DEPTNO;
④ DELETE FROM EMP WHERE DEPTNO IS NULL;

### 
정답 : 1

DEPTNO가 DEPT 테이블에 존재하지 않는 사원을 올바르게 삭제한다.
<오답 피하기>
②, ③ 문법 오류에 해당한다.
④ 조건 자체가 문제 의도와 다르며, DEPTNO가 PK이므로 NOT IN 사용 시에도 NULL에 대한 우려가 없다.

🔍 핵심 해설: 왜 1번이 정답이고 3번은 오답일까?
승원님이 고르신 3번은 의미상으로는 맞닿아 있지만, SQL 문법(Syntax)을 완전히 틀리게 작성해서 오답 처리가 되었어요. 각 보기의 문제점을 콕 짚어드릴게요.

❌ 3번이 오답인 결정적인 이유 (문법 오류)
NOT EXISTS 연산자는 뒤에 반드시 괄호 () 형태의 서브쿼리(SELECT문)가 와야 합니다.
- 틀린 문법 (3번): WHERE NOT EXISTS DEPT.DEPTNO = ... ➡️ 괄호도 없고 SELECT문도 없어서 에러 발생!
- 올바른 문법으로 고치면: 
```sql
DELETE FROM EMP A
WHERE NOT EXISTS (SELECT 1 FROM DEPT B WHERE B.DEPTNO = A.DEPTNO);

이렇게 괄호와 함께 내부에 서브쿼리를 제대로 짜주어야 정상 작동합니다.

⭕ 1번이 정답인 이유
- NOT IN (SELECT DEPTNO FROM DEPT)는 "DEPT 테이블의 부서 번호 목록에 포함되지 않는 것만 골라라"라는 뜻입니다.
- 문제에서 요구한 "DEPT 테이블에 존재하지 않는 부서의 사원을 삭제"하라는 조건과 완벽하게 일치하며, 문법적으로도 아주 깨끗합니다.

⚠️ 나머지 보기 오답 정리
- ②번: DELETE * FROM 이 문법은 틀렸습니다. DELETE 문은 SELECT *와 달리 별표(*)를 쓰지 않고 DELETE FROM 테이블명으로 시작해야 합니다.
- ④번: 단순히 부서 번호가 NULL인 것을 지우라는 뜻이므로, "DEPT 테이블에 존재하지 않는 부서"를 찾으라는 문제의 의도와는 완전히 무관합니다.

13. 서브쿼리의 종류 중에 서브쿼리를 실행하고 한 행, 한 칼럼을 반환하는 서브쿼리를 무엇이라고 하는가?

① Looping
② Scala Subquery
③ Associative Subquery
● Access Subquery

###
정답 : 2

스칼라 서브쿼리(Scala Subquery)는 SELECT문에서 사용하는 서브쿼리로 한 행만 반환한다.

## 중요 외울것

SELECT 절 = 스칼라 서브쿼리(Scalar Subquery) = 결과가 반드시 **1행 1열(단일값)**
FROM 절 = 인라인 뷰(Inline View) = 서브쿼리 결과를 하나의 가상 테이블처럼 사용함
WHERE 절 / HAVING 절 = 중첩 서브쿼리(Nested Subquery)  = 조건문 안에서 비교연산자(IN,ANY,ALL 등)와 함께 사용
WITH 절 = 서브쿼리 팩토링(Subquery Factoring) = 쿼리 가장 상단에 마치 하나의 '임시 테이블'처럼 이름을 붙여서 선언

16. 다음 중 SELF JOIN을 수행해야 할 때는 어떤 경우인가?

① 한 테이블 내에서 두 칼럼이 연관 관계가 있다.
② 두 테이블에 연관된 칼럼은 없으나 JOIN을 해야 한다.
③ 두 테이블에 공통 칼럼이 존재하고 두 테이블이 연관 관계가 있다.
● 한 테이블 내에서 연관된 칼럼은 없으나 JOIN을 해야 한다.

① SELF JOIN
② CROSS JOIN 성격
③ INNER/OUTER JOIN 가능
④ 해당 없음

###
정답 : 1

SELF JOIN은 하나의 테이블에서 두 개의 칼럼이 연관 관계를 가지고 있는 경우에 사용한다.

🔍 핵심 해설: SELF JOIN이 정확히 뭐야?
승원님이 고르신 4번은 "연관된 칼럼이 없다"고 해서 오답이 되었어요. 조인(JOIN)이라는 행위 자체가 무조건 두 컬럼 간의 '연관성(관계)'을 바탕으로 엮는 것이기 때문에 연관된 컬럼이 없으면 조인을 할 수 없답니다.

셀프 조인(SELF JOIN)의 핵심은 말 그대로 "자기 자신과 조인한다"는 뜻이에요. 별도의 다른 테이블을 불러오는 게 아니라, 똑같은 테이블 하나를 가지고 그 안에서 컬럼 대 컬럼으로 매칭을 시키는 방식입니다.

💡 가장 대표적인 예시: 사원과 상사(매니저) 관계
사원 테이블(EMP)을 보면 보통 다음과 같이 컬럼이 구성되어 있어요.
- EMPNO (사원번호)
- ENAME (사원이름)
- MGR (상사의 사원번호)

여기서 "특정 사원의 상사 이름"을 알고 싶다면 어떻게 해야 할까요? 상사도 결국 회사 직원이므로 똑같은 사원 테이블 안에 데이터가 들어있겠죠?

SQL
SELECT A.ENAME AS [사원 이름], 
       B.ENAME AS [상사 이름]
FROM EMP A 
JOIN EMP B ON A.MGR = B.EMPNO; -- 한 테이블 내의 두 컬럼(MGR, EMPNO)을 연관지음!
이처럼 하나의 테이블(EMP) 안에서 MGR 컬럼과 EMPNO 컬럼이 서로 연관 관계를 맺고 추적해 들어가야 하기 때문에, 정답은 ①번 "한 테이블 내에서 두 칼럼이 연관 관계가 있다"가 됩니다.

📌 보기 오답 정리
- ②, 4번: 기본적으로 조인은 서로 연결할 수 있는 '연관 컬럼(조건)'이 무조건 존재해야 성립합니다. 연관 컬럼이 없는데 억지로 엮는 조인은 Cross Join(카테시안 곱) 같은 특수한 경우인데, 문제의 의도와는 맞지 않습니다.
- ③번: 이것은 일반적인 테이블 간의 조인(예: EMP 테이블과 DEPT 테이블 조인)에 대한 설명입니다. 'SELF' 조인이 아니에요.

21. 두 개 릴레이션 Student와 Department가 있을 때, 질의문 "SELECT * FROM Student s, Department d WHERE s.dept > 100;"을 수행하려고 한다. 이 질의 수행으로 생성되는 결과 릴레이션의 차수(Degree)와 카디널리티(Cardinality)는 각각 얼마인가? (단, 릴레이션 Student의 애트리뷰트 '소속(dept)'은 릴레이션 Department의 애트리뷰트 '코드(dno)'를 외부키로 참조한다)

[Student]
학번(sno) | 성명(sname) | 주소(address) | 성적(score) | 소속(dept)
9801 | 홍길동 | 서울 | 80 | 100
9802 | 김철수 | 대전 | 90 | 200
9803 | 이순자 | 강릉 | 90 | 100
9805 | 이원영 | 부산 | 95 | 200
9806 | 홍남순 | 서울 | 65 | 300

[Department]
코드(dno) | 학과명(dname) | 학과장(manager)
100 | 정통 | 이순신
200 | 전자 | 강감찬
300 | 기계 | 김유신

① 차수 = 5, 카디널리티 = 3
② 차수 = 5, 카디널리티 = 2
③ 차수 = 8, 카디널리티 = 9
● 차수 = 8, 카디널리티 = 3

###
정답 : 3

🔍 개념 정리: 차수(Degree)와 카디널리티(Cardinality)
- 차수 (Degree): 릴레이션(테이블)의 열(Column, 애트리뷰트)의 총 개수
- 카디널리티 (Cardinality): 릴레이션(테이블)의 행(Row, 튜플)의 총 개수

✍️ 문제 풀이 및 계산 과정
질의문을 분석해서 최종 결과 테이블이 어떻게 만들어지는지 확인해 봅시다.

SQL
SELECT * FROM Student s, Department d WHERE s.dept > 100;

1️. 차수(Degree) 계산하기: 열의 개수
SELECT *를 사용해 두 테이블의 모든 컬럼을 다 가져오고 있습니다.
- Student 테이블의 열 개수 = 5개 (학번, 성명, 주소, 성적, 소속)
- Department 테이블의 열 개수 = 3개 (코드, 학과명, 학과장)
- 최종 차수 = 5 + 3 = 8 (따라서 ①, ②번은 제외됩니다.)

2️. 카디널리티(Cardinality) 계산하기: 행의 개수
여기서 중요하게 보셔야 할 점은 FROM Student s, Department d 입니다. 조인 조건(ON s.dept = d.dno) 없이 쉼표(,)로만 연결했기 때문에, 이는 두 테이블의 모든 경우의 수를 곱하는 교차 조인(Cross Join, 카테시안 곱)을 먼저 수행한다는 뜻입니다.

여기에 WHERE s.dept > 100이라는 필터링 조건이 붙었습니다.

먼저 Student 테이블에서 소속(dept) > 100인 행을 찾습니다.
- 9801 (dept 100) ➡️ 탈락 (100은 100보다 크지 않음)
- 9802 (dept 200) ➡️ 선택 (1)
- 9803 (dept 100) ➡️ 탈락
- 9805 (dept 200) ➡️ 선택 (2)
- 9806 (dept 300) ➡️ 선택 (3)
💥 조건을 만족하는 Student 행은 총 3개입니다.

이 선택된 3개의 행이 Department 테이블의 모든 행(3개)과 결합(Cross Join)하게 됩니다.
- Department 테이블의 행 개수 = 3개
- 최종 카디널리티 = 조건을 만족하는 Student 행(3개) X Department의 모든 행(3개) = 3 X 3 = 9

따라서 정답은 차수 = 8, 카디널리티 = 9인 ③번이 됩니다!

28. 다음 테이블과 SQL을 기준으로 실행 결과가 올바른 것은?

[TB_USER] 테이블
ID | NAME | GRADE | STATUS
1 | Kim | A | ACTIVE
2 | Lee | B | INACTIVE
3 | Park | A | INACTIVE
4 | Choi | C | ACTIVE
5 | Jang | B | ACTIVE

[쿼리]

SQL
SELECT NAME, GRADE, STATUS
FROM TB_USER
WHERE GRADE = 'A' OR GRADE = 'B' AND STATUS = 'ACTIVE';

###
정답 : 
② (결과 테이블)
Kim | A | ACTIVE
Park | A | INACTIVE
Jang | B | ACTIVE

⚡ 수학과 똑같은 SQL 연산자 우선순위
- 수학에서 더하기(+)와 곱하기(X)가 있으면 곱하기를 먼저 하죠?
- SQL 조건절에서도 OR보다 AND가 우선순위가 훨씬 높습니다!

따라서 문제의 조건절은 컴퓨터 내부적으로 다음과 같이 AND 부분에 자동으로 괄호가 쳐진 것처럼 해석됩니다.

SQL
WHERE GRADE = 'A' 
   OR (GRADE = 'B' AND STATUS = 'ACTIVE');

📊 데이터 대입해서 찾아보기
컴퓨터가 해석하는 바른 조건에 따라 데이터를 하나씩 매칭해 볼까요? 결과적으로 [조건 1]을 만족하거나, [조건 2]를 만족하는 데이터를 다 뽑으면 됩니다.
- [조건 1] GRADE = 'A' 인 사람 모두
- [조건 2] GRADE = 'B' 이면서 STATUS = 'ACTIVE' 인 사람 모두

1건씩 판정:
- Kim (A / ACTIVE): [조건 1] 만족! ➡️ 선택 ⭕
- Lee (B / INACTIVE): [조건 1] 탈락. [조건 2]도 STATUS가 INACTIVE라 탈락. ➡️ 탈락 ❌
- Park (A / INACTIVE): [조건 1] GRADE = 'A' 만족! (상태가 INACTIVE여도 조건 1을 통과했으므로 무조건 선택됩니다.) ➡️ 선택 ⭕
- Choi (C / ACTIVE): 둘 다 탈락. ➡️ 탈락 ❌
- Jang (B / ACTIVE): [조건 1] 탈락. 하지만 [조건 2] GRADE='B' 이고 ACTIVE이므로 만족! ➡️ 선택 ⭕

따라서 최종적으로 선택되는 사람은 Kim, Park, Jang 총 3명이 되어 정답은 ②번이 됩니다!

💡 요약 세팅!
- AND는 OR보다 힘이 세서 먼저 묶여서 계산된다!
- 만약 출제자가 1번을 정답으로 만들고 싶었다면 반드시 WHERE (GRADE = 'A' OR GRADE = 'B') AND STATUS = 'ACTIVE' 형태로 괄호를 직접 적어주었어야 합니다.

30. 다음 설명이 나타내는 데이터 모델의 개념은 무엇인가?

학생이라는 엔터티가 있을 때 학점이라는 속성값의 범위는 0.0에서 4.0 사이의 실수값이며 주소라는 속성은 길이가 20자리 이내의 문자열로 정의할 수 있다.

● 시스템 카탈로그(System Catalog)
② 용어 사전(Word Dictionary)
③ 속성 사전(Attribute Dictionary) (주: 원문 오타로 보이며 '속성 사전'의 오기로 추정)
④ 도메인(Domain)

###
정답 : 4 (도메인)

🔍 핵심 해설: '도메인(Domain)'이 정확히 뭔가요?
승원님이 고르신 1번 보기인 '시스템 카탈로그'는 데이터베이스의 모든 객체(테이블, 인덱스 등)에 대한 메타데이터가 저장되는 일종의 '시스템 사전'을 뜻해서 오답이 되었어요.

문제의 핵심 키워드는 "속성값의 범위", "20자리 이내의 문자열"과 같이 특정 속성이 가질 수 있는 '합합적인 값들의 집합이자 범위'를 지정하는 것입니다. 데이터 모델링에서는 이를 도메인(Domain)이라고 부릅니다.

💡 일상적인 예시로 이해하기
데이터베이스 테이블을 만들 때, 사용자가 말도 안 되는 데이터를 넣지 못하도록 시스템적으로 가이드라인을 쳐주는 역할을 하는 것이 바로 도메인이에요.
- 성별 속성의 도메인: ['남', '여'] ➡️ 여기에 '외계인'이라는 텍스트가 들어오면 데이터베이스가 팅겨냅니다.
- 나이 속성의 도메인: 0보다 큰 정수 ➡️ 나이에 -5세 같은 값이 들어오는 것을 막아줍니다.
- 학점 속성의 도메인 (문제 예시): 0.0 ~ 4.0 사이의 실수 ➡️ 실수로 4.5나 9.0을 입력하는 오류를 방지합니다.

즉, "엔터티의 속성이 가질 수 있는 동일한 타입의 원자값들의 집합"이자 "값의 범위 제약 조건"이라는 설명이 나오면 무조건 도메인(Domain)을 골라주시면 됩니다.

📌 보기 오답 정리 (가짜 용어들 솎아내기)
- ① 시스템 카탈로그(System Catalog): 데이터베이스 자체에 내장된 테이블, 뷰, 사용자 정보 등 시스템 전체의 메타데이터를 관리하는 저장소입니다. (속성의 값 범위를 정의하는 곳이 아니에요.)
- ② 용어 사전 / ③ 속성 사전: 데이터 표준화를 할 때 단어의 의미를 통일하기 위해 전사적으로 작성하는 문서 파일(또는 시스템)을 의미하며, 데이터 모델의 핵심 논리 개념 자체를 묻는 이 문제의 정답과는 거리가 멉니다.

31. JOIN의 종류에 대한 설명으로 틀린 것은 무엇인가?

① NON-EQUI JOIN은 등가 조건이 성립되지 않은 테이블에 JOIN을 걸어주는 방법이다.
● EQUI JOIN은 반드시 기본키, 외래키 관계에 의해서만 성립된다.
③ OUTER JOIN은 JOIN 조건을 만족하지 않는 데이터도 볼 수 있는 JOIN 방법이다.
④ SELF JOIN은 하나의 테이블을 논리적으로 분리시켜 EQUI JOIN을 이용하는 방법이다.


###
정답 : 2

EQUI JOIN은 반드시 기본키, 외래키 관계에 의해서만 성립되는 것은 아니다. 조인 칼럼이 1:1로 맵핑이 가능하면 사용할 수 있다.

🔍 핵심 해설: 왜 2번이 정답(틀린 설명)일까?
승원님이 아주 정확하게 ②번을 잘 골라내셨어요! 이 문제의 핵심 단어는 바로 "반드시"입니다.

자격증 시험 이론 문제에서 "무조건", "반드시", "절대"라는 극단적인 표현이 들어가면 오답일 확률이 매우 높은데요, 데이터베이스 이론에서도 마찬가지입니다.

⭕ EQUI JOIN(등가 조인)의 진짜 조건
EQUI JOIN은 두 테이블의 컬럼 값이 서로 같음(=)을 조건으로 엮는 가장 일반적인 조인 방식입니다.

많은 사람들이 기본키(PK)와 외래키(FK) 관계로 맺어진 테이블끼리만 = 조인을 하다 보니 "PK-FK 관계여야만 조인이 된다"고 착각하곤 합니다. 하지만 테이블 간에 아무런 제약조건(PK/FK)이 맺어져 있지 않더라도, 데이터 타입이 서로 같고 논리적으로 매핑이 가능하다면 얼마든지 등가 조인(=)을 수행할 수 있습니다.

📊 나머지 보기 완벽 정복 (조인 종류 요약)
시험에 나오는 조인의 핵심 특징들을 보기와 매칭해서 한눈에 기억해 두세요!
- ① NON-EQUI JOIN (비등가 조인): = 연산자가 아니라 >, <, BETWEEN a AND b 같이 같지 않은 조건으로 조인을 맺는 방식입니다. (예: 사원의 급여가 어떤 '급여 등급 테이블'의 최소~최대 범위 사이에 있는지 조인할 때 사용)
- ③ OUTER JOIN (외부 조인): 기존 Inner Join은 양쪽 테이블에 모두 데이터가 존재해야만 결과가 나오지만, OUTER JOIN은 조건에 맞지 않아 한쪽에만 존재하는 데이터(예: 부서가 배정되지 않은 신입사원)까지 버리지 않고 포함하여 출력하는 고마운 조인입니다.
- ④ SELF JOIN (자체 조인): 우리가 저번에 풀었던 문제 기억하시죠? 사원과 상사의 관계처럼 하나의 테이블을 개념적으로 두 개(A, B)인 것처럼 쪼개서 자기 자신과 = 조인을 거는 기법입니다.

33. Hash Join 기법에 대한 설명으로 옳은 것은?

① 조인 작업을 수행할 때는 결과 행의 수가 적은 테이블을 선행 테이블로 사용하는 것이 좋다.
● Hash Join은 해시 함수를 이용하여 조인을 수행하기 때문에 '=' 로 수행하는 조인인 동등조건 이외에도 사용할 수 있다.
③ 해시 테이블을 저장할 때 메모리에 적재할 수 있는 영역의 크기보다 커지면 초과한 크기를 제외한 영역만큼 메모리에 적재한다.
④ Hash Join은 조인 칼럼의 인덱스가 존재하지 않으면 사용할 수 없는 기법이다.

###
정답 : 1

① ⭕

결과 행이 적은(보통 작은) 테이블을 선행/Build 입력으로 쓰는 게 유리

HASH JOIN은 보통 작은 테이블로 해시 테이블 생성합니다.

② ❌

"동등조건(=) 이외에도 사용 가능"

이게 틀림.

HASH JOIN 핵심:

해시값 비교 기반 → 주로 =(EQUI JOIN)

즉,

A.id = B.id

가능.

하지만

A.sal BETWEEN B.low AND B.high
A.id > B.id

같은 NON-EQUI JOIN 은 일반적으로 HASH JOIN 대상 아님.

③ ❌

메모리 초과하면 일부만 적재한다

아님.

메모리 부족하면 보통:

TEMP / DISK 사용
Partitioning
Spill 발생

같은 방식 처리.

"초과분 제외" 하지 않음.

④ ❌

인덱스 없으면 사용 불가

반대에 가까움.

HASH JOIN 특징 중 하나가:

인덱스 없어도 사용 가능

입니다.

시험용 암기:

NL JOIN   → 인덱스 친화적
SM JOIN   → 정렬 후 병합
HASH JOIN → 해시 기반, '=' 조인, 인덱스 불필요

따라서 정답 = ① 입니다.
💡 조인 매커니즘 3대장 핵심 요약
1. Nested Loop Join (NL 조인)
   - 특징: 랜덤 액세스 방식, 인덱스가 아주 중요함.
   - 방향성: 대용량 처리에는 불리, 소량 데이터나 OLTP 환경에 적합.

2. Sort Merge Join (소트 머지 조인)
   - 특징: 양쪽 테이블을 각각 정렬(Sort)한 뒤 병합(Merge)함.
   - 방향성: 인덱스가 없어도 됨, 등가(=)와 비등가(<, >, BETWEEN) 조인 모두 가능.

3. Hash Join (해시 조인)
   - 특징: 메모리에 해시 테이블을 빌드함. 인덱스 없어도 됨. 작은 테이블을 먼저 빌드해야 이득.
   - 방향성: 오직 등가 조인(=)만 가능, 대용량 처리에 최강 효율.

34. 다음 중 아래 테이블 정의와 인덱스 구조를 참고하여, 인덱스를 효율적으로 액세스할 수 없는 검색조건을 고르시오.

[테이블 정의]

SQL
create table 주문 (
    주문번호    int            not null,
    주문자명    varchar(40)    null,
    주문금액    money          null,
    주문일자    varchar(8)     null );
[인덱스 구조]

SQL
create unique index 주문_pk on 주문 (주문번호);
create index 주문_ind1 on 주문 (주문자명);
create index 주문_ind2 on 주문 (주문일자, 주문금액);


① where 주문번호 between 1 and 10
② where 주문자명 like '%홍길동%'
③ where 주문일자 >= '20181201'
● where 주문일자 = '20181201'

참고: 해당 문제의 올바른 정답은 ②번입니다.

###
정답 : 2번

🔍 핵심 해설: 왜 2번이 정답(비효율적 검색)일까?
데이터베이스에서 인덱스(Index)는 책 맨 뒤에 있는 '찾아보기(색인)'와 같습니다. 색인은 가나다순이나 알파벳순으로 정렬되어 있어야 빠르게 찾을 수 있죠. SQL의 인덱스도 마찬가지로 정렬된 상태로 저장됩니다.

하지만 검색 조건의 형태에 따라 이 정렬된 지도를 전혀 쓰지 못하고 테이블 전체를 다 뒤져야 하는 경우가 생깁니다. 이를 인덱스 선두 컬럼 가공 및 변형에 따른 인덱스 미사용이라고 부릅니다.

❌ ②번이 인덱스를 효율적으로 쓸 수 없는 결정적인 이유
- 조건: where 주문자명 like '%홍길동%'
- 설명: LIKE 연산자를 쓸 때, 찾고자 하는 문자열의 맨 앞에 와일드카드 기호인 퍼센트(%)를 붙였습니다.
- 왜 안 될까?: 주문_ind1 인덱스는 '주문자명'을 기준으로 가나다순 정렬이 되어 있습니다. (예: 강감찬, 김유신, 홍길동...) 그런데 %홍길동%이라고 하면 이름 앞에 '김', '이', '박' 등 무엇이든 올 수 있다는 뜻이 됩니다. 인덱스 사전의 첫 글자가 무엇인지 알 수 없기 때문에 데이터베이스는 정렬된 인덱스 지도를 타지 못하고 처음부터 끝까지 다 읽는 Full Table Scan을 하게 됩니다. 매우 비효율적이죠!

⭕ 나머지 보기들이 인덱스를 잘 타는 이유 (정상 작동)
- ①번 (where 주문번호 between 1 and 10)
	- 주문_pk 인덱스가 주문번호 컬럼으로 이쁘게 정렬되어 있습니다. 1번부터 10번까지만 딱 스캔(Index Range Scan)하면 되므로 매우 효율적입니다.
- ③, ④번 (where 주문일자 >= '20181201', where 주문일자 = '20181201')
	- 주문_ind2 인덱스는 (주문일자, 주문금액) 순서로 묶여 있는 결합 인덱스입니다.
	- 인덱스의 첫 번째 컬럼(선두 컬럼)인 주문일자가 조건절에 명확하게 = 이나 >= 형태로 참여하고 있습니다. 따라서 시작 지점을 딱 찍고 인덱스 범위를 효율적으로 훑을 수 있습니다. (승원님이 고르신 4번은 인덱스를 가장 정석적으로 잘 타는 베스트 조건입니다!)

💡 시험장 대비 인덱스 매커니즘 핵심 요약
조건절에 다음과 같은 형태가 오면 인덱스를 정상적으로 타지 못하거나(Full Scan) 비효율적으로 작동하므로 시험 문제용 보기로 정말 잘 나옵니다!
- LIKE '%단어' 또는 LIKE '%단어%' ➡️ 맨 앞에 %가 오면 인덱스 스캔 불가 ❌
- 인덱스 컬럼을 가공하는 경우 (예: WHERE SUBSTR(주문일자, 1, 4) = '2018') ➡️ 컬럼 원본을 훼손하면 인덱스 스캔 불가 ❌
- 결합 인덱스의 선두 컬럼을 빼먹은 경우 ➡️ (주문일자, 주문금액) 인덱스가 있는데 WHERE 주문금액 = 50000 처럼 첫 번째 컬럼을 조건에서 빼먹으면 인덱스 사용 효율 급락 ❌

38. 다음 중 EMP 테이블에서 부서가 10번인 사원들만 선택하여 EMP_TEMP 테이블에 삽입하는 쿼리는? (단, EMP_TEMP와 EMP 테이블의 컬럼 개수, 자료형, 순서는 모두 같다.)

① INSERT INTO EMP_TEMP SELECT * FROM EMP;
● INSERT INTO EMP_TEMP VALUES (SELECT * FROM EMP WHERE DEPTNO = 10);
③ INSERT INTO EMP_TEMP SELECT * FROM EMP WHERE DEPTNO = 10;
④ INSERT * INTO EMP_TEMP FROM EMP WHERE DEPTNO = 10;

###
정답 : 3

① ❌
INSERT INTO EMP_TEMP
SELECT * FROM EMP;

조건 없음.

전체 사원 삽입.

② ❌
INSERT INTO EMP_TEMP
VALUES (
  SELECT * FROM EMP WHERE DEPTNO=10
);

문법 오류.

VALUES 는 보통:

VALUES(10,'SMITH',3000)

처럼 직접 값 입력할 때 사용.

SELECT 결과 넣을 때는 VALUES 안 씀.

③ ⭕
INSERT INTO EMP_TEMP
SELECT *
FROM EMP
WHERE DEPTNO=10;

문법 완벽.

SELECT 결과를 INSERT.

정답.

④ ❌
INSERT * INTO EMP_TEMP FROM EMP ...

SQL 문법 아님.

시험용 암기:

값 직접 입력

INSERT INTO 테이블
VALUES(...)

조회 결과 삽입

INSERT INTO 테이블
SELECT ...

✅ 정답: ③
