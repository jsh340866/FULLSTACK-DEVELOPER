문제

트랜잭션에 대한 설명 중 가장 적절하지 않은 것은?
답안과 정답

1번
하나의 트랜잭션으로 구성된 작업은 부분 COMMIT이 불가하다.
2번
순차적으로 수행되는 작업 A와 B가 하나의 트랜잭션일 경우 A만 실행되고 시스템 장애가 발생했다면 A를 undo해야 한다.
3번
원자성이란 하나의 트랜잭션의 작업이 모두 성공하거나 모두 취소되어야 하는 특징을 말한다.
4번
트랜잭션에 의한 관계는 선택적인 관계 형태를 가진다.

###
정답 : 4번

💡 정답 해설 (왜 4번이 적절하지 않을까요?)
4번: 트랜잭션에 의한 관계는 선택적인 관계 형태를 가진다. (X)
- 이유: 트랜잭션은 데이터베이스의 무결성을 유지하기 위해 "전부 실행되거나, 아니면 전혀 실행되지 않아야 한다(All or Nothing)"는 원자성(Atomicity)을 가장 중요한 특징으로 가져요.
- 따라서 트랜잭션 내부의 작업들은 서로 분리될 수 없으며, 반드시 함께 완료되거나 함께 취소되어야 하는 필수적인(Mandatory) 관계를 가집니다. 선택적으로 이랬다저랬다 할 수 있는 관계가 아니에요!

🔍 승원님의 답안 분석 (왜 2번은 맞는 설명일까요?)
2번: 순차적으로 수행되는 작업 A와 B가 하나의 트랜잭션일 경우 A만 실행되고 시스템 장애가 발생했다면 A를 undo해야 한다. (O)
- 이유: 앞서 말씀드린 트랜잭션의 원자성(All or Nothing) 때문이에요.
- 하나의 트랜잭션 안에 A와 B라는 작업이 묶여 있다면, 둘 다 성공해야만 데이터베이스에 최종 반영(Commit)돼요.
- 하지만 A만 실행된 상태에서 장애가 났다면, 이 트랜잭션은 '절반만 성공한 상태'가 되므로 데이터의 일관성이 깨지게 되죠.
- 따라서 비정상적으로 종료된 트랜잭션을 아예 시작 전 상태로 되돌리기 위해, 이미 실행된 A 작업을 취소(Undo / Rollback)하는 것이 정확히 맞는 절차랍니다.

📝 다른 보기 보기 쉽게 정리해 드릴게요!
- 1번: 하나의 트랜잭션으로 구성된 작업은 부분 COMMIT이 불가하다. (O)
	- 트랜잭션은 통째로 성공하든지 실패하든지 둘 중 하나만 가능해요. "일부만 성공했으니까 요것만 저장(Commit)할게요!"라는 것은 불가능하답니다.

- 3번: 원자성이란 하나의 트랜잭션의 작업이 모두 성공하거나 모두 취소되어야 하는 특징을 말한다. (O)
	- 트랜잭션의 4대 특징(ACID) 중 원자성(Atomicity)에 대한 가장 완벽한 정의예요.
트랜잭션의 핵심은 언제나 "다 같이 성공하든가, 다 같이 망하든가(All or Nothing)!" 이것만 기억하시면 다음번에 유사한 문제가 나와도 절대 틀리지 않으실 거예요.

'Undo = Ctrl + Z'라고 기억하시면 절대 안 헷갈리실 거예요!

아래의 테이블들에 대해서 SQL문을 수행하였을 때의 결과 값은?
지문

SELECT COUNT(*)
FROM TEST29_1 A
WHERE A.COL NOT IN(SELECT COL
FROM TEST29_2);


[TEST29_1]
COL
1
2
3
4

[TEST29_2]
COL
2
NULL



🔍 핵심 요약: NOT IN과 NULL의 치명적인 만남
SQL에서 NOT IN 연산자 뒤에 오는 서브쿼리의 결과에 NULL이 단 하나라도 포함되어 있으면, 전체 쿼리의 결과는 무조건 아무것도 선택되지 않고 0건(또는 NULL)이 돼요.

이유를 컴퓨터가 이해하는 논리식으로 풀어보면 바로 이해하실 수 있어요!

🛠️ 한 단계씩 풀어보는 쿼리 분석
보내주신 테이블의 데이터를 바탕으로 쿼리가 어떻게 변하는지 살펴볼게요.

1단계: 서브쿼리 실행하기
SQL
SELECT COL FROM TEST29_2

- TEST29_2 테이블의 COL 값은 2와 NULL이 있어요.
- 따라서 서브쿼리의 결과는 (2, NULL)이 됩니다.

2단계: 메인 쿼리에 대입하기
이제 원래 쿼리는 다음과 같이 바뀝니다.
SQL
SELECT COUNT(*) FROM TEST29_1 A
WHERE A.COL NOT IN (2, NULL);

3단계: NOT IN을 비교 연산자로 펼쳐보기
컴퓨터는 A NOT IN (B, C)를 처리할 때 내부적으로 (A != B) AND (A != C)로 바꾸어서 연산해요.
즉, TEST29_1의 데이터들을 하나씩 대입해 보면 이렇게 연산이 흘러가요.
- COL이 1일 때: (1 != 2) AND (1 != NULL)
- COL이 2일 때: (2 != 2) AND (2 != NULL)
- COL이 3일 때: (3 != 2) AND (3 != NULL)
- COL이 4일 때: (4 != 2) AND (4 != NULL)

4단계: NULL 비교의 함정 (가장 중요!)
데이터베이스에서 NULL은 '알 수 없는 값(Unknown)'이기 때문에, != 나 = 같은 일반 비교 연산자로는 참(True)인지 거짓(False)인지 판단할 수 없고, 결과가 무조건 Unknown(알 수 없음)이 돼요.
- 1 != NULL 👉 Unknown
- 3 != NULL 👉 Unknown

조건절(WHERE)은 오직 결과가 True(참)일 때만 데이터를 선택해요. 하지만 AND 연산은 하나라도 참이 아니면 최종 결과가 참이 될 수 없기 때문에, 모든 행의 조건이 전부 Unknown 혹은 False가 되어버립니다.

🎯 최종 결론
- TEST29_1 테이블의 어떤 값(1, 2, 3, 4)을 집어넣어도 서브쿼리의 NULL과 비교하는 순간 조건문이 Unknown 상태가 되어 통과하지 못합니다.
- 결국 만족하는 행이 단 한 개도 없기 때문에, COUNT(*)의 결과 값은 0이 나오게 되는 것이랍니다!

💡 시험장 꿀팁!
문제를 풀다가 WHERE 컬럼 NOT IN (SELECT ...) 형태를 만나면, 서브쿼리 결과에 NULL이 들어있는지부터 확인하세요! 만약 NULL이 존재한다면 메인 쿼리의 결과는 계산해 볼 필요도 없이 무조건 데이터가 안 나와서 COUNT는 0이 됩니다.
(만약 NOT IN이 아니라 일반 IN이었다면 NULL을 제외하고 정상적으로 매칭되는 2 하나만 찾아냈을 거예요!)

[문제] 다음 출력 결과로 가장 알맞은 것은?

[지문]
SELECT REGEXP_COUNT('abc1004 zz1234', '\d{2}+') AS C1, 
       REGEXP_COUNT('abc1004-zz1234-100', '\d{2,}+') AS C2
FROM DUAL;

--------------------------------------------------
[정답 및 결과 값]
3번 (2, 3)

[핵심 해설]
1. REGEXP_COUNT 함수는 소스 문자열에서 정규표현식 패턴과 일치하는 횟수(건수)를 반환합니다.
2. 수량자 뒤에 붙은 '+'는 독점적 수량자(Possessive Quantifier)로 작용하거나, 혹은 표준 수량자 중복 오류로 인해 일반적인 '+'와 동일하게 최장 일치(Greedy)로 동작합니다. 오라클 환경에서는 덩어리 자체를 한 번에 매칭합니다.

3. C1 계산: 'abc1004 zz1234'에서 '\d{2}'는 숫자 2개를 뜻합니다.
   - '1004'에서 숫자 2개 묶음 1개 찾음 ('10') -> 남은 '04'에서 숫자 2개 묶음 1개 찾음 ('04') -> 총 2개
   - '1234'에서 숫자 2개 묶음 1개 찾음 ('12') -> 남은 '34'에서 숫자 2개 묶음 1개 찾음 ('34') -> 총 2개
   - 여기에 뒤의 '+' 수량자가 결합하면서 연속된 숫자 덩어리 전체를 하나의 매칭으로 가져갑니다.
   - 결과적으로 '1004' 덩어리 전체에서 1회, '1234' 덩어리 전체에서 1회 매칭되어 C1 = 2가 됩니다.

4. C2 계산: 'abc1004-zz1234-100'에서 '\d{2,}'는 숫자가 2개 이상 연속된 것을 뜻합니다.
   - 첫 번째 숫자 덩어리: '1004' (숫자 2개 이상이므로 조건 만족, 1회)
   - 두 번째 숫자 덩어리: '1234' (숫자 2개 이상이므로 조건 만족, 1회)
   - 세 번째 숫자 덩어리: '100'  (숫자 2개 이상이므로 조건 만족, 1회)
   - 결과적으로 총 3개의 연속된 숫자 덩어리를 찾았으므로 C2 = 3이 됩니다.

5. 따라서 C1 = 2, C2 = 3 이므로 정답은 3번입니다.


[개념 정리] REGEXP_COUNT 패턴별 소스 문자열 예시 및 결과

--------------------------------------------------
1. \d{n} 패턴 (정확히 n개의 숫자 묶음 찾기)
- 패턴: '\d{2}' (숫자 2개씩 짝지어 세기)

  Example A) SELECT REGEXP_COUNT('123', '\d{2}') FROM DUAL;
  👉 결과: 1
  * 해설: 앞의 '12'에서 1번 찾고, 남은 '3'은 1글자라 숫자가 부족해서 안 세어집니다.

  Example B) SELECT REGEXP_COUNT('12345', '\d{2}') FROM DUAL;
  👉 결과: 2
  * 해설: '12'에서 1번, '34'에서 1번 찾고, 남은 '5'는 제외됩니다.

--------------------------------------------------
2. \d{n,} 패턴 (n개 이상 연속된 숫자 "덩어리" 찾기)
- 패턴: '\d{2,}' (숫자가 연속으로 2개 이상 붙어있는 뭉텅이 세기)

  Example A) SELECT REGEXP_COUNT('12-345-6', '\d{2,}') FROM DUAL;
  👉 결과: 2
  * 해설: '12'(2글자) 합격, '345'(3글자) 합격, '6'(1글자)은 탈락해서 총 2덩어리입니다.

  Example B) SELECT REGEXP_COUNT('123456789', '\d{2,}') FROM DUAL;
  👉 결과: 1
  * 해설: 숫자가 아무리 길어도 중간에 끊기지 않고 쭉 이어져 있으면 하나의 거대한 '1덩어리'로 취급합니다.

--------------------------------------------------
3. 시험 단골! 공백과 글자가 섞인 패턴
- 패턴: '[a-z]' (소문자 개수 세기) 또는 '\s' (공백 개수 세기)

  Example A) SELECT REGEXP_COUNT('abc 123', '[a-z]') FROM DUAL;
  👉 결과: 3
  * 해설: 'a', 'b', 'c' 각각 글자 한 개씩 인식해서 총 3개입니다.

  Example B) SELECT REGEXP_COUNT('apple banana', '\s') FROM DUAL;
  👉 결과: 1
  * 해설: 단어 사이의 '공백(스페이스바)'이 1개 존재하므로 1입니다.

--------------------------------------------------
4. 글자 수(글자 덩어리) 제한 패턴
- 패턴: 'ab{2}' (a 뒤에 b가 정확히 2개 연속하는 패턴 = abb)

  Example A) SELECT REGEXP_COUNT('ab abb abbb', 'ab{2}') FROM DUAL;
  👉 결과: 2
  * 해설: 
    - 'ab' (b가 1개라 탈락)
    - 'abb' (정확히 abb 일치, 1회)
    - 'abbb' (앞의 'abb' 부분만 일치, 1회) -> 총 2회

[문제] 다음 중 실행이 불가능한 SQL을 고르시오.

< TAB1 구조 >
COL1 : NUMBER(4)
COL2 : NUMBER(5,2)
COL3 : VARCHAR2(10)
COL4 : CHAR(10)

1번
INSERT INTO TAB1
VALUES(1000, 1234.5, '100', ' ');
2번
INSERT INTO TAB1
VALUES(1000, 123.456, '2024-01-01', NULL);
3번
INSERT INTO TAB1
VALUES(1000, 123.45, '100', 'ABC');
4번
INSERT INTO TAB1
VALUES(1000, 12.345, 100, 'ABC');

--------------------------------------------------
[정답 및 결과 값]
1번

[핵심 해설]
1. COL2의 데이터 타입은 NUMBER(5,2)입니다. 
   - 전체 자릿수는 최대 5자리이며, 그중 소수점 아래가 2자리를 차지합니다.
   - 따라서 소수점 앞(정수부)은 최대 (5 - 2) = 3자리까지만 입력이 가능합니다.

2. 1번이 불가능한 이유 (에러 발생):
   - COL2 자리에 '1234.5'라는 값을 넣으려고 시도하고 있습니다.
   - 이 값의 정수부는 '1234'로 총 4자리입니다.
   - COL2가 허용하는 정수부 최대 자릿수(3자리)를 초과했기 때문에 '자릿수 초과 에러(수치 오류)'가 발생하여 실행이 불가능합니다.

3. 2번(승원님의 답안)이 정상 실행되는 이유:
   - COL2에 '123.456'을 넣으면 정수부가 3자리('123')라 조건에 만족합니다.
   - 소수점 아래는 2자리까지만 저장되므로, 세 번째 자리인 '6'에서 반올림되어 '123.46'으로 자동 조절되어 정상 저장됩니다.
   - COL3에 날짜 형식의 문자열('2024-01-01')은 10바이트라 VARCHAR2(10)에 딱 맞게 들어갑니다.
   - COL4에 NULL을 넣는 것도 제약조건이 없다면 완전히 가능합니다.

[문제] 다음 중 데이터 타입에 대한 설명으로 옳지 않은 것은?

[지문]
1번 : CHAR(10)은 고정 길이 문자형으로, 입력값이 짧을 경우 자동으로 공백이 채워진다.
2번 : VARCHAR2(20)은 최대 20바이트까지 저장할 수 있는 가변 길이 문자형이다.
3번 : NUMBER(5,2)는 소수점 포함 최대 5자리이며, 정수 3자리와 소수 2자리를 저장할 수 있다.
4번 : DATE 타입은 날짜만 저장 가능하며, 시간 정보는 별도로 저장해야 한다.

--------------------------------------------------
[정답 및 결과 값]
4번

[핵심 해설]
1. 4번이 옳지 않은 이유 (정답):
   - 오라클의 DATE 타입은 '날짜(연, 월, 일)'뿐만 아니라 '시간(시, 분, 초)' 정보까지 **동시에 모두 저장**합니다. 
   - 따라서 "시간 정보는 별도로 저장해야 한다"는 설명은 완전히 틀린 설명입니다.
   - SQL서버가 날짜만 저장함

2. 2번(승원님의 답안)이 올바른 설명인 이유:
   - VARCHAR2는 대표적인 '가변 길이(Variable)' 문자형입니다.
   - 괄호 안의 숫자(20)는 최대 저장 공간을 뜻하므로, "최대 20바이트까지 저장할 수 있는 가변 길이 문자형이다"라는 설명은 정확히 맞는 표현입니다.

3. 다른 보기 요약:

[개념 비교] 오라클 vs SQL Server의 날짜/시간 데이터 타입 차이

--------------------------------------------------
1. Oracle의 방식: "DATE 하나로 퉁치자!"
- DATE: 날짜 + 시간(시분초)을 무조건 동시에 저장함.

--------------------------------------------------
2. SQL Server(MS-SQL)의 방식: "역할에 따라 골라 써라!"
- SQL Server는 과거 오라클처럼 쓰던 타입부터, 날짜와 시간을 칼같이 분리한 타입까지 다양하게 제공합니다.

  ① DATETIME (오라클의 DATE와 가장 유사함)
     - 날짜와 시간(시, 분, 초, 밀리초까지)을 동시에 저장합니다.
     - 단, 오라클 DATE보다 더 정밀하게 소수점 아래 초단위까지 기억합니다.

  ② DATE (진짜 날짜만!) ⭐ 중요
     - SQL Server에서 그냥 'DATE' 타입을 쓰면 오라클과 다릅니다!
     - 오라클과 달리 시간 정보는 완전히 배제하고, 오직 '연-월-일'만 저장합니다.

  ③ TIME (진짜 시간만!)
     - 날짜 정보는 빼고 오직 '시:분:초.밀리초' 정보만 저장합니다.

  ④ DATETIME2 (가장 권장되는 타입)
     - 날짜와 시간을 모두 저장하면서, 소수점 아래 7자리 초단위(나노초 수준)까지 엄청나게 정밀하게 저장합니다.

SELECT region,

정답 : 2번

[최종 출력 결과 테이블 데이터]
REGION | SELLER | AMOUNT | REGION_TOTAL
---------------------------------------
SEOUL  | KIM    | 500    | 800
SEOUL  | LEE    | 300    | 800
BUSAN  | PARK   | 450    | 850
BUSAN  | CHOI   | 200    | 850
BUSAN  | JUNG   | 200    | 850

[핵심 해설]
1. 일반 GROUP BY 절을 사용하면 데이터가 그룹별로 압축되어 행의 수가 줄어듭니다.
2. 하지만 OVER() 키워드를 사용하는 '윈도우 함수(Window Function)'는 원본 테이블의 행을 절대로 줄이지 않고 유지합니다.
3. PARTITION BY region은 지역별(SEOUL, BUSAN)로 묶어서 계산하라는 뜻입니다.
4. 따라서 서울 지역의 합계(500+300=800)와 부산 지역의 합계(450+200+200=850)를 계산한 뒤, 원본 데이터의 모든 행 옆에 그대로 반복해서 출력해 줍니다

###
[개념 정리] 4번 지문 중첩 DECODE 함수 완벽 분석

--------------------------------------------------
1. 기본 DECODE 문법 공식
- DECODE(컬럼, 조건1, 결과1, 조건2, 결과2, ..., 기본값)
- 의미: "컬럼 값이 조건1이면 결과1을 주고, 조건2면 결과2를 주고, 둘 다 아니면 기본값을 줘!"

2. 4번 지문 실제 코드
DECODE(DEPTNO, 10, DECODE(JOB, 'CLERK', 'A', 'B'), 20, 'C', 'D')

3. 한눈에 보는 바깥쪽-안쪽 구조 분해
- 바깥쪽 DECODE: DEPTNO(부서번호)를 검사합니다.
  - 조건이 10일 때 ➡️ [안쪽 DECODE]를 실행해라!
  - 조건이 20일 때 ➡️ 'C'를 줘라!
  - 둘 다 아닐 때 ➡️ 'D'를 줘라! (맨 마지막 값)

- 안쪽 DECODE: JOB(직무)을 검사합니다. (부서번호가 10일 때만 작동)
  - 조건이 'CLERK'일 때 ➡️ 'A'를 줘라!
  - 'CLERK'가 아닐 때 ➡️ 'B'를 줘라! (안쪽 DECODE의 기본값)
