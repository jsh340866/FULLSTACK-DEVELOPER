
## 📝 [오답노트] 데이터베이스 정규화 (정처기 단골 문제)

### 📌 문제
다음 정규형이 적용되었을 때 모든 일반 속성이 주식별자에 종속되어 있는 정규형은?

1. 제1 정규형
2. **제2 정규형 (정답)**
3. 제3 정규형
4. 보이스-코드 정규형 (내 답안)

---

### 🔍 해설 핵심 요약
* **정답이 '제2 정규형'인 이유:** "모든 일반 속성이 주식별자에 종속되어 있다"는 말은 '완전 함수적 종속'을 의미합니다. 주식별자의 일부분에만 종속되는 '부분 함수적 종속'을 제거하여 이 상태를 만드는 단계가 바로 '제2 정규형'입니다.
* **'BCNF'와 헷갈린 이유:** BCNF는 제3 정규형을 만족한 상태에서 "모든 결정자가 후보키이어야 한다"는 조건을 만족해야 합니다. 일반 속성의 완전 종속을 만족하는 최초의 단계는 제2 정규형이므로 문제의 정의와 가장 일치합니다.

---

### 💡 무조건 외우는 정규화 6단계 (도·부·이·결·다·조)

[정규화 단계 - 암기 키워드 - 대상 및 특징]

- 제1 정규형 (1NF) : [도]메인 원자값 / 도메인이 원자값이어야 함
- 제2 정규형 (2NF) : [부]분 함수 / 부분 함수적 종속 제거 (완전 함수 종속)
- 제3 정규형 (3NF) : [이]행적 / 이행적 함수적 종속 제거 (A→B, B→C 제거)
- BCNF             : [결]정자 / 결정자이면서 후보키가 아닌 것 제거
- 제4 정규형 (4NF) : [다]치 종속 / 다치 종속 제거
- 제5 정규형 (5NF) : [조]인 종속 / 조인 종속성 이용

## 📝 [오답노트] 대용량 테이블 설계 전략

### 📌 문제
데이터 구조의 목적을 생각하면, 트랜잭션 처리량이 매우 큰 테이블에 대해 설계 단계에서 우선 검토할 사항으로 옳은 것은?

1. 엔터티명을 길게 변경하는 작업
2. 모든 컬럼을 PK에 포함하는 방법 (내 답안)
3. 접근 패턴에 맞는 인덱스와 파티션 전략 (정답)
4. 모든 제약조건 제거

---

### 🔍 상세 해설
- 정답인 이유 : 트랜잭션(조회, 입력, 수정, 삭제) 처리량이 매우 큰 대용량 테이블은 조금만 조회가 밀려도 시스템 전체가 느려지는 병목 현상이 발생함. 이를 막기 위해 데이터가 어떤 경로로 자주 조회되는지(접근 패턴) 분석하여 빠르게 데이터를 찾아주는 '인덱스'를 설계하고, 거대한 테이블을 연도별이나 월별 등 특정 기준에 따라 작은 단위로 쪼개어 관리하는 '파티션 전략'을 가장 먼저 검토해야 성능을 보장할 수 있음.

- 내 답안이 오답인 이유 : 모든 컬럼을 PK(기본키)에 포함하는 방식은 심각한 성능 저하를 유발함. 데이터가 새로 입력되거나 수정될 때마다 데이터베이스는 모든 컬럼의 값이 중복되지 않았는지 일일이 비교하고 검사하는 대량의 연산 과정을 거쳐야 함. 또한 기본키를 기반으로 만들어지는 기본 인덱스의 크기가 너무 커져서 메모리(RAM) 효율도 극도로 나빠짐. 기본키는 테이블 내의 레코드를 식별할 수 있는 '최소한의 컬럼 조합'으로 구성하는 것이 원칙임.

- 다른 보기가 오답인 이유 :
  * 1번 : 엔터티(테이블)의 이름 길이는 데이터의 처리 성능이나 트랜잭션 속도와 아무런 연관이 없음.
  * 4번 : 제약조건(제한조건)을 모두 제거하면 잘못된 데이터나 중복 데이터가 무작위로 들어와 데이터의 무결성(정확성과 일관성)이 완전히 깨지므로 절대 해서는 안 되는 위험한 방법임.

---

### 💡 대용량 테이블 설계 3대 원칙
- [1] 인덱스 최적화 : 자주 조회되는 조건(WHERE 절)에 맞춰 검색 속도를 높임
- [2] 파티션 활용 : 대용량 데이터를 물리적으로 분할하여 데이터 조회 범위를 줄이고 관리 부하를 감소시킴
- [3] PK 최소화 : 기본키의 크기를 최대한 작고 단순하게 유지하여 메모리와 인덱스 검색 성능의 효율을 높임

## 📝 [개념노트] 계층형 쿼리 정렬 (ORDER SIBLINGS BY)

### 📌 핵심 구문
ORDER SIBLINGS BY [컬럼명] [ASC/DESC]

---

### 🔍 상세 해설
- 개념 : 오라클 계층형 쿼리(CONNECT BY)에서 계층 구조(부모-자식 관계)의 순서를 흐트러뜨리지 않고, 동일한 부모를 가진 '형제 노드(Siblings)'들 사이에서만 정렬을 수행하고 싶을 때 사용하는 구문임.

- 일반 ORDER BY와의 차이점 :
  * 일반 ORDER BY : 계층 구조를 완전히 무시하고 지정한 컬럼 기준으로 전체 데이터를 정렬해 버리기 때문에 트리 형태의 구조가 깨짐.
  * ORDER SIBLINGS BY : 대분류-중분류-소분류 같은 계층적 흐름을 그대로 유지한 상태에서, 대분류 안의 중분류끼리 혹은 중분류 안의 소분류끼리만 가나다순/순서순 정렬을 수행함.

---

### 💡 예시 쿼리문
SELECT 부서코드, 부서명, 상위부서코드, LEVEL
FROM 부서테이블
START WITH 상위부서코드 IS NULL
CONNECT BY PRIOR 부서코드 = 상위부서코드
ORDER SIBLINGS BY 부서명 ASC; 
-- 계층 구조를 유지하면서 동일한 상위 부서를 둔 부서들끼리만 부서명 사전순 정렬
