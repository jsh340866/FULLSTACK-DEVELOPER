
## 📝 [오답노트] 데이터베이스 정규화 (정처기 단골 문제)

### 📌 문제
다음 정규형이 적용되었을 때 모든 일반 속성이 주식별자에 종속되어 있는 정규형은?

1. 제1 정규형
2. **제2 정규형 (정답)**
3. 제3 정규형
4. 보이스-코드 정규형 (내 답안)

---

### 🔍 해설 핵심 요약
* **정답이 '제2 정규형'인 이유:** "모든 일반 속성이 주식별자에 종속되어 있다"는 말은 '완전 함수적 종속'을 의미합니다. 주식별자의 일부분에만 종속되는 '부분 함수적 종속'을 제거하여 이 상태를 만드는 단계가 바로 '제2 정규형'입니다.
* **'BCNF'와 헷갈린 이유:** BCNF는 제3 정규형을 만족한 상태에서 "모든 결정자가 후보키이어야 한다"는 조건을 만족해야 합니다. 일반 속성의 완전 종속을 만족하는 최초의 단계는 제2 정규형이므로 문제의 정의와 가장 일치합니다.

---

### 💡 무조건 외우는 정규화 6단계 (도·부·이·결·다·조)

[정규화 단계 - 암기 키워드 - 대상 및 특징]

- 제1 정규형 (1NF) : [도]메인 원자값 / 도메인이 원자값이어야 함
- 제2 정규형 (2NF) : [부]분 함수 / 부분 함수적 종속 제거 (완전 함수 종속)
- 제3 정규형 (3NF) : [이]행적 / 이행적 함수적 종속 제거 (A→B, B→C 제거)
- BCNF             : [결]정자 / 결정자이면서 후보키가 아닌 것 제거
- 제4 정규형 (4NF) : [다]치 종속 / 다치 종속 제거
- 제5 정규형 (5NF) : [조]인 종속 / 조인 종속성 이용

=============================================================================

## 📝 [오답노트] 대용량 테이블 설계 전략

### 📌 문제
데이터 구조의 목적을 생각하면, 트랜잭션 처리량이 매우 큰 테이블에 대해 설계 단계에서 우선 검토할 사항으로 옳은 것은?

1. 엔터티명을 길게 변경하는 작업
2. 모든 컬럼을 PK에 포함하는 방법 (내 답안)
3. 접근 패턴에 맞는 인덱스와 파티션 전략 (정답)
4. 모든 제약조건 제거

---

### 🔍 상세 해설
- 정답인 이유 : 트랜잭션(조회, 입력, 수정, 삭제) 처리량이 매우 큰 대용량 테이블은 조금만 조회가 밀려도 시스템 전체가 느려지는 병목 현상이 발생함. 이를 막기 위해 데이터가 어떤 경로로 자주 조회되는지(접근 패턴) 분석하여 빠르게 데이터를 찾아주는 '인덱스'를 설계하고, 거대한 테이블을 연도별이나 월별 등 특정 기준에 따라 작은 단위로 쪼개어 관리하는 '파티션 전략'을 가장 먼저 검토해야 성능을 보장할 수 있음.

- 내 답안이 오답인 이유 : 모든 컬럼을 PK(기본키)에 포함하는 방식은 심각한 성능 저하를 유발함. 데이터가 새로 입력되거나 수정될 때마다 데이터베이스는 모든 컬럼의 값이 중복되지 않았는지 일일이 비교하고 검사하는 대량의 연산 과정을 거쳐야 함. 또한 기본키를 기반으로 만들어지는 기본 인덱스의 크기가 너무 커져서 메모리(RAM) 효율도 극도로 나빠짐. 기본키는 테이블 내의 레코드를 식별할 수 있는 '최소한의 컬럼 조합'으로 구성하는 것이 원칙임.

- 다른 보기가 오답인 이유 :
  * 1번 : 엔터티(테이블)의 이름 길이는 데이터의 처리 성능이나 트랜잭션 속도와 아무런 연관이 없음.
  * 4번 : 제약조건(제한조건)을 모두 제거하면 잘못된 데이터나 중복 데이터가 무작위로 들어와 데이터의 무결성(정확성과 일관성)이 완전히 깨지므로 절대 해서는 안 되는 위험한 방법임.

---

### 💡 대용량 테이블 설계 3대 원칙
- [1] 인덱스 최적화 : 자주 조회되는 조건(WHERE 절)에 맞춰 검색 속도를 높임
- [2] 파티션 활용 : 대용량 데이터를 물리적으로 분할하여 데이터 조회 범위를 줄이고 관리 부하를 감소시킴
- [3] PK 최소화 : 기본키의 크기를 최대한 작고 단순하게 유지하여 메모리와 인덱스 검색 성능의 효율을 높임

## 📝 [개념노트] 계층형 쿼리 정렬 (ORDER SIBLINGS BY)

### 📌 핵심 구문
ORDER SIBLINGS BY [컬럼명] [ASC/DESC]

---

### 🔍 상세 해설
- 개념 : 오라클 계층형 쿼리(CONNECT BY)에서 계층 구조(부모-자식 관계)의 순서를 흐트러뜨리지 않고, 동일한 부모를 가진 '형제 노드(Siblings)'들 사이에서만 정렬을 수행하고 싶을 때 사용하는 구문임.

- 일반 ORDER BY와의 차이점 :
  * 일반 ORDER BY : 계층 구조를 완전히 무시하고 지정한 컬럼 기준으로 전체 데이터를 정렬해 버리기 때문에 트리 형태의 구조가 깨짐.
  * ORDER SIBLINGS BY : 대분류-중분류-소분류 같은 계층적 흐름을 그대로 유지한 상태에서, 대분류 안의 중분류끼리 혹은 중분류 안의 소분류끼리만 가나다순/순서순 정렬을 수행함.

---

### 💡 예시 쿼리문
SELECT 부서코드, 부서명, 상위부서코드, LEVEL
FROM 부서테이블
START WITH 상위부서코드 IS NULL
CONNECT BY PRIOR 부서코드 = 상위부서코드
ORDER SIBLINGS BY 부서명 ASC; 
-- 계층 구조를 유지하면서 동일한 상위 부서를 둔 부서들끼리만 부서명 사전순 정렬

=============================================================================

## 📝 [오답노트] 서브쿼리 연산자 에러 유형 (복수 정답 반영)

### 📌 문제
주어진 ERD를 참조하여 SQL을 수행하였을 때, 문법적 또는 논리적 오류가 발생하여 실행되지 않거나 에러(Error)가 날 수 있는 SQL문은? (정답: 1번, 2번, 4번)

1. SELECT 회원번호, 종목코드 FROM 일자별주문내역 WHERE 주문일자 ALL (SELECT DISTINCT 주문일자 FROM 계좌마스터);
2. SELECT 회원번호, 종목코드 FROM 일자별주문내역 WHERE 주문일자 EXISTS (SELECT DISTINCT 주문일자 FROM 계좌마스터);
3. SELECT * FROM 계좌마스터 WHERE 회원번호 IN (SELECT DISTINCT 회원번호 FROM 고객);
4. SELECT * FROM 계좌마스터 WHERE 회원번호 = (SELECT DISTINCT 회원번호 FROM 고객);

---

### 🔍 상세 해설

- 1번이 에러인 이유 (구문 오류) :
  * ALL 연산자는 단독으로 사용할 수 없고, 반드시 비교 연산자(=, >, <, >=, <=)와 함께 사용해야 함 (예: WHERE 주문일자 = ALL (...)). 
  * 비교 연산자 없이 '주문일자 ALL'이라고만 적었기 때문에 명백한 SQL 구문 에러(Syntax Error)가 발생함.

- 2번이 에러인 이유 (구문 오류) :
  * EXISTS 연산자는 서브쿼리의 결과가 존재하는지만 확인하는 연산자이므로, 앞에 컬럼명(주문일자)을 붙이지 않고 'WHERE EXISTS (...)' 형태로 사용해야 함.
  * 컬럼명 뒤에 EXISTS를 붙였기 때문에 이 역시 잘못된 문법으로 구문 에러가 발생함.

- 4번이 에러인 이유 (런타임 오류) :
  * 등호(=)는 오직 하나의 값만 비교하는 '단일 행 연산자'임. 하지만 서브쿼리(고객 테이블의 회원번호 조회)의 결과는 여러 개의 행(다중 행)을 반환함.
  * 단일 행 연산자 뒤에 여러 행이 들어오기 때문에 "단일 행 하위 질의에 2개 이상의 행이 반환되었습니다"라는 치명적인 에러가 발생함.
  * 등호(=)를 in으로 바꾸면 해결

- 3번만 정상 작동하는 이유 :
  * IN은 서브쿼리에서 반환된 여러 개의 값 중 하나라도 일치하는 게 있는지 검사하는 올바른 '다중 행 연산자'이며, 문법과 구조 모두 완벽하여 정상 실행됨.
  

---

### 💡 핵심 요약 키워드
- ALL / ANY : 반드시 앞에 비교 연산자(=, >, < 등)를 동반해야 함
- EXISTS : 앞에 컬럼명을 쓰지 않고 'WHERE EXISTS (서브쿼리)' 형태로만 사용함
- 단일 행 연산자(=) : 서브쿼리의 결과 행이 무조건 딱 1개여야 에러가 안 남

=============================================================================

## 📝 [오답노트] LEFT OUTER JOIN 결과 건수 계산

### 📌 문제
주어진 두 테이블(TAB1, TAB2)에 대해 아래 SQL을 수행한 결과 건수(CNT)로 가장 적절한 것은?

[문제 이미지 데이터 텍스트화]
<TAB1>
COL1 | COL2
  1  |  A
  2  |  B
  3  |  C
  4  |  D

<TAB2>
COL1 | COL2
  1  |  A
  2  |  B
  2  |  B
  4  |  C
  5  |  C

[SQL]
SELECT COUNT(TAB1.COL1) AS CNT
FROM TAB1 LEFT OUTER JOIN TAB2
  ON TAB1.COL2 = TAB2.COL2
 AND TAB1.COL1 = TAB2.COL1;

1. 6
2. 5 (정답)
3. 4 (내 답안)
4. 3

---

### 🔍 상세 해설

- 조인 조건 분석 :
  * 조건은 두 테이블의 'COL1과 COL2가 모두 일치'해야 함. 즉, 두 컬럼의 조합이 완전히 같은 행을 찾는 매칭 작업임.

- TAB1 기준으로 TAB2와 매칭 진행 과정 :
  * [TAB1의 1번째 행] (1, A) 
    -> TAB2에서 (1, A)를 찾음 (1개 존재). 
    -> 결과 행 생성: [1, A, 1, A] (1건)

  * [TAB1의 2번째 행] (2, B) 
    -> TAB2에서 (2, B)를 찾음 (주의: TAB2에 동일한 (2, B)가 2행 존재함). 
    -> TAB1의 한 행이 TAB2의 두 행과 각각 조인되므로 결과가 2개로 불어남.
    -> 결과 행 생성: [2, B, 2, B] / [2, B, 2, B] (2건)

  * [TAB1의 3번째 행] (3, C) 
    -> TAB2에서 (3, C)를 찾음 (존재하지 않음. TAB2에는 (4, C), (5, C)만 있음).
    -> 하지만 'LEFT' OUTER JOIN이므로 오른쪽(TAB2)에 매칭되는 데이터가 없어도 왼쪽(TAB1) 데이터는 무조건 살아남고 오른쪽은 NULL로 채워짐.
    -> 결과 행 생성: [3, C, NULL, NULL] (1건)

  * [TAB1의 4번째 행] (4, D) 
    -> TAB2에서 (4, D)를 찾음 (존재하지 않음).
    -> 마찬가지로 LEFT JOIN이므로 매칭 실패해도 살아남음.
    -> 결과 행 생성: [4, D, NULL, NULL] (1건)

- 최종 결과 도출 :
  * 최종적으로 조인 완료된 결과 테이블의 전체 행 수는 (1 + 2 + 1 + 1) = 총 5행임.
  * 문제에서 구하는 값은 COUNT(TAB1.COL1)이며, 생성된 5개의 모든 행에서 TAB1.COL1의 값은 [1, 2, 2, 3, 4]로 NULL이 아니기 때문에 정상적으로 5를 반환함.

---

### 💡 핵심 요약 키워드
- 1:N 조인의 데이터 증폭 : 조인 대상 테이블(오른쪽)에 조건이 일치하는 행이 여러 개 존재하면, 결과 행의 개수는 그 개수만큼 늘어남 (TAB1의 (2, B)가 2건으로 복사된 이유).
- LEFT OUTER JOIN의 특성 : 매칭되는 조건이 우측 테이블에 없더라도, 좌측 테이블의 행은 탈락하지 않고 NULL과 결합하여 반드시 결과에 포함됨.

=============================================================================

## 📝 [오답노트] 셀프 조인(Self Join)과 아우터 조인(Outer Join) 활용

### 📌 문제
다음 출력 결과를 얻기 위한 SQL 문장으로 가장 적절한 것은?

[문제 이미지 데이터 텍스트화]
<EMP>
EMPNO | ENAME   | MGR  | DEPTNO
7369  | SMITH   | 7566 | 20
7499  | ALLEN   | 7654 | 30
7521  | WARD    | 7566 | 30
7566  | JONES   | 7654 | 20
7654  | MARTIN  |      | 30

<결과>
EMPNO | ENAME   | MANAGER_NAME
7369  | SMITH   | JONES
7499  | ALLEN   | MARTIN
7521  | WARD    | JONES
7566  | JONES   | MARTIN
7654  | MARTIN  | 

[SQL]
1. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.EMPNO = E2.MGR(+) ORDER BY E1.EMPNO; (내 답안)
2. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.EMPNO = E2.MGR ORDER BY E1.EMPNO;
3. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.MGR = E2.EMPNO(+) ORDER BY E1.EMPNO; (정답)
4. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.MGR = E2.EMPNO ORDER BY E1.EMPNO;

---

### 🔍 상세 해설

- **조인 조건 분석** : 
  * 사원 테이블(E1)의 관리자 사원번호(`MGR`)를 통해 관리자 테이블(E2)의 사원번호(`EMPNO`)를 찾아 이름(`ENAME`)을 매칭하는 셀프 조인 문제임.
  * 결과 테이블에서 매니저가 없는 'MARTIN' 사원도 누락되지 않고 출력되었으므로 `LEFT OUTER JOIN`이 필요함.

- **풀이/매칭 진행 과정** : 
  * Oracle 문법에서 Outer Join 기호인 `(+)`는 데이터가 존재하지 않아 NULL로 채워져야 하는 쪽에 붙임. 매니저 정보가 없는 사원도 살려야 하므로 `E2` 테이블 컬럼에 `(+)`를 붙여야 함.
  * [7369, SMITH] (MGR: 7566) -> E2에서 EMPNO 7566인 JONES 매칭 성공.
  * [7654, MARTIN] (MGR: NULL) -> E2에서 매칭되는 EMPNO 없음. 단, `E2.EMPNO(+)` 조건에 의해 탈락하지 않고 우측 데이터는 NULL 처리되어 정상 출력됨.

- **최종 결과 도출** : 
  * 사원의 관리자 번호로 관리자의 사원번호를 조인해야 하므로 기본 조건은 `E1.MGR = E2.EMPNO`가 됨.
  * 여기에 매니저가 없는 사원까지 누락 없이 표현하기 위해 오른쪽 테이블 컬럼 뒤에 `(+)`를 붙인 **3번**이 최종 정답임.

---

### 💡 핵심 요약 키워드
- **셀프 조인의 방향성** : 사원-관리자 관계 조인 시 기준점은 `사원.MGR = 관리자.EMPNO`가 됨.
- **오라클 Outer Join 기호 `(+)`** : LEFT OUTER JOIN 구현 시, 우측 테이블(NULL로 채워질 대상) 컬럼 뒤에 `(+)`를 추가함.

## 📝 [오답노트] GROUP BY ROLLUP과 메인 쿼리 COUNT(*) 계산

### 📌 문제
다음의 SQL문 실행 결과로 조회되는 행의 개수는?

[문제 이미지 데이터 텍스트화]
<Mytest>
DATA1 | DATA2
  A   | 1000
  B   | 2000
  C   | 3000
  C   | 4000

[SQL]
SELECT COUNT(*)
FROM(
    SELECT COUNT(*)
    FROM Mytest
    GROUP BY ROLLUP(DATA1), DATA2
);

1. 8 (정답)
2. 6
3. 4 (내 답안)
4. 3

---

### 🔍 상세 해설

- **조인 조건 및 문법 분석** : 
  * 인라인 뷰(서브쿼리) 내부의 `GROUP BY ROLLUP(DATA1), DATA2` 구조를 정확히 파악해야 함.
  * `ROLLUP`은 나열된 컬럼에 대해 우측에서부터 하나씩 제거하며 소계를 구하는 함수임.
  * 주의할 점은 `DATA2`는 `ROLLUP` 괄호 밖에 있으므로, **`DATA2`별 그룹화는 무조건 유지**된 채로 `DATA1`의 `ROLLUP` 소계가 추가되는 형태임.

- **풀이/매칭 진행 과정** : 
  * `GROUP BY ROLLUP(DATA1), DATA2`에 의해 생성되는 그룹화 기준 조합은 다음과 같음:
    1) **`GROUP BY DATA1, DATA2`** (기본 조합 전체)
    2) **`GROUP BY DATA2`** (`ROLLUP` 괄호 내부의 `DATA1`이 찌그러지며 `NULL` 처리된 전체 소계)

  * 위의 두 가지 기준에 따라 생성되는 결과 행들을 하나씩 나열하면 다음과 같음:
    
    **1) (DATA1, DATA2) 기본 그룹화 행 (총 4개 행 생성)**
    * (A, 1000) -> 1건
    * (B, 2000) -> 1건
    * (C, 3000) -> 1건
    * (C, 4000) -> 1건

    **2) (NULL, DATA2) 소계 그룹화 행 (총 4개 행 생성)**
    * (NULL, 1000) -> 1건
    * (NULL, 2000) -> 1건
    * (NULL, 3000) -> 1건
    * (NULL, 4000) -> 1건

  * 따라서 서브쿼리가 최종적으로 반환하는 총 행의 개수는 `4 + 4 = 8행`이 됨.

- **최종 결과 도출** : 
  * 메인 쿼리인 `SELECT COUNT(*)`는 서브쿼리가 반환한 결과 집합의 **전체 행 개수**를 세는 것임.
  * 서브쿼리에서 총 8개의 행이 조회되었으므로, 이를 카운트한 최종 결과는 **8**이 되어 **1번**이 정답임.

---

### 💡 핵심 요약 키워드
- **ROLLUP의 소계 생성 기준** : `GROUP BY ROLLUP(A), B` 형태로 작성하면, 괄호 밖의 `B`는 고정된 상태에서 `(A, B)` 그룹과 `(NULL, B)` 소계 그룹이 각각 생성됨.

## 📝 [오답노트] ERD 관계 분석과 컬럼 순서에 따른 INSERT 오류

### 📌 문제
다음의 주어진 ERD에서 실행했을 때 오류가 발생하는 SQL문은?

[문제 이미지 데이터 텍스트화]
<고객>
고객ID (PK)
-----------
고객명
주문ID (FK)

<주문>
주문ID (PK)
-----------
상품
고객ID (FK)

+ PRIMARY KEY : 고객(고객ID)
+ 주문(고객ID) REFERENCES 고객(고객ID)

1. INSERT INTO 주문 VALUES ('O002', 'C002', 'YYY');
2. UPDATE 주문 SET 고객ID = NULL WHERE 주문ID = 'O001'; (내 답안)
3. INSERT INTO 주문 VALUES ('O001', 'C001', 'XXX');
4. INSERT INTO 고객 VALUES ('C001', 'AAA'); (정답)

---

### 🔍 상세 해설

- **조건 및 테이블 구조 분석** : 
  * 테이블에 데이터를 넣을 때 컬럼명을 명시하지 않으면(`INSERT INTO 테이블명 VALUES (...)`), 테이블이 정의된 **실제 컬럼 순서대로** 데이터가 들어가야 함.
  * ERD에 표시된 속성(Column)의 순서는 다음과 같음:
    * **고객 테이블**: `고객ID`, `고객명`, `주문ID` (총 3개 컬럼)
    * **주문 테이블**: `주문ID`, `상품`, `고객ID` (총 3개 컬럼)

- **풀이/매칭 진행 과정** : 
  * **4번 보기 분석 (정답인 이유)**:
    * `INSERT INTO 고객 VALUES ('C001', 'AAA');` 구문은 데이터를 **2개**만 집어넣고 있음.
    * 하지만 고객 테이블은 `고객ID`, `고객명`, `주문ID`까지 총 **3개의 컬럼**으로 구성되어 있음.
    * 컬럼 리스트를 생략한 채 2개의 값만 넣으려고 시도하면 **"값의 수가 충분하지 않습니다 (ORA-00947)"** 에러가 발생하며 SQL문이 실패하게 됨.
  
  * **1, 3번 보기 분석**:
    * 주문 테이블의 컬럼 순서인 (`주문ID`, `상품`, `고객ID`)에 맞춰 각각 3개의 값('O002', 'C002', 'YYY' 등)을 정상적으로 매칭하여 삽입하고 있으므로 문법적 오류가 없음. (참고: 참조 무결성 제약조건에 의해 외래키인 고객ID에 없는 값이 들어가면 에러가 나지만, 4번은 순수한 SQL 구조적 개수 부족으로 무조건 에러가 남)

  * **2번 보기 분석**:
    * 외래키(`FK`) 제약조건이 걸려있더라도, 기본적으로 외래키 컬럼에는 `NULL` 값을 허용하므로 `UPDATE` 구문 자체는 정상적으로 수행될 수 있음.

- **최종 결과 도출** : 
  * 외래키나 참조 무결성 함정에 빠지기 쉽지만, 테이블 구조에 정의된 컬럼의 개수와 `VALUES`에 전달된 데이터의 개수가 일치하지 않는 **4번**이 명백한 구조적 오류를 발생시키므로 최종 정답임.

---

### 💡 핵심 요약 키워드
- **INSERT 명시적/암묵적 컬럼 매칭** : `INSERT INTO 테이블명 VALUES (...)` 구조를 사용할 때는 테이블에 정의된 전체 컬럼 개수 및 순서와 반드시 일치해야 함. 값이 부족하면 구조적 오류 발생.
- **ERD 컬럼 순서 확인** : 텍스트 데이터의 선 위(PK)와 선 아래(일반 속성)를 차례대로 합쳐 전체 컬럼 리스트를 파악하는 습관이 중요함.

⚠️ 한눈에 보는 핵심 요약 규칙
- JOIN ➡️ INNER JOIN (교집합, 매칭 안 되면 탈락!)
- LEFT JOIN ➡️ LEFT OUTER JOIN (왼쪽 기준, 매칭 안 돼도 NULL로 생존!)
- RIGHT JOIN ➡️ RIGHT OUTER JOIN (오른쪽 기준, 매칭 안 돼도 NULL로 생존!)
