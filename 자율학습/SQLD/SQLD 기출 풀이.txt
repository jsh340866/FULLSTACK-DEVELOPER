

오라클 데이터베이스에서 내일 날짜를 조회하는 방법으로 올바른 것은?
답안과 정답

1번
SELECT TO_CHAR(SYSDATE-1, 'YYYYMMDD')
FROM DUAL;
2번
내 답안
SELECT TO_DATE(SYSDATE-1, 'YYYYMMDD')
FROM DUAL;
3번
정답
SELECT TO_CHAR(SYSDATE+1, 'YYYYMMDD')
FROM DUAL;
4번
SELECT TO_DATE(SYSDATE+1, 'YYYYMMDD')
FROM DUAL;

###
정답 : 3번
💡 왜 3번이 정답일까요?
오라클에서 "내일 날짜"를 구하려면 현재 날짜와 시간을 의미하는 SYSDATE에 +1을 해주어야 해요!

SYSDATE : 오늘 날짜
SYSDATE - 1 : 어제 날짜 (1일을 뺌)
SYSDATE + 1 : 내일 날짜 (1일을 더함) 🌟
따라서 '내일'을 구하는 연산은 +1이 들어간 3번과 4번 중에 나와야 해요.

❌ 2번 답안이 오답인 이유와 TO_CHAR vs TO_DATE 차이점
승원님께서 고르신 2번은 '날짜 계산 방향(-1)'과 '형변환 함수 선택' 두 가지 이유 때문에 오답이 되었어요.
① 날짜 계산 방향 오류 (-1)
SYSDATE - 1을 하게 되면 내일이 아니라 어제 날짜가 나오게 된답니다.

② 함수 선택 오류 (TO_DATE 사용)
SYSDATE + 1의 결과는 이미 날짜(DATE) 데이터 타입이에요.
- TO_CHAR(날짜, '포맷'): 날짜 데이터를 문자로 예쁘게 출력할 때 사용해요. (3번이 정답인 이유!)
- TO_DATE(문자, '포맷'): '20260518' 같은 문자열을 날짜 데이터로 바꿀 때 사용해요. 날짜 타입인 SYSDATE를 첫 번째 인자로 넣으면 오라클이 내부적으로 문자로 바꿨다 다시 날짜로 바꾸는 과정에서 에러(오류)가 발생하거나 엉뚱한 값이 나올 수 있어요.

다음 SQL문 중에서 결괏값이 다른 하나는?
답안과 정답

1번
SELECT CONCAT('0', '5')
FROM DUAL
2번
SELECT TRIM('05')
FROM DUAL
3번
정답
SELECT EXTRACT(MONTH
FROM DATE '2022 - 05 - 01')
FROM DUAL;
4번
내 답안
SELECT SUBSTR(TO_CHAR ('20220504'), 5,2)
FROM DUAL

###
정답 : 3번

💡 핵심 요약: 왜 3번만 결괏값이 다를까요?
이 문제의 핵심은 "문자열 '05'인가, 아니면 숫자 5인가!"의 차이예요.
1번, 2번, 4번의 결과: 모두 '05' (앞에 0이 붙은 문자열)

3번(정답)의 결과: 5 (앞에 0이 없는 숫자)

3번 (정답): SELECT EXTRACT(MONTH FROM DATE '2022-05-01') FROM DUAL;
해설: EXTRACT(MONTH FROM ...) 함수는 날짜 데이터에서 '월' 정보를 숫자형(NUMBER)으로 추출해 주는 함수예요.

결과: 2022년 5월 1일에서 월을 추출하면 문자가 아니라 순수한 숫자 5가 돼요! 오라클에서 숫자는 앞에 0을 붙여서 05로 표현하지 않고 그냥 5로 출력하기 때문에, 이 보기만 결괏값이 다릅니다. 🌟

+--------+------+---------+

###
정답 : 2번(2)

🗺️ [1단계] "어디서부터 출발할까?" ➔ START WITH
SQL
- START WITH EMPNO = 3
	- 해석: "자, 탐색 대장! 이 회사 족보에서 EMPNO가 3번인 직원(KIM)을 찾아서 거기서부터 조사를 시작해!"
	- 컴퓨터의 상태: 3번 KIM을 첫 번째 데이터로 찜합니다. (이때 컴퓨터 내부적으로 LEVEL = 1이 부여돼요!)

🧗‍♂️ [2단계] "어느 방향으로 올라갈까?" ➔ CONNECT BY
SQL
- CONNECT BY EMPNO = PRIOR MANAGER
	- 해석: "그다음 데이터들은 어떻게 찾냐고? 지금 내 위치(EMPNO)의 직속 상사(PRIOR MANAGER) 번호를 확인해서, 그 번호를 가진 사람을 다음 데이터로 연결해!"
	- 컴퓨터의 상태: *  3번 KIM의 상사(MANAGER)가 2번이네? ➔ 2번 PARK을 찾아감 (LEVEL = 2)
			2번 PARK의 상사(MANAGER)가 1번이네? ➔ 1번 LIM을 찾아감 (LEVEL = 3)
			1번 LIM의 상사는 NULL(없음)이네? ➔ 탐색 종료!
			현재까지 모은 후보군: 3번 KIM, 2번 PARK, 1번 LIM (총 3건)

🎨 [3단계] "화면에 어떻게 예쁘게 보여줄까?" ➔ SELECT
SQL
- SELECT LPAD('**', (LEVEL-1)*2, ' ') || EMPNO AS EMP, NAME
	- 해석: "화면에 출력할 때, 그냥 숫자만 띡 보여주면 직급(레벨) 구분이 안 가잖아? 그러니까 (LEVEL-1)*2만큼 스페이스바(공백)를 채우고 그 뒤에 별()을 붙인 다음, 사원번호(EMPNO)를 본드로 찰떡같이 이어 붙여서(||) 출력해 줘! 컬럼 이름은 EMP라고 하고, 옆에 이름(NAME)도 같이 띄워주고!"
	- 컴퓨터의 상태: 머릿속으로 출력 모양을 계산합니다.
		- LEVEL 1 (3번 KIM) ➔ 공백 0칸 ➔ 3
		- LEVEL 2 (2번 PARK) ➔ 공백 0칸 + 별 2개 ➔ 2
		- LEVEL 3 (1번 LIM) ➔ 공백 2칸 + 별 2개 ➔   1

🛑 [4단계] "마지막으로 거를 사람은?" ➔ WHERE (최종 필터링)
SQL
- WHERE EMPNO <> 3
	- 해석: "아, 맞다! 다 찾아놓은 결과창에서 EMPNO가 3번인 데이터는 눈에 안 보이게 쏙 빼고 나머지만 최종 화면에 띄워라!"
	- 컴퓨터의 상태: 열심히 만든 결과물에서 3번 KIM 줄을 슥 지워버립니다.

###
정답 : 2번( ORA- )

🔍 핵심 부품 2개 뜯어보기
이 문제의 비밀은 [^0-9]+ 기호의 조합에 숨겨져 있어요.

- 부품 ① [^0-9] ➔ 대괄호 안의 캐럿(^)은 "부정(NOT)"
	- 만약 그냥 [0-9]라고 쓰면 숫자를 찾으라는 뜻이지만, 대괄호 안에 ^가 들어가면 "숫자가 아닌 것(문자, 공백, 특수문자 등)"을 찾으라는 뜻이 돼요!
	- 💡 승원 님이 4번(50)을 고르신 이유는 아마 이 ^ 기호를 문장의 시작점이나 숫자 매칭으로 오해하셨기 때문일 거예요.

- 부품 ② + ➔ 1개 이상 연속됨
	- "숫자가 아닌 글자들이 끊기지 않고 연속으로 쭉 이어져 있는 덩어리"를 통째로 가져오라는 뜻이에요.

🕵️‍♂️ 컴퓨터가 글자를 읽어 내려가는 과정
컴퓨터는 'ORA-00600 Oracle SQL-Server 50' 문장을 왼쪽 맨 첫 글자부터 한 글자씩 검사하기 시작해요.
- 'O' : 숫자가 아니네? (합격! 킵해둠) ➔ O
- 'R' : 숫자가 아니네? (합격! 연속됨) ➔ OR
- 'A' : 숫자가 아니네? (합격! 연속됨) ➔ ORA
- '-' : 숫자가 아니네? 특수문자도 합격! ➔ ORA-
- '0' : 앗! 숫자 등장!! 🛑

여기서 중요해요! REGEXP_SUBSTR 함수는 조건을 만족하는 "첫 번째 덩어리"를 만나는 순간, 뒤는 더 쳐다보지도 않고 그 자리에서 칼퇴근(종료)을 해버려요.

숫자인 0을 만나는 순간 "숫자가 아닌 연속된 덩어리"가 끊겨버렸기 때문에, 컴퓨터는 지금까지 모아둔 ORA-만 손에 쥐고 낼름 출력해 버리는 거랍니다.

🗺️ 정렬 기준 4대장 분석하기

- [3순위] amount ASC (금액 오름차순: 작은 순서 ➔ 큰 순서)
- [4순위] region ASC (지역 오름차순: 알파벳/가나다 순서)

🏃‍♂️ 컴퓨터의 1차 필터링: 100점을 기준으로 반 나누기 (1순위 적용)
우선 테이블의 4개 데이터를 금액이 100 이상인지 아닌지로 크게 두 동강을 냅니다.
- 그룹 1 (우선 출력): SEOUL(150), BUSAN(100), SEOUL(100)
- 그룹 2 (나중 출력): INCHEON(80)
💡 여기서 이미 정답 발견! > 금액이 100 미만이라 그룹 2로 밀려난 녀석은 INCHEON, B, 80 딱 하나밖에 없어요! 그룹 2는 그룹 1보다 무조건 뒤에 출력되므로, 뒤쪽 정렬 기준들을 더 계산해 볼 필요도 없이 **INCHEON이 무조건 꼴등(마지막 행)**이 됩니다!

문제

이래는 어느 회사의 정산 데이터 모델의 일부이며 고객이 서비스를 사용한 시간대에 따라 차등 단가를 적용하려고 한다. 다음 중 시간대별사용량 테아블을 기반으로 고객별 사용금액을 추출하는 SQL으로 가장 적절한 것은?
j93-1
답안과 정답

1번
내 답안
SELECT A.고객ID, A.고객명, SUM(B.사용량 * C.단가) AS 사용금액
FROM 고객 A
INNER
JOIN 시간대별사용량 B
ON (A. 고객ID = B.고객ID) BETWEEN
JOIN 시간대구간 C
GROUP BY A.고객ID, A.고객명
ORDER BY A.고객ID, A.고객명;
2번
정답
SELECT A.고객ID, A.고객명, SUM(B.사용량 * C.단가) AS 사용금액
FROM 고객 A
INNER
JOIN 시간대별사용량 B
ON (A.고객ID = B.고객ID)
INNER
JOIN 시간대구간 C
ON B.사용시간대 BETWEEN C.시작시간대
AND C.종료시간대
GROUP BY A.고객ID, A.고객명
ORDER BY A.고객ID, A.고객명;
3번
SELECT A.고객ID, A.고객명, SUM(B.사용량 * C.단가) AS 사용금액

### 
정답 : 2번

🕵️‍♂️ 정답인 2번 코드가 완벽한 이유 분석
2번의 FROM 절과 JOIN 절을 컴퓨터의 시선으로 한 줄씩 뜯어볼게요.

① 1단계: 고객(A) 테이블과 시간대별사용량(B) 테이블을 먼저 연결!
SQL
FROM 고객 A
INNER JOIN 시간대별사용량 B ON (A.고객ID = B.고객ID)
해석: "고객ID가 똑같은 것끼리 매칭해서 두 테이블을 1차로 찰떡같이 붙여라!"

결과: 고객 이름과 그 고객이 몇 시에(사용시간대) 얼마나(사용량) 썼는지 정보가 합쳐져요.

② 2단계: 합쳐진 결과에다가 시간대구간(C) 테이블을 마저 연결!
SQL
INNER JOIN 시간대구간 C ON B.사용시간대 BETWEEN C.시작시간대 AND C.종료시간대
해석: "자, 1차로 합친 결과에 있는 사용시간대가, 시간대구간 테이블의 시작시간대와 종료시간대 사이(BETWEEN AND)에 쏙 들어가는지 확인해서 단가(C.단가) 정보를 옆에 마저 붙여라!"

결과: 드디어 고객명, 사용량, 단가가 한 줄에 다 모이게 됩니다!

❌ 승원 님이 고르신 1번과 다른 보기들이 오답인 이유
- 1번 (내 답안): SQL에는 BETWEEN JOIN이라는 문법이 아예 없어요! INNER JOIN을 쓰고 나서 ON 조건 절 안에 BETWEEN을 써야 정당한 문법이 됩니다.
- 3번: FROM 고객 A INNER JOIN 시간대별사용량 B INNER JOIN 시간대구간 C 처럼 조인을 연속으로 두 번 쓰고 ON을 맨 뒤에 몰아서 쓰면, 컴퓨터는 첫 번째 조인을 할 때 "기준이 뭔데?!" 하고 에러를 내뿜어요.
- 4번: B.사용시간대 <= C.시작시간대 AND B.사용시간대 >= C.종료시간대 부분의 부등호 방향이 완전 거꾸로 되었어요! 만약 14시면 시작(12시)보다는 크거나 같고(>=), 종료(18시)보다는 작거나 같아야(<=) 범위 안에 들어가겠죠? 부등호 낚시였답니다.

###
정답 : 2번 (NULLIF)

🏃‍♂️ 1번, 3번, 4번 함수 분석: "NULL이면 100으로 바꿔줘!" 🤝
이 세 친구는 이름은 다르지만 "값이 NULL이면 지정한 대체값(100)을 뱉어낸다"는 점에서 결과가 똑같아요!

- 1번: ISNULL(COMM, 100) (SQL Server 스타일)
	- 컴퓨터의 해석: "COMM이 NULL이네? 그럼 100을 반환할게!"
- 4번: NVL(COMM, 100) (오라클 스타일 - 1번과 쌍둥이)
	- 컴퓨터의 해석: "COMM이 NULL이구나? 그럼 뒤에 적힌 100으로 채워줄게!"
- 3번 (내 답안): NVL2(COMM, COMM, 100) (오라클 스타일 삼항연산자)
	- 문법: NVL2(대상, NULL이 아닐 때 값, NULL일 때 값)
	- 컴퓨터의 해석: "COMM이 NULL이네? 그럼 3번째 자리에 있는 100을 뱉을게!"
	- (만약 NULL이 아니라 500이었다면 2번째 자리인 500을 뱉었을 거예요!)

💥 결론: 1번, 3번, 4번은 COMM이 NULL일 때 전부 똑같이 100이라는 결과를 출력해요!

⚡ 2번 정답 함수 분석: "값이 같으면 NULL로 만들어버려!" 💔
혼자 정답이 된 NULLIF는 작동 방식이 완전히 딴판이에요!
- 문법: NULLIF(A, B) ➔ A와 B가 같으면 NULL을 반환하고, 다르면 A를 반환한다.
- 컴퓨터의 해석 (COMM이 100일 때): "NULLIF(100, 100)이네? 어, 둘이 똑같다! 그럼 난 NULL을 뱉을래!"
- 컴퓨터의 해석 (COMM이 NULL일 때): "NULLIF(NULL, 100)이네? 둘이 다르니까 첫 번째 값인 NULL을 뱉을래!"

어떤 숫자를 넣어도 2번 NULLIF 함수는 절대 100이라는 결과를 뱉지 않고 NULL이나 원래 있던 숫자를 뱉기 때문에, 혼자 결과가 달라서 정답이 되는 거랍니다!

📌 요약 노트!
- NVL, ISNULL, NVL2 ➔ NULL을 만나면 다른 정상적인 숫자(100)로 구제해 주는 함수들!
- NULLIF ➔ 특정 조건이 맞으면 오히려 값을 NULL로 훼손(변환)시키는 함수!

라) 단일행 함수는 다중행 함수와 다르게 여러 개의 인수가 입력 되어도 단일 값만을 반환한다. (거짓 ❌)
- 왜 틀렸을까?: 문장이 아주 교묘하죠? '여러 개의 인수가 입력되어도 단일 값만을 반환한다'는 성질은 단일행 함수와 다중행 함수 둘 다의 공통점이에요!
- 비교해 보기: * 단일행 함수인 CONCAT('A', 'B') ➔ 인자 2개 들어가서 결과는 'AB' (단일 값)

- 즉, 다중행 함수와 '다르게'라고 말했기 때문에 틀린 문장이 됩니다. 둘 다 똑같이 최종 결과는 단일 값을 뱉어내니까요!

📌 요약 노트!
- 단일행 함수는 행이 아무리 많아도 각 행마다 독립적으로 실행되므로, 조인 결과가 다중행이어도 얼마든지 사용할 수 있다! (다 오답 처리)

답안과 정답

1번
내 답안
SELECT DEPTNO

2번
정답
SELECT ENAME

WHERE ROWNUM = 2;
3번
SELECT EMPNO
FROM EMP
WHERE ROWNUM = 1;
4번
내 답안
정답
SELECT ROWNUM, ENAME
FROM EMP
WHERE ROWNUM = 2;

###
정답 : 2,4번

🔑 ROWNUM의 절대 법칙: "1등이 없으면 2등도 없다!"
ROWNUM은 테이블에 원래 저장되어 있는 숫자가 아니에요. 데이터가 검색되어 화면에 출력되는 순서대로 오라클이 실시간으로 1번부터 매겨주는 '임시 번호'랍니다.

이 임시 번호가 매겨지는 메커니즘에는 엄청나게 엄격한 규칙이 있어요.
	- 🚨 오라클의 ROWNUM 규칙: > 데이터가 화면에 합격해서 나갈 때마다 번호를 매기기 때문에, 반드시 1번(1등)부터 차례대로 번호가 부여되어야만 한다! 1번 번표를 받아 간 데이터가 없다면, 그 뒤에 2번, 3번 번표는 세상에 태어날 수가 없다!

🕵️‍♂️ 2번, 4번 쿼리가 폭망하는 컴퓨터의 처리 과정 (WHERE ROWNUM = 2)
컴퓨터가 WHERE ROWNUM = 2라는 조건을 만나면 어떤 삽질을 하는지 순서대로 보여드릴게요.
- 컴퓨터: "자, EMP 테이블에서 첫 번째 행(예: 김승원)을 일단 뽑아보자!"
- 컴퓨터: "얘가 첫 번째로 뽑힌 데이터니까 일단 임시로 ROWNUM = 1을 부여할게."
- 컴퓨터: "이제 WHERE 절 조건이랑 비교해 볼까? ROWNUM이 2여야 합격인데... 어? 너 1번이잖아? 탈락!! ❌"
- 컴퓨터: "첫 번째 데이터가 탈락했으니, 다음 데이터(예: 이순신)를 가져와 보자!"
- 컴퓨터: "자, 이순신이 다시 첫 번째로 합격 대기 줄에 섰네? 그럼 얘한테 다시 ROWNUM = 1을 부여해야지!"
- 컴퓨터: "조건 비교 시작! 어? 너도 1번이네? 탈락!! ❌"
- 컴퓨터: (테이블 끝날 때까지 1번만 계속 주다가 무한 탈락 반복...)

💥 결론: 1번이 합격해서 통과되어야 다음 녀석한테 2번 번호가 부여되는데, 시작하자마자 2번이냐고 물어보니 1번 데이터들이 영원히 통과를 못 하는 구조가 됩니다. 그래서 2번과 4번 쿼리는 에러는 안 나지만 결과가 아무것도 나오지 않는(No rows selected) 잘못된 쿼리가 되는 거예요!

📌 오답 노트 꿀팁!
- ROWNUM은 무조건 1번부터 차례대로 생겨나야 한다.
- 따라서 ROWNUM = 2, ROWNUM = 3처럼 1을 건너뛰고 특정 숫자만 콕 집어서 같냐고 물어보는 조건문(=)은 무조건 오답이다!
- 마찬가지로 ROWNUM > 5 처럼 1등을 배제하는 초과, 크다 조건도 전부 데이터가 안 나오는 엉터리 조건이다!

TAB1을 기준으로 TAB2에서 값이 같은 녀석을 찾아서 기차처럼 연결해 볼게요.

① TAB1의 1번 행 (1, 'A') 처리
- TAB2에서 COL2가 'A'인 녀석을 찾습니다. ➔ TAB2 응답: "여기 1번 행(1, 'A') 있어요!"
- 합체 결과 1개 생성: (COL1: 1, COL2: 'A') — (COL1: 1, COL2: 'A')

② TAB1의 2번 행 (2, 'B') 처리 ★★★ 여기가 대박 함정!
- TAB2에서 COL2가 'B'인 녀석을 찾습니다. ➔ TAB2 응답: "어? 나 'B' 두 개나 있는데? 2번 행이랑 3번 행 둘 다 주지!"
- 합체 결과 2개 생성: * 하나는 TAB2의 2번이랑 합체 ➔ (COL1: 2, COL2: 'B') — (COL1: 2, COL2: 'B')
	- 다른 하나는 TAB2의 3번이랑 합체 ➔ (COL1: 2, COL2: 'B') — (COL1: 3, COL2: 'B')

③ TAB1의 4번 행 (4, 'C') 처리
- TAB2에서 'C'를 찾지만 없네요? ➔ 탈락!

결과
| 1번 행 |   1    |          'A'          |   1    |  'A'  |
| 2번 행 |   2    |          'B'          |   2    |  'B'  |

문제

SQL의 LIKE 구문을 사용해서 데이터 내부에 "_"이 있는 것을 검색하는 것은?

답안과 정답

1번
SELECT *
FROM Mytest
WHERE NAME LIKE '%_%' ESCAPE '_'
2번
정답
SELECT *
FROM Mytest
WHERE NAME LIKE '%@_%' ESCAPE '@'
3번
SELECT *
FROM Mytest
WHERE NAME LIKE '%#_%'
4번
내 답안
SELECT *
FROM Mytest
WHERE NAME LIKE '%_%'

###
정답 : 2번

🪄 해결사 등장: ESCAPE (탈출 문자)
그렇다면 진짜 글자 모양 그대로의 언더바(_)를 찾고 싶을 때는 어떻게 해야 할까요? 바로 ESCAPE라는 옵션을 써서 와일드카드의 초능력을 잠시 빼앗아야 해요!

💡 ESCAPE 규칙:
"내가 지정한 특수문자(예: @나 #) 바로 뒤에 오는 와일드카드는 초능력을 잃고 순수한 일반 글자로 취급한다!"

⭕ 2번 정답 공식의 컴퓨터 해석 (LIKE '%@_%' ESCAPE '@')
- 맨 뒤에 ESCAPE '@'가 붙었네요? 컴퓨터는 "지금부터 골뱅이(@) 바로 뒤에 붙는 와일드카드는 진짜 글자로 취급할게!" 하고 인지합니다.
- 이제 조건을 봅니다 ➔ %@_%
- 맨 앞과 맨 뒤의 %는 평범한 와일드카드니까 "앞뒤에 무슨 글자가 오든 노상관!" 이라는 뜻이에요.
- 그런데 가운데를 보니 @_ 가 있죠? @ 뒤에 _가 왔으니, 이 _는 '아무 글자 1개'가 아니라 진짜 눈에 보이는 언더바(_) 글자 자체로 변신합니다!
- 최종 해석: "이름 내부에 진짜 언더바(_) 글자가 콕 박혀있는 데이터만 골라내라!" (완벽한 정답! 🎯)

### 🚨 SQL LIKE 와일드카드 탈출 (ESCAPE) 핵심 정리

1. 일반적인 LIKE 와일드카드 의미
   - `%` : 글자 수 제한 없음 (0글자 이상)
   - `_` : 아무 글자나 딱 1글자 매칭

2. 함정 분석: WHERE NAME LIKE '%_%'
   - 컴퓨터는 가운데 `_`를 '아무 글자 1개'로 해석함.
   - 즉, '글자가 1개라도 있는 모든 데이터'를 조회하므로 '언더바 자체'를 검색할 수 없음.

3. 해결책: ESCAPE 옵션 사용
   - 특정 기호 뒤의 와일드카드를 순수 문자로 인식하게 만듦.
   - 예시: WHERE NAME LIKE '%@_%' ESCAPE '@'
   - 해석: `@` 뒤에 오는 `_`는 와일드카드가 아닌 순수한 언더바('_') 글자 자체로 취급함!

아래와 같은 테이블 TAB1, TAB2가 있을 때 아래 SQL의 결과 건수를 알맞게 나열한 것은?

TAB1
| COL1 | COL2 | KEY1 |
|  BBB  |  123  |   B  |
|  DDD  |  222  |   C  |
|  EEE  |  233  |   D  |
|  FFF  |  143  |   E  |

TAB2
| KEY2 | COL1 | COL2 |
|   A  |  10  |  BC  |
|   B  |  10  |  CD  |
|   C  |  10  |  DE  |

SELECT * FROM TAB1 A INNER JOIN TAB2 B ON (A.KEY1 = B.KEY2);

SELECT * FROM TAB1 A LEFT OUTER JOIN TAB2 B ON (A.KEY1 = B.KEY2);

SELECT * FROM TAB1 A RIGHT OUTER JOIN TAB2 B ON (A.KEY1 = B.KEY2);

SELECT * FROM TAB1 A FULL OUTER JOIN TAB2 B ON (A.KEY1 = B.KEY2);

SELECT * FROM TAB1 A CROSS JOIN TAB2 B;

답안과 정답

1번
내 답안
2,4,3,7,12
2번
2,3,4,5,12
3번
2,4,5,3,12
4번
정답
2,4,3,5,12


###
정답 : 4번

📊 조인(JOIN) 종류별 결과 건수 마스터하기
[기본 데이터 상태]
- TAB1 (왼쪽) : 총 4행 (KEY1: B, C, D, E)
- TAB2 (오른쪽): 총 3행 (KEY2: A, B, C)
* 교집합(커플): B, C (2개)
* 왼쪽 솔로  : D, E (2개)
* 오른쪽 솔로 : A (1개)

[조인 결과 건수 공식]
1. INNER JOIN
   - 공식: 순수 커플 매칭 건수
   - 계산: 2건 (B, C)

2. LEFT OUTER JOIN
   - 공식: 커플 건수 + 왼쪽 솔로 건수
   - 계산: 2 + 2 = 4건

3. RIGHT OUTER JOIN
   - 공식: 커플 건수 + 오른쪽 솔로 건수
   - 계산: 2 + 1 = 3건

4. FULL OUTER JOIN ★중요★
   - 공식: 커플 건수 + 왼쪽 솔로 건수 + 오른쪽 솔로 건수 (중복 제거)
   - 계산: 2 + 2 + 1 = 5건

5. CROSS JOIN
   - 공식: 왼쪽 행 수 X 오른쪽 행 수 (카테시안 곱)
   - 계산: 4 X 3 = 12건

★ 최종 정답 배열: 2, 4, 3, 5, 12

문제

식과 절의 반환 규칙을 적용하면, 다음 표현식 결과로 옳은 것은?
지문

SELECT NULLIF(100, 100)
FROM dual;

답안과 정답

1번
내 답안
100
2번
정답
NULL
3번
-1
4번
0

###
정답 : 2번(NULL)

🔑 NULLIF 함수의 절대 규칙: "같으면 NULL, 다르면 첫 번째 값!"
NULLIF(값1, 값2) 함수는 오라클 컴퓨터한테 딱 한 가지만 검사하라고 시키는 보초병과 같아요. 규칙은 아주 단순합니다.

🪄 NULLIF 작동 매커니즘:
	- 들어온 두 값이 **완벽하게 같으면 ➔ NULL**을 반환한다.
	- 들어온 두 값이 **서로 다르면 ➔ 무조건 앞의 녀석(값1)**을 반환한다.

 컴퓨터 내부에서는 이 함수를 사실상 아래와 같은 CASE WHEN 문장으로 바꿔서 해석해요.
SQL
-- 컴퓨터가 속으로 해석하는 원래 문장
CASE 
    WHEN 값1 = 값2 THEN NULL
    ELSE 값1
END

🕵️‍♂️ 지문의 쿼리 처리 과정 파헤치기 (NULLIF(100, 100))
이제 지문에 나온 데이터를 대입해 볼까요?
오라클 컴퓨터가 NULLIF(100, 100)을 만나면 아래 순서대로 뇌 회로를 돌립니다.

- 컴퓨터: "오, NULLIF 함수가 들어왔네? 두 값을 비교해 봐야지."
- 컴퓨터: "앞에 있는 숫자는 100이고, 뒤에 있는 숫자도 100이네?"
- 컴퓨터: "어라? 두 값이 완벽하게 같잖아! (100 = 100)"
- 컴퓨터: "규칙에 따라 똑같은 녀석들이 들어왔으니, 흔적을 지우고 NULL을 리턴한다!"

그래서 최종 화면에는 아무것도 없는 상태인 NULL이 쾅 찍히게 되는 거랍니다!

NULLIF(100, 200) = 100 출력

🔢 2단계: TO_NUMBER(...) 분석하기
방금 잘라낸 문자열을 순수한 숫자로 바꾸라는 명령이에요. 숫자로 바뀌면서 앞자리에 있던 의미 없는 숫자 0이 탈락하게 됩니다! ★★★ 여기가 첫 번째 변화 포인트예요!

'12' ➔ 12
'11' ➔ 11
'06' ➔ 6 (앞의 0이 지워짐)
'01' ➔ 1 (앞의 0이 지워짐)
'08' ➔ 8 (앞의 0이 지워짐)

🔤 3단계: TO_CHAR(...) 분석하기 ★★★ 대박 함정 등장!
정렬하기 직전, 숫자로 바뀐 녀석들을 다시 문자로 변환하라고 합니다. 형변환 형식 포맷(예: '00')을 따로 지정하지 않고 그냥 값만 넣었기 때문에, 앞의 0이 날아간 순수한 숫자 모양 그대로의 문자로 변신해요!

12 ➔ '12'
11 ➔ '11'
6 ➔ '6'
1 ➔ '1'
8 ➔ '8'
