PIVOT과 UNPIVOT에 대한 설명으로 가장 적절한 것은?

1
PIVOT 시 FOR 앞에는 반드시 집계함수(SUM, AVG 등)의 형태여야 한다.

2
UNPIVOT시 쌓을 컬럼을 지정할 수 없다.

3
UNPIVOT은 LONG 데이터를 WIDE 데이터로 변환하는 기법이다.

4
PIVOT은 교차표 형태의 데이터를 TIDY 데이터로 변경하는 문법이다.


###
정답: 1번

해설: PIVOT은 행 데이터를 열로 바꾸면서 특정 값들을 요약해서 보여주는 기능이에요. 그렇기 때문에 열로 변환될 데이터들에 대해 반드시 SUM, AVG, COUNT 같은 집계 함수를 사용하여 어떻게 합칠지 지정해줘야 한답니다.

오답 체크 (왜 틀렸을까요?)
2번: 틀렸어요! UNPIVOT을 할 때 새롭게 생성될 컬럼명(값들이 들어갈 컬럼과 이름이 들어갈 컬럼)을 사용자가 직접 지정할 수 있습니다.
3번: 반대로 설명되었어요. UNPIVOT은 가로로 넓은 WIDE 데이터를 세로로 긴 LONG 데이터로 바꾸는 기법이에요. (WIDE → LONG)
4번: 이것도 반대예요! PIVOT은 데이터 분석을 위해 펼쳐진 교차표(Cross Tab) 형태로 만드는 것이고, TIDY 데이터(단정한 데이터) 형태로 만드는 것은 보통 UNPIVOT의 역할이랍니다.

데이터 구조의 목적을 생각하면, 논리적 데이터 독립성에 대한 설명으로 가장 적절한 것은?
지문
스토리지 구조 변경 후 응용 SQL 영향 범위를 검토한다.


1
개념 스키마가 바뀌지 않으면 외부 스키마는 물리 저장 방식 변경의 영향을 적게 받는다.

2
논리적 데이터 독립성은 백업 정책만을 의미한다.

3
논리적 데이터 독립성은 COMMIT과 ROLLBACK의 독립성을 말한다.

4
테이블스페이스 위치가 바뀌면 모든 응용 SQL을 수정해야 한다.


###
정답: 1번

해설: 논리적 데이터 독립성이란 개념 스키마(전체적인 논리적 구조)가 변경되어도 외부 스키마(사용자 뷰)에는 영향을 주지 않는 성질을 말해요. 보기 1번은 비록 '물리 저장 방식'이라는 단어가 섞여 있어 헷갈릴 수 있지만, 핵심은 "상위 단계(외부 스키마)가 하위 단계(개념 스키마)의 변화에 영향을 받지 않는다"는 논리적 독립성의 원리를 설명하고 있어요.

💡 오답 체크 (왜 틀렸을까요?)
2번: 데이터 독립성은 백업 정책과는 거리가 멀고, 데이터 구조 변경에 따른 응용 프로그램의 유지보수 비용을 줄이는 데 목적이 있어요.

3번: COMMIT과 ROLLBACK은 트랜잭션 제어(TCL)에 관한 내용이지, 데이터 독립성과는 상관이 없답니다.

4번: 테이블스페이스(물리적 저장 위치)가 바뀌어도 응용 SQL을 수정하지 않아도 되는 성질은 물리적 데이터 독립성에 해당해요. 즉, 수정해야 한다는 설명은 틀린 것이죠!

###
💡 집합 연산자의 '중복 제거' 규칙
SQL에서 사용하는 집합 연산자 4형제 중, 중복을 그대로 두는 착한(?) 친구는 딱 하나뿐이에요.

- UNION ALL: "난 귀찮아, 그냥 다 합쳐!" (중복 제거 안 함, 정렬 안 함)
- UNION: "합치되, 똑같은 건 하나만 남겨!" (중복 제거, 정렬함)
- INTERSECT: "교집합만 남기고, 똑같은 건 하나만!" (중복 제거, 정렬함)
- MINUS (또는 EXCEPT): "차집합 구하고, 남은 것 중에 똑같은 건 하나만!" (중복 제거, 정렬함)

TEST1 + TEST2 - TEST3(MINUS중복제거) 

-----------------------------------------------------------------------------

1. INNER JOIN (내부 조인)
시험에서는 보통 WHERE절에 조건을 주거나 INNER JOIN 키워드를 써서 나와요.

- 핵심: 양쪽 테이블에 조인 키(Key) 값이 동시에 존재해야만 결과에 나타나요.
- 시험 포인트: 한쪽 테이블에만 데이터가 있거나, 조인 키 컬럼에 NULL이 있으면 결과에서 무조건 제외됩니다!

2. OUTER JOIN (외부 조인)
SQLD에서 정말 좋아하는 함정 문제예요. '기준'이 어디냐가 생명이죠!

- LEFT OUTER JOIN: 왼쪽 테이블은 '묻지도 따지지도 않고' 다 나와요. 오른쪽 테이블에 짝이 없으면 그 자리만 NULL로 채워집니다.
- RIGHT OUTER JOIN: 오른쪽 테이블이 주인공! 오른쪽은 다 나오고 왼쪽이 NULL로 채워져요.
- FULL OUTER JOIN: 양쪽 다 나오는데, 짝 없는 곳은 전부 NULL 파티!

3. INNER vs OUTER 차이점 딱 한 줄 정리!
- OUTER JOIN: "짝이 없어도 일단 다 나와! 대신 빈자리는 NULL로 채워줄게."
- INNER JOIN: "양쪽 다 데이터가 있어야만 나올 수 있어! 한쪽이라도 없으면 출력에서 빼버려!"

정답: 2번 Natural Join

해설
NATURAL
JOIN은 두 테이블 간에 동일한 칼럼 이름을 가진 것을 모두 출력하는 조인 방법이다.

해설: NATURAL JOIN은 이름 그대로 '자연스럽게' 조인을 해주는 방식이에요. 우리가 일일이 ON A.ID = B.ID라고 적어주지 않아도, SQL이 알아서 두 테이블을 뒤져보고 이름과 데이터 유형이 똑같은 컬럼이 있으면 그걸 기준으로 조인을 수행한답니다.

💡 보기에 나온 다른 조인들도 슥 살펴볼까요? (SQLD 대비용!)
1번 USING 절: NATURAL JOIN처럼 컬럼 이름이 같을 때 쓰지만, 이름이 같은 컬럼이 여러 개일 때 "이 컬럼 하나만 기준으로 써!"라고 딱 집어서 지정해주고 싶을 때 사용해요.
3번 Cross Join: 이건 짝을 찾는 게 아니라, 양쪽 테이블의 모든 행을 서로 다 한 번씩 곱해버리는 방식이에요. (결과가 엄청나게 많아지겠죠? 😱)
4번 Inner Join: 우리가 아까 공부한 가장 일반적인 조인이에요. 보통 ON절을 써서 어떤 컬럼끼리 맞출지 직접 알려줘야 해요.


⚠️ SQLD 시험용 주의사항 (꼭 읽어보세요!)
NATURAL JOIN은 편리해 보이지만 시험에서 함정으로 자주 나오는 특징이 있어요.
1. 중복 컬럼은 하나만!: 원래 조인을 하면 A.ID, B.ID 이렇게 두 개가 다 보일 수 있는데, NATURAL JOIN은 똑똑하게 ID 컬럼을 하나로 합쳐서 맨 앞에 보여줘요.
2. 별칭(Alias) 금지: NATURAL JOIN에서 기준이 된 컬럼 앞에는 테이블 이름이나 별칭(예: A.ID)을 붙이면 오류가 나요! 그냥 ID라고만 적어야 합니다.
3. 데이터 유형도 같아야 함: 이름만 같다고 다 되는 게 아니라 데이터 타입까지 똑같아야 '자연스럽게' 연결된답니다.

테이블 그림을 기준으로 SQL문을 해석하면, 다음 계층형 질의 결과에서 LEVEL = 2인 행 수는?
지문

SELECT emp_id,
       emp_name,
       mgr_id,
       LEVEL AS lv
FROM emp_tree
START WITH mgr_id IS NULL
CONNECT BY PRIOR emp_id = mgr_id
ORDER SIBLINGS BY emp_name;

###
📝 계층형 질의(Hierarchical Query) 한 줄 해설
SELECT emp_id, emp_name, mgr_id, LEVEL AS lv
	의미: 사원번호, 이름, 관리자번호를 가져오고, 특히 계층의 깊이를 나타내는 가상의 컬럼인 LEVEL을 lv라는 별칭으로 보여달라는 뜻이에요. (루트는 1, 그 아래는 2...)

FROM emp_tree
	의미: 데이터를 꺼내올 테이블 이름이 emp_tree라는 뜻이에요.

START WITH mgr_id IS NULL
	의미: "어디서부터 시작할까?"를 정하는 문장이에요. 관리자 번호(mgr_id)가 비어있는 사람, 즉 최상위 대장(CEO)부터 나무를 그리기 시작하겠다는 뜻이에요. (여기가 LEVEL 1이 됩니다!)

CONNECT BY PRIOR emp_id = mgr_id
	의미: "부모와 자식을 어떻게 연결할까?"를 정하는 핵심 문장이에요.

PRIOR emp_id: "방금 찾은 사람(부모)의 사원번호가"
	= mgr_id: "누군가의 관리자 번호와 같은 사람을 찾아라"
	즉, 위에서 아래로 내려가는 순방향 전개를 하겠다는 뜻이에요.

ORDER SIBLINGS BY emp_name
	의미: "형제들끼리만 정렬해!"라는 뜻이에요.
	그냥 ORDER BY를 쓰면 계층 구조가 엉망진창 섞여버리지만, SIBLINGS를 붙이면 같은 부모를 둔 자식들(형제들)끼리만 이름순으로 정렬해줘서 계층 구조가 예쁘게 유지된답니다.

요약!
- START WITH: 시작점 (뿌리)
- CONNECT BY: 연결 고리 (가지)
- PRIOR: "이전 단계의 것" (이게 어디 붙어있느냐에 따라 위로 갈지 아래로 갈지 정해져요!)
- LEVEL: 계층의 깊이 (1부터 시작!)

###
정답 : ( 2,3 )

1. 필터: 결과 컬럼의 개수가 같은가? (가장 중요!)
1번: SELECT A.ID, B.ID → 컬럼이 2개입니다. (A의 ID 칸, B의 ID 칸이 따로 있어요)
2, 3번: 집합 연산은 무조건 위아래로 포개기 때문에 결과적으로 1개(또는 정해진 개수)의 컬럼으로 합쳐집니다.
결론: 여기서 이미 1번은 탈락!

2. 필터: 중복을 어떻게 처리하는가?
2번: LEFT JOIN과 RIGHT JOIN은 가운데 교집합이 겹치는데, UNION이 이걸 한 줄로 합쳐줍니다.
3번: INNER JOIN, A만 있는 거, B만 있는 거를 따로 구했기 때문에 겹칠 일이 없죠. 그래서 UNION ALL을 써도 중복이 안 생겨요.
결론: 2번과 3번은 최종적으로 같은 데이터 셋을 만듭니다.

3. 필터: WHERE 조건으로 차집합을 잘 구했는가? (3번 분석)
3번에서 쓴 WHERE NOT EXISTS는 "상대방 테이블에 내 ID가 없는 경우만 가져와라"라는 뜻이에요.
즉, 순수한 차집합을 구하는 전형적인 문법이죠.
결론: (교집합) + (A-B 차집합) + (B-A 차집합) = 합집합이라는 논리를 완벽하게 구현한 거예요.

###요약 노트
FULL OUTER JOIN: "나란히 보여주기" (조인 문법)
UNION / UNION ALL: "위아래로 쌓기" (집합 문법)
NOT EXISTS: "너 빼고 나만" (차집합 구현)

틀린 이유: '방식'이라는 단어 때문이에요, 관계의 페어링이 아닌 관계의 차수에 에 관한 설명이다

페어링(Pairing): 실제 데이터(레코드) 하나하나가 서로 '짝을 맺고 있는 상태' 그 자체를 의미해요. (구체적)

옳은 표현: "관계의 페어링은 엔터티 내의 인스턴스(데이터)들이 서로 개별적으로 관계를 맺고 있는 '실제 상태'를 나타낸다."

3번 쿼리: 한 줄씩 뜯어보기
1. SELECT (CASE GROUPING(B.지역ID) WHEN 1 THEN '지역전체' ELSE MIN(B.지역명) END) AS 지역명
- 의미: "지금 이 줄이 모든 지역을 다 합친 총합계 줄인가요?" 하고 물어보는 거예요.
- 만약 맞다면(WHEN 1), 표의 맨 마지막 줄처럼 '지역전체'라고 써주고,
- 그냥 일반 지역 데이터라면(ELSE), 원래 이름인 '서울, 경기...' 등을 보여주라는 뜻이에요. (MIN은 문법상 맞추기 위해 쓴 거예요!)

2. ,(CASE GROUPING(TO_CHAR(A.이용일시, 'YYYY.MM')) WHEN 1 THEN '월별합계' ELSE TO_CHAR(A.이용일시, 'YYYY.MM') END) AS 이용월
- 의미: "이번엔 이 줄이 한 지역 내에서 월들을 다 합친 소계 줄인가요?" 하고 묻는 거예요.
- 맞다면(WHEN 1), 표 중간중간 보이는 '월별합계'라는 글자를 찍어주고,
- 아니라면 그냥 날짜(2014.01 등)를 예쁘게 글자로 바꿔서 보여주라는 뜻이죠!

3. ,SUM(A.이용량) AS 이용량
- 의미: 이건 쉽죠? 끼리끼리 묶인 것들의 이용량을 다 더해서 숫자로 보여달라는 뜻이에요.

4. FROM 이용내역 A INNER JOIN 지역 B ON (A.지역ID = B.지역ID)
- 의미: '이용내역' 테이블이랑 '지역' 테이블을 ID가 같은 것끼리 딱 붙여서 가져오겠다는 거예요. (그래야 지역 이름을 알 수 있으니까요!)

5. GROUP BY ROLLUP(B.지역ID, TO_CHAR(A.이용일시, 'YYYY.MM'))
- 핵심: 이게 이 문제의 주인공이에요!
- ROLLUP은 계단을 내려오듯 합계를 구해요.
	- 1단계: (지역, 월)별로 상세히 더하기
	- 2단계: 지역별로 월을 싹 합친 소계 구하기 (`월별합계`가 여기서 나와요!)
	- 3단계: 마지막으로 모든 지역을 다 합친 총계 구하기 (`지역전체`가 여기서 나와요!)

###
🔍 GROUPING(B.지역ID)이 하는 일
보통 GROUP BY를 하면 데이터가 묶이잖아요? 그런데 ROLLUP이나 CUBE를 쓰면 컴퓨터가 중간에 '합계'나 '총계' 줄을 강제로 끼워 넣어요. 이때 이 줄이 진짜 데이터인지, 아니면 컴퓨터가 만든 합계 줄인지 헷갈릴 수 있죠.

그때 GROUPING 함수를 쓰면 숫자 0이나 1로 대답해줘요.
- 결과가 1이면: "맞아! 지금 이 줄은 지역ID들을 싹 다 합쳐서(ROLLUP/CUBE) 만든 합계 줄이야!"라는 신호예요.
- 결과가 0이면: "아니, 이건 그냥 평범한 데이터 줄이야."라는 뜻이죠.

###
GROUP BY ROLLUP 과 GROUPING 차이
1. ROLLUP (합계 생성기 🏗️)
GROUP BY 뒤에 붙어서, 우리가 평소 보는 데이터 외에 중간 합계(소계)와 맨 밑 총합계 줄을 실제로 만들어내는 역할을 해요.
- 하는 일: "서울 1월", "서울 2월" 데이터만 있는 게 아니라, 그 밑에 "서울 합계"라는 줄을 물리적으로 추가합니다.
- 특징: 합계 줄을 만들 때, 합쳐진 칸(지역명 등)은 넣을 데이터가 없으니 기본적으로 NULL로 표시돼요.

2. GROUPING (합계 판독기 🔍)
ROLLUP이 열심히 만들어놓은 줄들을 하나씩 검사하는 역할을 해요.
- 하는 일: "이 줄은 원래 있던 데이터야? 아니면 ROLLUP이 방금 만든 합계 줄이야?"라고 물어보고 답을 줍니다.
	- 0 반환: 원래 있던 데이터 줄이다!
	- 1 반환: ROLLUP이 만든 합계 줄이다!
- 쓰는 이유: 합계 줄에 나오는 보기 싫은 NULL 대신, 승원님이 아까 보신 '지역전체'나 '월별합계' 같은 예쁜 이름을 붙여주기 위해 사용해요.

### 요약
🏗️ 1. GROUP BY (기본 바구니)
역할: 데이터를 끼리끼리 묶어주는 가장 기본적인 바구니예요.
한 줄 요약: "전체 데이터를 지역별, 혹은 월별로 나누는 기준을 정해요."

🪜 2. ROLLUP (계단식 합계)
역할: 묶은 데이터들 사이에 중간 합계(소계)와 맨 밑 총합계 줄을 추가해요.
한 줄 요약: "위에서 아래로 내려오며 단계별로 합계 줄을 만들어줘요."

🧊 3. CUBE (모든 조합 합계)
역할: ROLLUP보다 더 부지런하게, 가능한 모든 항목의 조합에 대해 합계 줄을 만들어요.
한 줄 요약: "순서 상관없이 모든 경우의 수에 대한 합계를 다 보여줘요."

🔍 4. GROUPING (합계 판독기)
역할: 지금 보고 있는 줄이 진짜 데이터인지, 아니면 ROLLUP/CUBE가 만든 합계 줄인지 확인해요.
한 줄 요약: "합계 줄이면 1, 아니면 0을 줘서 이름을 '총계'로 바꿀 수 있게 도와줘요."

그룹 내 순위 관련 WINDOW 함수의 특징으로 틀린 것은?

1
CUMM_RANK 함수는 누적된 순위를 부여할 수 있다(등수를 누적 순위로 표현함).

2
RANK 함수가 동일한 값에 대해서는 동일한 순위를 부여하는 데 반해 ROW_NUMBER 함수는 고유한 순위를 부여한다(같은 등수가 존재할 수 없음).

3
DENSE_RANK 함수는 RANK 함수와 흡사하나 동일한 순위를 하나의 건수로 취급하는 것이 틀린 점이다(같은 등수에 여럿이 존재하는 경우에도 등수가 SKIP되지 않음).

4
RANK 함수는 동일한 값에 대해서는 동일한 순위를 부여한다(같은 등수에 여럿이 존재하는 경우 등수가 SKIP될 수 있음).

정답은 1번

🔍 1번이 틀린 이유 (CUMM_RANK는 없어요!)

DENSE_RANK를 설명하는 지문.
비슷한 함수: 아마 CUME_DIST라는 함수와 헷갈리게 하려고 낸 함정일 거예요. CUME_DIST는 누적 백분율(0~1 사이의 값)을 구하는 함수이지, 단순히 '누적 등수'를 표현하는 함수는 아니랍니다.

✅ 2, 3, 4번이 맞는 이유 (순위 3대장 비교)
이 부분은 승원님이 실무나 시험에서 정말 자주 보게 될 내용이라 그림과 함께 정리해 두면 아주 좋아요!

함수		특징				예시 (점수가 100, 100, 90일 때)
RANK		공동 순위 인정, 다음 순위 건너뜀	1등, 1등, 3등
DENSE_RANK	공동 순위 인정, 다음 순위 유지	1등, 1등, 2등
ROW_NUMBER	공동 순위 무시, 고유 번호 부여	1등, 2등, 3등

###
정답 2번.
🔍 2번이 틀린 이유 (속성의 '원자성')
보기 내용: 하나의 인스턴스에서 각각의 속성은 하나 이상의 속성값을 가질 수 있다. (❌)

진짜 정답: 하나의 인스턴스(행)에서 각 속성(열)은 반드시 단 하나(Single Value)의 값만 가져야 합니다.

이유: 예를 들어 '승원'이라는 학생(인스턴스)의 '전화번호' 속성에 번호 2개를 한 칸에 몰아서 넣으면 안 된다는 뜻이에요. 이를 데이터 모델링에서는 '원자성(Atomicity)'이라고 부릅니다. 값이 여러 개라면 속성을 분리하거나 별도의 엔터티로 관리해야 해요.

✅ 1, 3, 4번이 맞는 이유
1번 (속성도 집합이다): 속성은 그 속성이 가질 수 있는 값들의 범위(도메인)라는 집합을 가지고 있기 때문에 집합의 성질을 가집니다. (맞음!)

3번 (두 개 이상의 속성): 엔터티가 엔터티답기 위해서는 최소한 그 대상을 설명할 속성이 2개 이상은 있어야 의미가 있어요. (예: 학번만 있고 이름이 없으면 학생 엔터티라고 하기 힘들겠죠?) (맞음!)

4번 (구체적인 정보): 엔터티(학생)를 더 자세히 설명해주는 것(이름, 나이, 주소)이 바로 속성이 하는 일이에요. (맞음!)

다음 함수 사용시 결과값이 올바르지 않은 것은?

1
SIGN(0) = 0

2
MOD(8,3) = 2

3
FLOOR(-12.345) = -13

4
CEIL(-12.345) = -13

###
정답 : 4번
4번이 틀린 이유 (CEIL 함수의 원리)
CEIL(숫자): 천장(Ceiling)이라는 뜻처럼, 주어진 숫자보다 **크거나 같은 최소의 정수**를 찾아요. (위로 올림!)

문제의 상황: CEIL(-12.345)
- 수직선에서 -12.345보다 오른쪽(큰 쪽)에 있는 정수 중 가장 가까운 것은 -12예요.
- 따라서 결과는 -13이 아니라 -12가 되어야 맞습니다!

✅ 1, 2, 3번이 맞는 이유
- 1번 SIGN(0): 이 함수는 숫자의 부호를 알려줘요. (양수면 1, 음수면 -1, **0이면 0**) 아주 정직한 친구라 맞습니다!
- 2번 MOD(8, 3): 나머지를 구하는 함수죠? 8을 3으로 나누면 몫은 2고, **나머지는 2**가 남으니 정확해요!
- 3번 FLOOR(-12.345): 바닥(Floor)이라는 뜻처럼, 숫자보다 **작거나 같은 최대의 정수**를 찾아요. (아래로 내림!)
	- 수직선에서 -12.345보다 왼쪽(작은 쪽)에 있는 정수는 -13이 맞습니다. (음수에서는 숫자가 커질수록 더 작은 거 아시죠? ☺️)

참조 무결성(Referential Integrity)에 대한 설명으로 옳은 것은?

1
자식 테이블은 부모 없이 항상 먼저 생성돼야 한다.

2
자식의 외래키 값은 부모의 기본키 값에 존재하거나 NULL이어야 한다.

3
외래키는 중복될 수 없다.

4
참조 무결성은 집계 함수가 보장한다.

###
정답 : 2번
✅ 2번이 정답인 이유 (참조 무결성의 핵심!)
내용: 자식의 외래키 값은 부모의 기본키 값에 존재하거나 NULL이어야 한다.

설명: 예를 들어 '학생(자식)' 테이블에 '학과코드'가 적혀 있다면, 그 코드는 반드시 '학과(부모)' 테이블에 실제로 등록된 코드여야 해요. 없는 학과에 학생이 소속될 수는 없으니까요! 다만, 아직 학과를 정하지 않은 신입생이라면 NULL(빈칸)로 비워둘 수는 있답니다. 이게 바로 참조 무결성의 기본 원칙이에요.

🔍 1, 3, 4번이 틀린 이유
1번 (생성 순서): 부모 없는 자식은 없죠? 테이블도 마찬가지예요! 부모 테이블이 먼저 만들어져야 그걸 참조하는 자식 테이블을 만들 수 있습니다. (순서가 반대로 되었어요 🙅‍♂️)
3번 (중복 여부): 외래키는 얼마든지 중복될 수 있어요. 예를 들어 '컴퓨터공학과'라는 부모 키를 여러 명의 학생(자식)이 가질 수 있는 것과 같죠. (중복 가능! 👍)
4번 (보장 주체): 참조 무결성은 집계 함수(SUM, AVG 등)가 아니라, 데이터베이스의 제약 조건(Constraint)이 보장합니다.

다음 그림과 SQL을 함께 보고 판단할 때, 다음 SQL 결과에서 gr = 1 이고 gp = 1 인 행 수는?
지문

SELECT region,
       product,
       SUM(amount) AS amt,
GROUPING(region) AS gr,
       GROUPING(product) AS gp
FROM order_amt
GROUP BY ROLLUP(region, product);

REGION		PRODUCT	AMOUNT
SEOUL		A		100
SEOUL		B		200
BUSAN		A		150
BUSAN		B		50


###
정답 : 1개


승원 님! 요청하신 SQL 쿼리를 한 줄씩 차근차근 설명해 드릴게요. 이 쿼리는 데이터를 그룹화하고 합계를 내는 아주 유용한 문장이에요!

🔍 SQL 구문 상세 설명
1. SELECT region, product, SUM(amount) AS amt,
- 화면에 보여줄 항목들을 정하는 부분이에요.
- region(지역)과 product(상품) 이름을 그대로 가져오고, SUM(amount)를 통해 금액의 합계를 구해서 amt라는 이름으로 보여달라는 뜻이에요.

2. GROUPING(region) AS gr,
- region 컬럼이 집계(소계/총계)에 사용되었는지 확인하는 함수예요.
- 해당 행이 지역별로 묶여서 나온 결과라면 0, 지역 구분 없이 합쳐진(총계) 상태라면 1을 반환하고 이름을 gr이라고 붙였어요.

3. GROUPING(product) AS gp
- 위와 마찬가지로 product 컬럼이 집계되었는지 확인해요.
- 상품별 상세 데이터라면 0, 상품 구분 없이 합쳐진(소계나 총계) 상태라면 1을 반환하고 이름을 gp라고 했어요.

4. FROM order_amt
- 계산에 필요한 원본 데이터가 들어있는 테이블 이름이 order_amt라는 것을 알려주는 거예요.

5. GROUP BY ROLLUP(region, product);
- 이 쿼리의 핵심이에요! 데이터를 그룹화하는데, 계층적인 합계를 자동으로 만들어달라는 명령이에요.
- (지역, 상품)별 합계 → (지역)별 소계 → (전체) 총계 순서로 데이터를 층층이 쌓아서 결과를 만들어낸답니다.

SEOUL	A	100	0	0	일반 데이터
SEOUL	B	200	0	0	일반 데이터
SEOUL	NULL	300	0	1	서울 지역 소계
BUSAN	A	150	0	0	일반 데이터
BUSAN	B	50	0	0	일반 데이터
BUSAN	NULL	200	0	1	부산 지역 소계
NULL	NULL	500	1	1	전체 총계

다음 SQL중 입력오류가 발생할 문장으로 가장 적절한 것은?
지문

CREATE TABLE TAB1( 
COL1    VARCHAR(10) PRIMARY KEY, 
COL2 NUMBER NOT NULL,    
COL3 CHAR(10) NOT NULL,     
COL4   DATE NOT NULL);


1
INSERT INTO TAB1
VALUES('0003', 40, 'CCC', '2024/01/01');

2
INSERT INTO TAB1
VALUES('0002', '30', '1000', CURRENT_DATE);

3
INSERT INTO TAB1
VALUES('0001', '20', 'BBB', SYSTIMESTAMP);

4
INSERT INTO TAB1
VALUES(1, 10, 'AAA', SYSDATE);

###
정답 : 1

1. 왜 1번이 범인인가요? ('2024/01/01')
SQL(특히 오라클)에서 날짜는 그냥 문자가 아니라 특정한 형식을 갖춰야 해요.

설정의 문제: DB 서버 설정이 만약 YYYY-MM-DD로 되어 있다면, 슬래시(/)를 쓴 '2024/01/01'은 "어? 나는 하이픈(-)만 알아듣는데 이건 뭐야?" 하고 오류를 뱉어버려요.

안전하지 않은 코드: 1번처럼 입력하면 서버 설정에 따라 성공할 수도, 실패할 수도 있어요. 그래서 시험 문제에서는 이렇게 불확실한 형식을 입력오류의 주범으로 꼽는 경우가 많답니다.

2. 그럼 다른 것들은 왜 괜찮나요?
2, 3, 4번의 날짜: CURRENT_DATE, SYSTIMESTAMP, SYSDATE는 문자가 아니라 시스템 함수예요. 컴퓨터가 자기한테 딱 맞는 날짜 데이터를 직접 생성해서 넣어주는 거라 포맷 오류가 날 일이 절대 없어요!

3번 보충 설명: 아까 제가 말한 SYSTIMESTAMP는 DATE 컬럼에 들어갈 때 초 미세 단위만 털어내고 자동으로 들어가는 경우가 많아서, 형식 자체가 틀린 1번보다는 "안전"하다고 판단되는 거예요.

3. 결론: "날짜는 함수로 넣거나, 정확한 포맷을 지켜라!"
1번 문장은 "서버가 슬래시(/)를 이해하지 못할 수도 있다"는 위험성 때문에 정답이 되는 거예요.

데이터 구조의 목적을 생각하면, 논리적 데이터 독립성에 대한 설명으로 가장 적절한 것은?
지문

스토리지 구조 변경 후 응용 SQL 영향 범위를 검토한다.


1
개념 스키마가 바뀌지 않으면 외부 스키마는 물리 저장 방식 변경의 영향을 적게 받는다.

2
논리적 데이터 독립성은 백업 정책만을 의미한다.

3
논리적 데이터 독립성은 COMMIT과 ROLLBACK의 독립성을 말한다.

4
테이블스페이스 위치가 바뀌면 모든 응용 SQL을 수정해야 한다.

### 
정답 : 1번

🔍 왜 1번이 정답일까요?
논리적 데이터 독립성의 핵심은 "데이터의 논리적 구조(개념 스키마)가 바뀌어도, 내가 보는 화면(외부 스키마)은 영향을 받지 않아야 한다"는 거예요.

- 외부 스키마: 사용자나 응용 프로그램이 보는 화면 (예: 로그인 화면)
- 개념 스키마: 전체 데이터베이스의 논리적 구조 (예: 회원 테이블의 구조)
- 논리적 독립성: 회원 테이블에 새로운 컬럼이 추가되거나 구조가 조금 바뀌어도(개념 스키마 변경), 사용자가 쓰는 로그인 프로그램(외부 스키마)은 수정할 필요가 없어야 한다는 뜻입니다.

❌ 다른 보기들이 틀린 이유
- 2번: 백업 정책은 데이터의 안전을 위한 것이지, 구조적 독립성과는 관계가 없어요.
- 3번: COMMIT과 ROLLBACK은 트랜잭션 제어(TCL)에 관한 내용이지, 독립성 개념이 아니에요.
- 4번: 테이블스페이스(물리적 저장소) 위치가 바뀌는 것은 물리적 데이터 독립성에 해당해요. 물리적 독립성이 잘 지켜진다면 응용 SQL을 수정할 필요가 없어야 정상입니다.

💡암기 꿀팁!
시험 문제에서 '독립성'이 나오면 아래 두 가지만 기억하세요!
- 논리적 독립성: 개념 스키마가 변해도 외부 스키마가 무사함! (응용 프로그램 보호)
- 물리적 독립성: 내부 스키마(저장 방식)가 변해도 개념 스키마가 무사함! (DB 구조 보호)

SQL SERVER에 구축된 TEAMSCORE 테이블에서 WINCNT가 가장 높은 4위까지 조회한다. 단, WINCNT에 동일한 순위 팀이 있으면 같이 조회하는 SQL문으로 올바른 것은?

1
SELECT TOP(4) WITH TIES TEAMNAME, WINCNT
FROM TEAMSCORE
ORDER BY WINCNT DESC;

2
SELECT TEAMNAME, WINCNT
FROM TEAMSCORE
WHERE ROWNUM <= 4
ORDER BY WINCNT DESC;

3
SELECT TOP(4) TEAMNAME, WINCNT
FROM TEAMSCORE;

4
SELECT TOP(4) TEAMNAME, WINCNT
FROM TEAMSCORE
ORDER BY WINCNT ASC;

###
정답 : 1번

🔍 왜 1번이 정답일까요?
- TOP(4): 상위 4개 행을 가져오겠다는 뜻이에요.
- WITH TIES: 이 옵션이 바로 문제에서 요구한 "동일한 순위 팀이 있으면 같이 조회하라"는 마법의 키워드예요!
	- 예를 들어, 4등의 승수가 10승인데, 5등과 6등도 똑같이 10승이라면 이 친구들까지 다 끌어모아서 보여주는 옵션이랍니다.
- ORDER BY WINCNT DESC: 높은 순서(내림차순)대로 정렬해야 '상위' 순위를 매길 수 있겠죠?

❌ 다른 보기들이 오답인 이유
- 2번: ROWNUM은 Oracle에서 사용하는 방식이에요. 문제에서 SQL SERVER라고 명시했기 때문에 문법상 틀립니다.
- 3번: ORDER BY가 없으면 순위를 매길 기준이 없어서 랜덤하게 4개가 나올 수 있고, 동일 순위 처리 옵션도 없어요.
- 4번: ASC(오름차순)로 정렬하면 승수가 가장 '낮은' 팀부터 나오게 되니 꼴찌부터 4등까지 보여주게 돼요.

다음 중 실행이 불가한 구문은?

1
SELECT COL1, COL2, COL3 C1
FROM TAB1 T
ORDER BY COL1, COL1, T.C1;

2
SELECT COL1, COL2, COL3 C1
FROM TAB1 T
ORDER BY 1, COL2, C1;

3
SELECT COL1, COL2, COL3 C1
FROM TAB1 T
ORDER BY 1, 2, 3;

4
SELECT COL1, COL2, COL3 C1
FROM TAB1 T
ORDER BY 1, COL2, COL3;

###
정답 : 1번
🔍 왜 1번이 범인일까요?
문제가 되는 부분은 바로 T.C1이에요.
- C1은 컬럼 별칭이에요: SELECT COL3 C1이라고 해서 COL3에 C1이라는 새 이름을 붙여주었죠.
- T는 테이블 별칭이에요: FROM TAB1 T라고 해서 테이블에 T라는 별명을 붙였고요.
- 결합의 오류: T.COL1이나 T.COL3처럼 실제 테이블에 존재하는 컬럼 앞에는 T.을 붙일 수 있어요. 하지만 C1은 테이블에 원래 있던 게 아니라 출력할 때만 잠깐 붙인 별명(Alias)일 뿐이죠?
	- 데이터베이스 입장에선 "테이블 T 안에 C1이라는 컬럼은 없는데?"라고 판단해서 오류를 냅니다.

핵심: ORDER BY에서 별칭(C1)은 그냥 쓸 수 있지만, 테이블 별칭을 붙인 T.C1 형태로는 쓸 수 없습니다.

✅ 다른 보기들이 괜찮은 이유
- 2번: 1(첫 번째 컬럼), COL2(실제 이름), C1(별칭)을 섞어 썼네요. ORDER BY는 SELECT 절의 별칭을 인식할 수 있어서 아주 잘 작동합니다.
- 3번: 1, 2, 3처럼 숫자를 썼죠? 이건 SELECT 절에 나열된 순서대로 정렬하라는 뜻이라 아주 표준적인 방식이에요.
- 4번: 숫자와 실제 컬럼명을 섞어 썼어요. 역시 아무 문제 없이 잘 실행됩니다.

표와 관계를 함께 읽으면, 다음 제약 조건 가정에서 부모 ORDERS 행 삭제에 대한 설명으로 옳은 것은?
지문

ORDER_DETAIL.order_id는 ORDERS.order_id를 참조하고, FK는 NULL 허용이며
ON DELETE CASCADE는 없다고 가정한다.

1
자식이 부모를 참조 중이면 부모 삭제는 거부될 수 있다.

2
부모 삭제 시 자식도 항상 자동 삭제된다.

3
NULL 허용 FK이면 참조 무결성 검사를 하지 않는다.

4
자식 FK가 자동으로 NULL로 바뀐다.

###
정답 : 1번

🔍 왜 1번이 정답일까요?
데이터베이스는 데이터끼리 서로 엉키지 않도록 참조 무결성이라는 규칙을 지켜요.
- 참조 중인 상태: 현재 ORDER_DETAIL(자식)이 ORDERS(부모)를 참조하고 있죠?
- 부모 삭제 시도: 이때 부모 데이터를 그냥 지워버리면, 자식 데이터는 누구를 참조해야 할지 모르는 '미아' 상태가 되어버려요.
- 기본 동작 (Restrict): 문제에서 별도의 ON DELETE CASCADE(자동 삭제)나 ON DELETE SET NULL(NULL로 변경) 설정이 없다고 가정했으므로, 데이터베이스는 무결성을 지키기 위해 부모 데이터의 삭제를 거절합니다.

쉽게 말해서: "너를 바라보고 있는 자식들이 아직 남아있는데, 네가 먼저 사라지면 안 돼!"라고 막아버리는 거예요.

❌ 다른 보기들이 오답인 이유
- 2번: ON DELETE CASCADE 설정이 없다고 문제에 명시되어 있으므로, 자식이 자동으로 삭제되지 않습니다.
- 3번: FK가 **NULL을 허용하더라도 참조 무결성 검사는 항상 수행**합니다. NULL이 들어가는 건 괜찮지만, **존재하지 않는 부모 ID**를 갖는 건 절대 허용하지 않거든요.
- 4번: 자동으로 NULL로 바뀌려면 **ON DELETE SET NULL** 옵션이 설정되어 있어야 해요. 그런 설정이 없다면 자동으로 바뀌지 않고 삭제 자체가 거부됩니다.

💡 SQLD 핵심 요약: 삭제 옵션 3대장
- RESTRICT / NO ACTION (기본값): 자식이 있으면 부모 삭제 불가! (1번 정답의 근거)
- CASCADE: 부모 삭제하면 자식도 같이 삭제!
- SET NULL: 부모 삭제하면 자식의 FK 값을 NULL로 변경!

다음 중 [사원] 테이블에 대하여 아래와같은 SQL을 수행하였을 때 예상되는 결과로 가장 적절한 것은?

사원ID	부서ID	사원명	연봉
001	100	홍길동	2500
002	100	강감찬	3000
003	200	김유신	4500
004	200	김선달	3000
005	200	유학생	2500
006	300	변사또	4500
007	300	박문수	3000

SELECT Y.사원ID, Y.부서ID, Y.사원명, Y.연봉
FROM (SELECT 사원ID, MAX(연봉) OVER(PARTITION BY 부서ID) AS 최고연봉
      FROM 사원) X, 사원 Y
WHERE X.사원ID = Y.사원ID
AND X.최고연봉 = Y.연봉;

결과값
002 / 100 / 강감찬 / 3000

003 / 200 / 김유신 / 4500

006 / 300 / 변사또 / 4500

###
정답 : 1번

1. 안쪽 쿼리: (SELECT 사원ID, MAX(연봉) OVER(...) AS 최고연봉 FROM 사원) X
이 부분은 원본 데이터에 "우리 부서 1등은 얼마 받아?"라는 정보를 한 줄씩 미리 적어두는 단계예요.
- MAX(연봉) OVER(PARTITION BY 부서ID):
	- PARTITION BY 부서ID: 사원들을 부서별로 잠깐 칸막이를 쳐서 나눠요 (100번팀, 200번팀, 300번팀).
	- MAX(연봉): 그 칸막이 안에서 가장 높은 연봉을 찾아요.
	- 결과: 모든 사원의 옆에 그 사람이 속한 부서의 1등 연봉이 최고연봉이라는 이름으로 따라다니게 됩니다.
	- (예: 연봉이 2500인 홍길동 옆에 "우리 부서(100번) 1등은 3000이야"라고 적힌 딱지가 붙는 셈이죠!)

2. 바깥쪽 쿼리: SELECT ... FROM X, 사원 Y
이제 위에서 만든 '딱지가 붙은 명단(X)'과 '실제 사원 명단(Y)'을 비교해서 진짜 1등만 골라낼 차례예요.
- WHERE X.사원ID = Y.사원ID: 동일 인물끼리 매칭시켜요 (데이터를 연결하는 선).
- AND X.최고연봉 = Y.연봉: 핵심 조건! "네 몸값(Y.연봉)이 아까 딱지에 적힌 부서 1등 금액(X.최고연봉)이랑 똑같니?"라고 물어보는 거예요.

3. 왜 이렇게 복잡하게 할까?
그냥 GROUP BY를 쓰면 되지 않나 싶지만, GROUP BY를 쓰면 1등 연봉값만 나오고 그게 '누구'인지는 한눈에 알기 어렵거든요.
이 쿼리 방식을 쓰면:
- 각 부서별 최고 연봉 금액을 구하면서
- 그 금액을 가진 사람의 상세 정보(사원ID, 이름 등)까지 한 번에 싹 긁어올 수 있다는 장점이 있어요!

다음 중 에러가 나지 않는 문장은? (단, DBMS는 오라클)

1
SELECT COL1 AS 컬럼1, AVG(COL2) AS 평균
FROM TAB1
GROUP BY COL1
HAVING AVG(COL2) >= 100;

2
SELECT COL1 AS 컬럼1, AVG(COL2) AS 평균
FROM TAB1
WHERE AVG(COL2) >= 100
GROUP BY 컬럼1;

3
SELECT COL1 컬럼1, AVG(COL2) 평균
FROM TAB1
GROUP BY COL2;

4
SELECT COL1 컬럼1, AVG(COL2) 평 균
FROM TAB1;

###
정답 : 1번
📋 정답 및 해설
1번: 정답 (정상 실행)
- 이유: GROUP BY로 묶인 컬럼(COL1)이 SELECT 절에 있고, 집계 함수 결과에 대한 조건은 HAVING 절에 아주 잘 작성되었어요. 오라클에서 HAVING 절은 그룹화된 결과에 필터를 걸 때 사용하며, 집계 함수를 직접 사용할 수 있답니다.

❌ 오답 체크
2번: 오류 발생
- 원인 1: WHERE 절에는 AVG(COL2) 같은 **집계 함수를 사용할 수 없어요.** 집계 함수 조건은 반드시 HAVING 절에 써야 해요.
- 원인 2: GROUP BY 절에는 SELECT 절에서 정의한 **별칭(Alias)인 '컬럼1'을 사용할 수 없어요.** 반드시 실제 컬럼명인 COL1을 써야 한답니다.

3번: 오류 발생
- 원인: SELECT 절에 집계 함수가 아닌 일반 컬럼(COL1)이 있는데, 정작 GROUP BY 절에는 다른 컬럼(COL2)만 명시되어 있어요. GROUP BY를 사용할 때는 **SELECT 절의 일반 컬럼이 반드시 GROUP BY 절에도 포함**되어야 오류가 나지 않아요.

4번: 오류 발생
- 원인 1: COL1과 집계 함수가 같이 있는데 GROUP BY 절이 빠졌어요.
- 원인 2: 별칭(Alias)에 공백이 포함된 '평 균'을 쓰려면 반드시 큰따옴표("평 균")로 감싸야 해요. 그냥 한 칸 띄우면 문법 오류가 발생한답니다.

다음 주어진 두 개의 테이블에 대해서 아래와 같은 결괏값이 반환되도록 아래의 SQL문의 빈칸에 들어갈 값을 적으시오.
지문

SELECT b.grade, a.StudentNo, SUM(b.grade)
FROM TEST44_1 a, TEST44_2 b
GROUP by
(                       );

[결과]
GRADE	STUDENTNO	SUM(B.GRADE)
50	10		50
50	20		50
50	30		50
50			150
...


1
GROUPING SETS(a.studentno, (b.grade, a.studentno));

### 
정답 : 2번

1. 그룹화 기준의 '계층적' 일관성
가장 왼쪽에 GRADE가 있고 그 다음에 STUDENTNO가 나오죠?
- 2번: GROUPING SETS(b.grade, (b.grade, a.studentno))
- 3번: GROUPING SETS(b.grade, (a.studentno, b.grade))
2번은 첫 번째 그룹 기준(b.grade)이 두 번째 복합 그룹 안에서도 가장 앞에 위치해요. 데이터가 GRADE를 중심으로 먼저 분류되고 그 안에서 STUDENTNO로 나뉘는 계층적인 구조를 문법적으로도 그대로 보여주는 거죠.

2. 정렬 순서의 암시 (Ordering)
SQL 문장에서 GROUP BY 절에 적어준 컬럼의 순서는 보통 결과의 기본 정렬 순서에 영향을 주는 경우가 많아요.
- 3번처럼 (a.studentno, b.grade)라고 쓰면, DBMS에 따라 학번을 기준으로 먼저 정렬하려고 시도할 수 있어요.
- 하지만 결과 표는 명확하게 GRADE 별로 모여서 나오고 있죠? 따라서 기준이 되는 b.grade가 앞에 오는 2번이 결과 화면과 더 완벽하게 일치하는 표현이 되는 거예요.

3. 출제 의도: ROLLUP과의 연관성
이 문제는 사실 ROLLUP(b.grade, a.studentno)과 GROUPING SETS의 변환 관계를 이해하고 있는지 묻는 문제이기도 해요.
- ROLLUP(A, B)를 GROUPING SETS로 풀면 GROUPING SETS(A, (A, B), ())가 되는데 (전체 합계 제외 시), 여기서 보듯이 기준이 되는 A가 항상 앞에 오는 것이 정석적인 표기법이랍니다.

요약하자면!
3번이 "절대 틀린 데이터가 나온다"라기보다는, 결과 표의 컬럼 순서와 정렬 상태를 보았을 때 가장 자연스럽고 정석적인 문법은 2번이기 때문에 정답이 되는 거예요.

다음 중 Oracle 계층형 질의에 대한 설명으로 가장 부적절한 것은?

1
루트 노드의 LEVEL 값은 0이다.

2
순방향전개란 부모 노드로부터 자식 노드 방향으로 전개하는 것을 말한다.

3
ORDER SIBLINGS BY절은 형제 노드 사이에서 정렬을 지정하는 구문이다.

4
START WITH절은 계층 구조의 시작점을 지정하는 구문이다.

###
정답 : 1번
📋 정답 및 해설
1번: 부적절함 (정답)
- 이유: 오라클 계층형 질의에서 루트 노드(최상위 노드)의 LEVEL 값은 1부터 시작해요. 0이 아니랍니다!
- 계층 구조: 루트 노드가 1, 그 자식 노드가 2, 그다음 손자 노드가 3... 이런 식으로 1씩 증가하면서 깊이를 나타내요.

✅ 옳은 문장 체크
2번: 옳음
- 설명: 순방향 전개는 부모로부터 자식 방향으로 내려가는 것을 말하고, 반대로 자식에서 부모로 올라가는 것을 역방향 전개라고 해요. SQLD 시험에서 두 방향을 구분하는 문제가 자주 나오니 주의 깊게 봐주세요!

3번: 옳음
- 설명: ORDER SIBLINGS BY 절은 계층 구조의 형태를 유지하면서, 같은 부모를 둔 형제 노드들끼리만 순서를 정렬하고 싶을 때 사용하는 아주 유용한 구문이에요.

4번: 옳음
- 설명: START WITH 절은 "어디서부터 조회를 시작할 것인가?"를 정하는 시작점(Root) 지정 구문이에요. 보통 START WITH 컬럼명 IS NULL 같은 식으로 최상위 관리자를 지정하곤 하죠.

💡 핵심 암기 노트
계층형 질의(CONNECT BY) 문제를 풀 때는 다음 세 가지만 기억하세요!
- LEVEL: 1부터 시작한다 (0 아님!).
- START WITH: 시작 위치를 정한다.
- CONNECT BY PRIOR: 부모와 자식의 관계를 정한다. (PRIOR 자식 = 부모 면 역방향, PRIOR 부모 = 자식 이면 순방향!)

다음 중 팀(TEAM) 테이블과 구장(STADIUM) 테이블의 관계를 아용해서 소속팀이 가지고 있는 전용구장의 정보를 팀의 정보와 함께 출력하는 SQL을 작성할 때 결과가 다른 것은?

1
SELECT TEAM.REGION_NAME, TEAM.TEAM_NAME,
TEAM.STADIUM_ID, STADIUM.STADIUM_NAME 
FROM TEAM, STADIUM
WHERE TEAM.STADIUM_ID = STADIUM.STADIUM_ID;

2
SELECT T.REGION_NAME, T.TEAM_NAME, T.STADIUM_ID,
S.STADIUM_NAME
FROM TEAM T, STADIUM S
WHERE T.STADIUM_ID = S.STADIUM_ID;

3
SELECT TEAM.REGION_NAME, TEAM.TEAM_NAME,
TEAM.STADIUM_ID, STADIUM.STADIUM_NAME 
FROM TEAM
INNER
JOIN STADIUM
ON (TEAM.STADIUM_ID =
 STADIUM.STADIUM_ID) ;

4
SELECT T.REGION_NAME, T.TEAM_NAME, T.STADIUM_ID,
S.STADIUM_NAME
FROM TEAM T
INNER
JOIN STADIUM S
 USING (T.STADIUM_ID = S.STADIUM_ID);

###
정답 : 4번
📋 정답 및 해설
4번: 결과가 다르거나 오류 발생 (정답)
- 이유: USING 절은 두 테이블에서 이름이 같은 컬럼을 기준으로 조인할 때 사용하며, 괄호 안에는 컬럼 이름만 적어야 해요.
- 틀린 부분: USING (T.STADIUM_ID = S.STADIUM_ID)처럼 조건식(=)이나 테이블 별칭(T., S.)을 사용하면 문법 오류가 발생해요.
- 올바른 문법: USING (STADIUM_ID)라고만 적어야 정상적으로 작동한답니다.

✅ 나머지 보기가 같은 결과를 내는 이유
1번 & 2번: Oracle 표준 조인 (Oracle Join)
- 설명: FROM 절에 테이블을 나열하고 WHERE 절에 조인 조건을 적는 전통적인 방식이에요. 2번처럼 테이블 별칭(T, S)을 쓰든 1번처럼 풀네임을 쓰든 결과는 똑같답니다.

3번: ANSI 표준 조인 (INNER JOIN ON)
- 설명: 현대 표준 방식인 INNER JOIN과 ON 절을 사용했어요. 1, 2번의 WHERE 조건과 동일한 논리이기 때문에 완벽히 같은 결과를 보여줘요

다음의 연산 결과가 다른 하나는?

1
SELECT LAST_DAY(TO_DATE('2024/05/14', 'YYYY/MM/DD'))
FROM DUAL;

2
SELECT TO_DATE('2024/05', 'YYYY/MM')
FROM DUAL;

3
SELECT ROUND(TO_DATE('2024/05/14', 'YYYY/MM/DD'), 'MONTH')
FROM DUAL;

4
SELECT TRUNC(TO_DATE('2024/05/14', 'YYYY/MM/DD'), 'MONTH')
FROM DUAL;

###
정답 : 1번
📋 정답 및 해설

1번: 결과가 다름 (정답)
- 연산 결과: 2024-05-31
- 이유: LAST_DAY 함수는 인자로 들어온 날짜가 속한 달의 마지막 날짜를 반환해요. 2024년 5월의 마지막 날은 31일이므로 31일이 출력된답니다.

2번: 결과값 2024-05-01
- 이유: TO_DATE 함수에 '연/월'까지만 입력하면, 일자는 자동으로 그 달의 첫 번째 날인 1일로 설정돼요.

3번: 결과값 2024-05-01
- 이유: ROUND(날짜, 'MONTH')는 월을 기준으로 반올림을 해요. 15일 이상이면 다음 달 1일로 넘어가고, 14일까지는 현재 달의 1일로 반올림된답니다. 14일이라서 5월 1일이 돼요.

4번: 결과값 2024-05-01
- 이유: TRUNC(날짜, 'MONTH')는 월 이하의 단위를 모두 버림해요. 즉, 해당 월의 무조건 첫 번째 날(1일)로 되돌리는 함수라서 5월 1일이 출력됩니다

ROW_NUMBER() OVER (PARTITION BY dept
ORDER BY sal DESC)의 의미로 옳은 것은?

1
전체 테이블에서 한 번만 번호를 부여한다.

2
부서별로 급여가 높은 순서의 일련번호를 부여한다.

3
부서별 합계를 계산한다.

4
NULL만 번호를 부여한다.

###
정답 : 2번

📋 정답 및 해설
2번: 부서별로 급여가 높은 순서의 일련번호를 부여한다. (정답)
- PARTITION BY dept: 전체 데이터를 부서(dept)별로 그룹을 나누는 역할을 해요.
- ORDER BY sal DESC: 나눈 부서 안에서 급여(sal)를 기준으로 내림차순(높은 순서) 정렬을 시킵니다.
- ROW_NUMBER(): 정렬된 순서대로 1, 2, 3... 처럼 중복 없이 고유한 일련번호를 붙여줘요.

❌ 오답 체크
- 1번: 전체 테이블에서 한 번만 번호를 붙이려면 PARTITION BY 절을 생략해야 해요.
- 3번: 합계를 계산하려면 ROW_NUMBER()가 아니라 SUM() 함수를 사용해야 한답니다.
- 4번: 이 함수는 NULL 여부와 상관없이 정렬된 모든 행에 번호를 부여해요.

###
- ROW_NUMBER(): 1,2,3,4 순서대로
- OVER: "어디서 계산할지 범위를 정하자!"
- PARTITION BY dept: "부서별로 팀을 나눠줘!"
- ORDER BY sal DESC: "급여 높은 순으로 줄 세워!"

일반적으로
FROM절에 정의된 후 먼저 수행되어 SQL 문장 내에서 절차성을 주는 효과를 볼 수 있는 것은 어떤 유형의 서브쿼리 문장인가?

1
NESTED SUBQUERY

2
CORRELATED SUBQUERY

3
INLINE VIEW

4
SCALAR SUBQUERY

###
📋 정답 및 해설
3번: INLINE VIEW (정답)
- 정의: FROM 절 안에 직접 SQL 문을 써서 만드는 서브쿼리를 말해요.
- 특징: SQL 문장이 실행될 때 마치 하나의 가상 테이블처럼 작동해요.
- 절차성: FROM 절에서 먼저 실행되어 결과 데이터를 미리 만들어 놓고, 그 결과를 다른 테이블처럼 사용하기 때문에 쿼리 안에서 절차적인 느낌(미리 처리하는 효과)을 줄 수 있어요.

🔍 다른 서브쿼리들은 어디에 쓰일까요?
NESTED SUBQUERY (중첩 서브쿼리):
- 보통 WHERE 절에 나타나는 서브쿼리를 말해요.
CORRELATED SUBQUERY (상관 서브쿼리):
- 서브쿼리가 메인쿼리의 컬럼을 참조하는 형태예요. 메인쿼리 한 행마다 서브쿼리가 한 번씩 실행되는 특징이 있어요.
SCALAR SUBQUERY (스칼라 서브쿼리):
- SELECT 절에 나타나는 서브쿼리로, 딱 하나의 값(1행 1열)만 반환해야 해요.

💡 암기 팁! (위치별 명칭)
- SELECT 절에 있으면 → Scalar Subquery (S-S!)
- FROM 절에 있으면 → Inline View (FI! '파이'라고 외우세요!)
- WHERE 절에 있으면 → Nested Subquery (WN! '윈'이라고 외우세요!)

이미지 내의 [결과] 테이블을 함께 분석해 볼까요?
- DEPARTMENT_ID 60인 그룹 확인:
