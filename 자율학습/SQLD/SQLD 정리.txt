다) 1：M 관계의 두 테이블을 조인할 경우 이쪽에 다중행이 출력되므로 단일행 함수는 사용할 수 없다. (거짓 ❌)

- 예시: 아까 풀었던 문제 기억하시나요? 고객 테이블과 시간대별사용량 테이블을 조인해서 다중행이 출력되었지만, 우리는 SUM(B.사용량 * C.단가)를 하기 전에 곱하기(*)라는 단일행 연산을 아무 문제 없이 처리했답니다. 결과 행이 많다고 단일행 함수를 못 쓴다는 건 완전 뻥이에요!

라) 단일행 함수는 다중행 함수와 다르게 여러 개의 인수가 입력 되어도 단일 값만을 반환한다. (거짓 ❌)
- 왜 틀렸을까?: 문장이 아주 교묘하죠? '여러 개의 인수가 입력되어도 단일 값만을 반환한다'는 성질은 단일행 함수와 다중행 함수 둘 다의 공통점이에요!
- 비교해 보기: * 단일행 함수인 CONCAT('A', 'B') ➔ 인자 2개 들어가서 결과는 'AB' (단일 값)
	- 다중행 함수인 SUM(급여) ➔ 사원 100명의 급여(인자 100개)가 들어가서 결과는 총합계 (단일 값)
- 즉, 다중행 함수와 '다르게'라고 말했기 때문에 틀린 문장이 됩니다. 둘 다 똑같이 최종 결과는 단일 값을 뱉어내니까요!

📌 요약 노트!
- 단일행 함수는 행이 아무리 많아도 각 행마다 독립적으로 실행되므로, 조인 결과가 다중행이어도 얼마든지 사용할 수 있다! (다 오답 처리)
- 단일행 함수든 다중행 함수든 최종 결과물은 하나의 값(단일 값)을 반환하는 것이 공통점이다! (라 오답 처리)

■■■■■■ [SQL 족보] 단일행 함수 vs 다중행 함수 핵심 비교 ■■■■■■

1. 한눈에 보는 핵심 차이점 테이블
====================================================================
  구분         | 단일행 함수 (Single-Row)   | 다중행 함수 (Multi-Row / 집계)
--------------------------------------------------------------------
  개념         | 각 행(Row)마다 따로 연산   | 여러 행을 뭉뚱그려서 집계
  입출력       | N개 입력 ➔ N개 출력        | N개 입력 ➔ 1개 출력
  WHERE 절     | 가능 ⭕                     | 불가능 ❌ (최대 함정!)
  GROUP BY     | 필요 없음 (단독 사용)       | 그룹 통계 낼 때 필수
  NULL 처리    | 데이터가 NULL이면 결과도 NULL| COUNT(*) 제외하고 NULL 무시
  대표 종류    | LOWER, ROUND, TO_CHAR,     | SUM, AVG, COUNT, MAX, MIN
               | EXTRACT                    |
====================================================================

##주의!!!##
1. SELECT SUM(값) FROM 테이블;
     - 만약 데이터가 [5], [NULL], [10] 이렇게 3개의 행(Row)으로 분리되어 있다면?
     - SUM 함수가 중간의 [NULL] 행을 쏙 빼고 [5 + 10]만 계산하므로 결과는 "15"가 됩니다.

  2. SELECT SUM(5 + NULL + 10) FROM DUAL;
     - 한 행 안에서 괄호 치고 수식을 먼저 묶어버렸다면?
     - 안쪽 더하기 연산에서 이미 "NULL"로 폭파된 뒤 SUM으로 들어가므로 결과는 "NULL"이 됩니다.

SQL의 LIKE 구문을 사용해서 데이터 내부에 "_"이 있는 것을 검색하는 것은?

답안과 정답

1번
SELECT *
FROM Mytest
WHERE NAME LIKE '%_%' ESCAPE '_'
2번
정답
SELECT *
FROM Mytest
WHERE NAME LIKE '%@_%' ESCAPE '@'
3번
SELECT *
FROM Mytest
WHERE NAME LIKE '%#_%'
4번
내 답안
SELECT *
FROM Mytest
WHERE NAME LIKE '%_%'

###
정답 : 2번

🪄 해결사 등장: ESCAPE (탈출 문자)
그렇다면 진짜 글자 모양 그대로의 언더바(_)를 찾고 싶을 때는 어떻게 해야 할까요? 바로 ESCAPE라는 옵션을 써서 와일드카드의 초능력을 잠시 빼앗아야 해요!

💡 ESCAPE 규칙:
"내가 지정한 특수문자(예: @나 #) 바로 뒤에 오는 와일드카드는 초능력을 잃고 순수한 일반 글자로 취급한다!"

⭕ 2번 정답 공식의 컴퓨터 해석 (LIKE '%@_%' ESCAPE '@')
- 맨 뒤에 ESCAPE '@'가 붙었네요? 컴퓨터는 "지금부터 골뱅이(@) 바로 뒤에 붙는 와일드카드는 진짜 글자로 취급할게!" 하고 인지합니다.
- 이제 조건을 봅니다 ➔ %@_%
- 맨 앞과 맨 뒤의 %는 평범한 와일드카드니까 "앞뒤에 무슨 글자가 오든 노상관!" 이라는 뜻이에요.
- 그런데 가운데를 보니 @_ 가 있죠? @ 뒤에 _가 왔으니, 이 _는 '아무 글자 1개'가 아니라 진짜 눈에 보이는 언더바(_) 글자 자체로 변신합니다!
- 최종 해석: "이름 내부에 진짜 언더바(_) 글자가 콕 박혀있는 데이터만 골라내라!" (완벽한 정답! 🎯)

### 🚨 SQL LIKE 와일드카드 탈출 (ESCAPE) 핵심 정리

1. 일반적인 LIKE 와일드카드 의미
   - `%` : 글자 수 제한 없음 (0글자 이상)
   - `_` : 아무 글자나 딱 1글자 매칭

2. 함정 분석: WHERE NAME LIKE '%_%'
   - 컴퓨터는 가운데 `_`를 '아무 글자 1개'로 해석함.
   - 즉, '글자가 1개라도 있는 모든 데이터'를 조회하므로 '언더바 자체'를 검색할 수 없음.

3. 해결책: ESCAPE 옵션 사용
   - 특정 기호 뒤의 와일드카드를 순수 문자로 인식하게 만듦.
   - 예시: WHERE NAME LIKE '%@_%' ESCAPE '@'
   - 해석: `@` 뒤에 오는 `_`는 와일드카드가 아닌 순수한 언더바('_') 글자 자체로 취급함!

32번 문제
다음 중 정상적으로 실행되지 않는 문장은? (단, DBMS는 오라클)

1번
정답
SELECT NVL(100, 'NULL')
FROM DUAL;
2번
SELECT TO_DATE('11', 'DD') + 10
FROM DUAL;
3번
SELECT TO_DATE('20240101', 'YYYYMMDD') - 10
FROM DUAL;
4번
내 답안
SELECT 100 + '1'
FROM DUAL;

###
정답 : 1번

💡 1번 문장에서 에러가 발생하는 결정적 이유!
오라클의 NVL(값1, 값2) 함수는 "값1이 NULL이면 값2를 출력하고, NULL이 아니면 값1을 출력해라"라는 함수예요. 그런데 아주 중요한 철칙이 하나 있어요!

🚨 NVL 함수의 철칙: 값1과 값2의 데이터 타입은 반드시 일치해야 합니다! 만약 다르면, 오라클은 값2를 값1의 데이터 타입으로 자동 형변환하려고 시도해요.

⭕ 4번 보기 (내 답안): SELECT 100 + '1' FROM DUAL;
- 오라클의 능력: 오라클은 숫자와 문자를 더하기 연산자(+)로 계산하려고 할 때, 문자 안에 들어있는 값이 숫자로 바뀔 수 있는 글자(예: '1')라면 자동으로 숫자로 바꿔서 계산해 줍니다!
- 즉, 내부적으로 100 + 1로 변환되어 에러 없이 101이라는 정답이 아주 잘 출력돼요. (이걸 묵시적 형변환이라고 해요!)

⭕ 2번 보기: SELECT TO_DATE('11', 'DD') + 10 FROM DUAL;
- '11'이라는 문자를 일(Day)을 뜻하는 DD 형식의 날짜(Date)로 바꿨어요. (연도와 월은 현재 시점의 연/월이 자동으로 들어갑니다.)
- 오라클에서 날짜에 숫자를 더하면(+ 10) '며칠 뒤'를 계산하라는 뜻이 돼요. 따라서 11일에 10일이 더해진 정상적인 날짜가 에러 없이 잘 출력됩니다.

⭕ 3번 보기: SELECT TO_DATE('20240101', 'YYYYMMDD') - 10 FROM DUAL;
- 2024년 1월 1일이라는 날짜 데이터에서 10을 뺐어요.
- 날짜에서 숫자를 빼는 것 역시 '며칠 전'을 계산하는 정상적인 문법이에요. 2024년 1월 1일에서 10일 전인 2023년 12월 22일이 아주 예쁘게 출력된답니다.

💡 1단계: 기본 데이터 상태 확인
우선 TAB1 테이블에 들어간 데이터를 눈으로 확인해 봐요.
- ('A', 100)
- ('B', 200)
- ('C', 300)
- ('C', 400)

여기서 핵심은 COL1의 종류가 총 3가지(A, B, C)라는 점과, C는 데이터가 2건 있다는 점이에요.

💡 2단계: 함정 탈출! GROUP BY ROLLUP(COL1), COL1 분석
이 문제의 알파이자 오메가인 그룹화 조건을 뜯어볼게요.
우리가 보통 아는 롤업은 GROUP BY ROLLUP(COL1) 형식이지만, 여기서는 COL1이 뒤에 한 번 더 붙어있어요!

GROUP BY ROLLUP(COL1), COL1

오라클이나 일반적인 SQL 엔진에서 ROLLUP(A), B 구조를 만나면, 내부적으로 아래의 2가지 그룹 조합을 각각 계산한 뒤 하나로 합쳐(UNION ALL) 줍니다.

- 첫 번째 조합: COL1 (앞의 ROLLUP 조합) + COL1 (뒤의 기본 컬럼) -> 그냥 GROUP BY COL1과 같아요.
- 두 번째 조합: () (앞의 ROLLUP 총합 행) + COL1 (뒤의 기본 컬럼) -> 이 역시 결과적으로 GROUP BY COL1과 똑같이 작동해요.

❗ 즉, 결과적으로 GROUP BY COL1을 두 번 연달아 실행한 것과 같은 행들이 만들어지게 돼요!

💡 3단계: 서브쿼리 결과 행 추적하기
그럼 각각의 조합에서 어떤 결과 행들이 나오는지 세어볼까요?

① 첫 번째 조합 (COL1 그룹화)
COL1인 A, B, C로 묶어서 합계를 냅니다. 데이터 종류가 3개니까 당연히 3개 행이 나와요.
- A ➔ 100
- B ➔ 200
- C ➔ 700 (300 + 400)

② 두 번째 조합 (총합 + COL1 그룹화)
롤업의 집계 행(NULL) 상태에서 뒤에 붙은 COL1으로 한 번 더 그룹화를 짓기 때문에, 전체 총합 1줄이 나오는 게 아니라 COL1별로 총합 행이 하나씩 다 생겨나요. 그래서 여기서도 똑같이 3개 행이 추가로 만들어집니다!
- NULL(총합의 표현), A ➔ 100
- NULL(총합의 표현), B ➔ 200
- NULL(총합의 표현), C ➔ 700

💡 4단계: 최종 COUNT(*) 계산
서브쿼리(SUB)에서 만들어진 행들을 최종적으로 합쳐보면 다음과 같이 총 6개의 행이 존재하게 됩니다.

-----------------------------------------------------------------
구문 기법	| 작동하는 실제 메커니즘	| 결과 행 계산 공식
-----------------------------------------------------------------
ROLLUP(A)	| A 그룹화(N건) + 전체 총합(1건)	| N + 1 건
ROLLUP(A), A	| A 그룹화(N건) + A 그룹화(N건)	| N * 2 건 (총합 없음!)
-----------------------------------------------------------------
※ 이 문제의 경우 COL1의 데이터 종류(A, B, C)가 3가지이므로, 3 * 2 = 6건이 정답!

###
GROUP BY ROLLUP(COL1,COL2),COL1 -
	> (COL1,COL2,COL1),(COL1,COL1),((),COL1) 
	->(중복제거) (COL1,COL2),(COL1),(COL1)

SELF JOIN은 하나의 테이블에서 두 개의 칼럼이 연관 관계를 가지고 있는 경우에 사용한다.

🔍 핵심 해설: SELF JOIN이 정확히 뭐야?
승원님이 고르신 4번은 "연관된 칼럼이 없다"고 해서 오답이 되었어요. 조인(JOIN)이라는 행위 자체가 무조건 두 컬럼 간의 '연관성(관계)'을 바탕으로 엮는 것이기 때문에 연관된 컬럼이 없으면 조인을 할 수 없답니다.

셀프 조인(SELF JOIN)의 핵심은 말 그대로 "자기 자신과 조인한다"는 뜻이에요. 별도의 다른 테이블을 불러오는 게 아니라, 똑같은 테이블 하나를 가지고 그 안에서 컬럼 대 컬럼으로 매칭을 시키는 방식입니다.

💡 가장 대표적인 예시: 사원과 상사(매니저) 관계
사원 테이블(EMP)을 보면 보통 다음과 같이 컬럼이 구성되어 있어요.
- EMPNO (사원번호)
- ENAME (사원이름)
- MGR (상사의 사원번호)

여기서 "특정 사원의 상사 이름"을 알고 싶다면 어떻게 해야 할까요? 상사도 결국 회사 직원이므로 똑같은 사원 테이블 안에 데이터가 들어있겠죠?

SQL
SELECT A.ENAME AS [사원 이름], 
       B.ENAME AS [상사 이름]
FROM EMP A 
JOIN EMP B ON A.MGR = B.EMPNO; -- 한 테이블 내의 두 컬럼(MGR, EMPNO)을 연관지음!
이처럼 하나의 테이블(EMP) 안에서 MGR 컬럼과 EMPNO 컬럼이 서로 연관 관계를 맺고 추적해 들어가야 하기 때문에, 정답은 ①번 "한 테이블 내에서 두 칼럼이 연관 관계가 있다"가 됩니다.

📌 보기 오답 정리
- ②, 4번: 기본적으로 조인은 서로 연결할 수 있는 '연관 컬럼(조건)'이 무조건 존재해야 성립합니다. 연관 컬럼이 없는데 억지로 엮는 조인은 Cross Join(카테시안 곱) 같은 특수한 경우인데, 문제의 의도와는 맞지 않습니다.
- ③번: 이것은 일반적인 테이블 간의 조인(예: EMP 테이블과 DEPT 테이블 조인)에 대한 설명입니다. 'SELF' 조인이 아니에요.

JOIN 수행 방식 3개
NESTED LOOP JOIN (NL JOIN)
SORT MERGE JOIN (SM JOIN)
HASH JOIN

① NL JOIN
- 하나씩 반복 조회
- 작은 테이블 → 큰 테이블 탐색.
- 인덱스 활용 잘함.

② SORT MERGE JOIN
- 정렬 후 병합
- 정렬해서 비교.

③ HASH JOIN
- 해시 테이블 만들어 JOIN
- 간단히:
- 작은 테이블 → HASH 메모리 생성
- 큰 테이블 → HASH 키로 빠르게 매칭
- 데이터가 크면 쪼개서 디스크 창고에 저장후 하니씩 조인

보통:

대용량 데이터
등가조건(=) JOIN
인덱스 부족

상황에서 효율적.

시험에서 이 정도만 기억하면 충분한 경우 많아요.

암기 한 줄:

NL = 반복탐색
SM = 정렬후병합
HASH = 해시기반매칭(주로 '=' JOIN)

그래서 HASH JOIN 자체는 알고 가는 게 안전합니다.
다만 SQLD에서 엄청 깊게 실행계획 최적화 레벨로 파지는 않는 편이에요.

33. Hash Join 기법에 대한 설명으로 옳은 것은?

① 조인 작업을 수행할 때는 결과 행의 수가 적은 테이블을 선행 테이블로 사용하는 것이 좋다.
● Hash Join은 해시 함수를 이용하여 조인을 수행하기 때문에 '=' 로 수행하는 조인인 동등조건 이외에도 사용할 수 있다.
③ 해시 테이블을 저장할 때 메모리에 적재할 수 있는 영역의 크기보다 커지면 초과한 크기를 제외한 영역만큼 메모리에 적재한다.
④ Hash Join은 조인 칼럼의 인덱스가 존재하지 않으면 사용할 수 없는 기법이다.

###
정답 : 1

① ⭕

- 결과 행이 적은(보통 작은) 테이블을 선행/Build 입력으로 쓰는 게 유리
- HASH JOIN은 보통 작은 테이블로 해시 테이블 생성합니다.

② ❌

 "동등조건(=) 이외에도 사용 가능"
이게 틀림.

HASH JOIN 핵심:
 해시값 비교 기반 → 주로 =(EQUI JOIN)
즉,
A.id = B.id
가능.

하지만
A.sal BETWEEN B.low AND B.high
A.id > B.id

같은 NON-EQUI JOIN 은 일반적으로 HASH JOIN 대상 아님.

③ ❌

메모리 초과하면 일부만 적재한다

아님.

메모리 부족하면 보통:

TEMP / DISK 사용
Partitioning
Spill 발생

같은 방식 처리.

"초과분 제외" 하지 않음.

④ ❌

인덱스 없으면 사용 불가

반대에 가까움.

HASH JOIN 특징 중 하나가:

인덱스 없어도 사용 가능

입니다.

시험용 암기:

NL JOIN   → 인덱스 친화적
SM JOIN   → 정렬 후 병합
HASH JOIN → 해시 기반, '=' 조인, 인덱스 불필요

따라서 정답 = ① 입니다.
💡 조인 매커니즘 3대장 핵심 요약
1. Nested Loop Join (NL 조인)
   - 특징: 랜덤 액세스 방식, 인덱스가 아주 중요함.
   - 방향성: 대용량 처리에는 불리, 소량 데이터나 OLTP 환경에 적합.

2. Sort Merge Join (소트 머지 조인)
   - 특징: 양쪽 테이블을 각각 정렬(Sort)한 뒤 병합(Merge)함.
   - 방향성: 인덱스가 없어도 됨, 등가(=)와 비등가(<, >, BETWEEN) 조인 모두 가능.

3. Hash Join (해시 조인)
   - 특징: 메모리에 해시 테이블을 빌드함. 인덱스 없어도 됨. 작은 테이블을 먼저 빌드해야 이득.
   - 방향성: 오직 등가 조인(=)만 가능, 대용량 처리에 최강 효율.

34. 다음 중 아래 테이블 정의와 인덱스 구조를 참고하여, 인덱스를 효율적으로 액세스할 수 없는 검색조건을 고르시오.

create table 주문 (

create index 주문_ind1 on 주문 (주문자명);
create index 주문_ind2 on 주문 (주문일자, 주문금액);


① where 주문번호 between 1 and 10
② where 주문자명 like '%홍길동%'
③ where 주문일자 >= '20181201'
● where 주문일자 = '20181201'

참고: 해당 문제의 올바른 정답은 ②번입니다.

###
정답 : 2번

🔍 핵심 해설: 왜 2번이 정답(비효율적 검색)일까?
데이터베이스에서 인덱스(Index)는 책 맨 뒤에 있는 '찾아보기(색인)'와 같습니다. 색인은 가나다순이나 알파벳순으로 정렬되어 있어야 빠르게 찾을 수 있죠. SQL의 인덱스도 마찬가지로 정렬된 상태로 저장됩니다.

하지만 검색 조건의 형태에 따라 이 정렬된 지도를 전혀 쓰지 못하고 테이블 전체를 다 뒤져야 하는 경우가 생깁니다. 이를 인덱스 선두 컬럼 가공 및 변형에 따른 인덱스 미사용이라고 부릅니다.

❌ ②번이 인덱스를 효율적으로 쓸 수 없는 결정적인 이유
- 조건: where 주문자명 like '%홍길동%'
- 설명: LIKE 연산자를 쓸 때, 찾고자 하는 문자열의 맨 앞에 와일드카드 기호인 퍼센트(%)를 붙였습니다.
- 왜 안 될까?: 주문_ind1 인덱스는 '주문자명'을 기준으로 가나다순 정렬이 되어 있습니다. (예: 강감찬, 김유신, 홍길동...) 그런데 %홍길동%이라고 하면 이름 앞에 '김', '이', '박' 등 무엇이든 올 수 있다는 뜻이 됩니다. 인덱스 사전의 첫 글자가 무엇인지 알 수 없기 때문에 데이터베이스는 정렬된 인덱스 지도를 타지 못하고 처음부터 끝까지 다 읽는 Full Table Scan을 하게 됩니다. 매우 비효율적이죠!

⭕ 나머지 보기들이 인덱스를 잘 타는 이유 (정상 작동)
- ①번 (where 주문번호 between 1 and 10)
	- 주문_pk 인덱스가 주문번호 컬럼으로 이쁘게 정렬되어 있습니다. 1번부터 10번까지만 딱 스캔(Index Range Scan)하면 되므로 매우 효율적입니다.
- ③, ④번 (where 주문일자 >= '20181201', where 주문일자 = '20181201')
	- 주문_ind2 인덱스는 (주문일자, 주문금액) 순서로 묶여 있는 결합 인덱스입니다.
	- 인덱스의 첫 번째 컬럼(선두 컬럼)인 주문일자가 조건절에 명확하게 = 이나 >= 형태로 참여하고 있습니다. 따라서 시작 지점을 딱 찍고 인덱스 범위를 효율적으로 훑을 수 있습니다. (승원님이 고르신 4번은 인덱스를 가장 정석적으로 잘 타는 베스트 조건입니다!)

💡 시험장 대비 인덱스 매커니즘 핵심 요약
조건절에 다음과 같은 형태가 오면 인덱스를 정상적으로 타지 못하거나(Full Scan) 비효율적으로 작동하므로 시험 문제용 보기로 정말 잘 나옵니다!
- LIKE '%단어' 또는 LIKE '%단어%' ➡️ 맨 앞에 %가 오면 인덱스 스캔 불가 ❌
- 인덱스 컬럼을 가공하는 경우 (예: WHERE SUBSTR(주문일자, 1, 4) = '2018') ➡️ 컬럼 원본을 훼손하면 인덱스 스캔 불가 ❌
- 결합 인덱스의 선두 컬럼을 빼먹은 경우 ➡️ (주문일자, 주문금액) 인덱스가 있는데 WHERE 주문금액 = 50000 처럼 첫 번째 컬럼을 조건에서 빼먹으면 인덱스 사용 효율 급락 ❌

27. 다음 중 설계 단계에서 데이터 모델의 성능을 고려하는 절차와 방법에 포함되지 않는 것은?

① 이력모델의 조정, 기본키/외래키 조정, 슈퍼타입/서브타입 조정 등을 수행한다.
② 데이터베이스 용량 산정을 수행한다.
③ 데이터베이스에 발생되는 트랜잭션의 유형을 파악한다.
④ 데이터 모델링을 할 때 분석 단계에서부터 반정규화를 수행한다.

###
정답 : ④

🔍 왜 ④번이 정답(포함되지 않는 것)일까요?
- 반정규화는 가장 마지막 보루입니다! 분석 단계부터 막 지르는 게 아니에요.
- 데이터 모델의 성능을 향상시키기 위해 구조를 쪼개고 정돈하는 '정규화'가 무조건 첫 번째 단계입니다. 정규화를 완벽히 끝내놓고 성능을 검토한 뒤, "아, 이 부분은 도저히 속도가 안 나오네?" 싶을 때 마지막 단계에서 성능 향상을 위해 테이블을 합치거나 중복을 허용하는 반정규화(역정규화)를 고민하는 것입니다.
- 지문처럼 "분석 단계에서부터 반정규화를 수행한다"는 말은 순서가 완전히 꼬인 잘못된 방법이기 때문에 확실한 오답입니다

📌 성능 데이터 모델링의 올바른 6단계 절차 (이것만 기억하세요!)
시험 문제에는 이 절차의 순서를 섞어놓거나 4번처럼 뜬금없는 시점에 뭘 한다고 속이는 유형이 많아요.
- 1단계: 데이터 모델링을 할 때 정규화를 정확하게 수행한다. (무조건 정규화가 1등!)
- 2단계: 데이터베이스 용량 산정을 수행한다. (지문 ②번)
- 3단계: 데이터베이스에 발생하는 트랜잭션의 유형을 파악한다. (지문 ③번)
- 4단계: 용량과 트랜잭션 유형에 따라 반정규화를 수행한다. (구조적 접근)
- 5단계: 데이터 성능 향상을 위해 이력모델 조정, PK/FK 조정, 슈퍼/서브타입 조정을 한다. (지문 ①번)
- 6단계: 성능 관점에서 데이터 모델을 최종 검증한다.

❌ 나머지 보기들이 올바른 설명인 이유
①, ②, ③번은 위의 6단계 절차에 아주 예쁘게 잘 포함되어 있는 정석적인 절차와 방법들입니다.

     * 홍길동(1000)의 상위관리자는 'NULL'이므로 여기서 전개가 종료됩니다.

[문제] 제시된 집합 연산 SQL의 실행 결과 행 수는?

지문

SELECT val
FROM (
SELECT 1 AS val
UNION ALL
SELECT 2
UNION ALL
SELECT 2
UNION ALL
SELECT 3
) a
MINUS
SELECT val
FROM (
SELECT 2 AS val
UNION
SELECT 4
) b;

--------------------------------------------------
[정답 및 결과 값]
2번 (2개 행)

[최종 출력 데이터 결과 테이블]
VAL
----
1
3

[핵심 해설]
1. 위쪽 서브쿼리 (a 집합) 계산: UNION ALL
   - UNION ALL은 중복을 제거하지 않고 모든 데이터를 그대로 합칩니다.
   - 데이터 내용: [1, 2, 2, 3] (총 4개 행)

2. 아래쪽 서브쿼리 (b 집합) 계산: UNION
   - 순수 UNION은 중복된 데이터를 자동으로 제거(정렬 후 중복 제거)합니다.
   - 데이터 내용: [2, 4] (총 2개 행)

3. 최종 연산: a 집합 MINUS b 집합 (차집합) ⭐⭐⭐
   - 오라클의 MINUS(차집합) 연산자는 아주 중요한 절대 규칙이 있습니다.
     "앞의 집합(a)에서 뒤의 집합(b)에 있는 원소를 빼버리는데, 
      그 과정에서 결과 집합의 중복을 '자동으로 제거'하고 최종 결과를 보여준다!"
   
   - 연산 과정:
     * a 집합 [1, 2, 2, 3] 에서 b 집합에 있는 '2'와 '4'를 지웁니다.
     * 내부적으로 중복을 제거, 사실상 [1, 2, 3] - [2, 4] 이다
     * 2가 지워지고 나면 [1, 3] 이 남습니다.
     * 결과 집합에 중복이 없으므로 그대로 [1, 3] 총 2개의 행이 최종 출력됩니다.

### 💡 무조건 외우는 정규화 6단계 (도·부·이·결·다·조)

[정규화 단계 - 암기 키워드 - 대상 및 특징]

- 제1 정규형 (1NF) : [도]메인 원자값 / 도메인이 원자값이어야 함
- 제2 정규형 (2NF) : [부]분 함수 / 부분 함수적 종속 제거 (완전 함수 종속)
- 제3 정규형 (3NF) : [이]행적 / 이행적 함수적 종속 제거 (A→B, B→C 제거)
- BCNF             : [결]정자 / 결정자이면서 후보키가 아닌 것 제거
- 제4 정규형 (4NF) : [다]치 종속 / 다치 종속 제거
- 제5 정규형 (5NF) : [조]인 종속 / 조인 종속성 이용

AND > OR

## 📝 [오답노트] 서브쿼리 연산자 에러 유형 (복수 정답 반영)

### 📌 문제
주어진 ERD를 참조하여 SQL을 수행하였을 때, 문법적 또는 논리적 오류가 발생하여 실행되지 않거나 에러(Error)가 날 수 있는 SQL문은? (정답: 1번, 2번, 4번)

1. SELECT 회원번호, 종목코드 FROM 일자별주문내역 WHERE 주문일자 ALL (SELECT DISTINCT 주문일자 FROM 계좌마스터);
2. SELECT 회원번호, 종목코드 FROM 일자별주문내역 WHERE 주문일자 EXISTS (SELECT DISTINCT 주문일자 FROM 계좌마스터);
3. SELECT * FROM 계좌마스터 WHERE 회원번호 IN (SELECT DISTINCT 회원번호 FROM 고객);
4. SELECT * FROM 계좌마스터 WHERE 회원번호 = (SELECT DISTINCT 회원번호 FROM 고객);

---

### 🔍 상세 해설

- 1번이 에러인 이유 (구문 오류) :
  * ALL 연산자는 단독으로 사용할 수 없고, 반드시 비교 연산자(=, >, <, >=, <=)와 함께 사용해야 함 (예: WHERE 주문일자 = ALL (...)). 
  * 비교 연산자 없이 '주문일자 ALL'이라고만 적었기 때문에 명백한 SQL 구문 에러(Syntax Error)가 발생함.

- 2번이 에러인 이유 (구문 오류) :
  * EXISTS 연산자는 서브쿼리의 결과가 존재하는지만 확인하는 연산자이므로, 앞에 컬럼명(주문일자)을 붙이지 않고 'WHERE EXISTS (...)' 형태로 사용해야 함.
  * 컬럼명 뒤에 EXISTS를 붙였기 때문에 이 역시 잘못된 문법으로 구문 에러가 발생함.

- 4번이 에러인 이유 (런타임 오류) :
  * 등호(=)는 오직 하나의 값만 비교하는 '단일 행 연산자'임. 하지만 서브쿼리(고객 테이블의 회원번호 조회)의 결과는 여러 개의 행(다중 행)을 반환함.
  * 단일 행 연산자 뒤에 여러 행이 들어오기 때문에 "단일 행 하위 질의에 2개 이상의 행이 반환되었습니다"라는 치명적인 에러가 발생함.
  * 등호(=)를 in으로 바꾸면 해결

- 3번만 정상 작동하는 이유 :
  * IN은 서브쿼리에서 반환된 여러 개의 값 중 하나라도 일치하는 게 있는지 검사하는 올바른 '다중 행 연산자'이며, 문법과 구조 모두 완벽하여 정상 실행됨.
  

---

### 💡 핵심 요약 키워드
- ALL / ANY : 반드시 앞에 비교 연산자(=, >, < 등)를 동반해야 함
- EXISTS : 앞에 컬럼명을 쓰지 않고 'WHERE EXISTS (서브쿼리)' 형태로만 사용함
- 단일 행 연산자(=) : 서브쿼리의 결과 행이 무조건 딱 1개여야 에러가 안 남

## 📝 [오답노트] 셀프 조인(Self Join)과 아우터 조인(Outer Join) 활용

### 📌 문제
다음 출력 결과를 얻기 위한 SQL 문장으로 가장 적절한 것은?

[문제 이미지 데이터 텍스트화]
<EMP>
EMPNO | ENAME   | MGR  | DEPTNO
7369  | SMITH   | 7566 | 20
7499  | ALLEN   | 7654 | 30
7521  | WARD    | 7566 | 30
7566  | JONES   | 7654 | 20
7654  | MARTIN  |      | 30

<결과>
EMPNO | ENAME   | MANAGER_NAME
7369  | SMITH   | JONES
7499  | ALLEN   | MARTIN
7521  | WARD    | JONES
7566  | JONES   | MARTIN
7654  | MARTIN  | 

[SQL]
1. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.EMPNO = E2.MGR(+) ORDER BY E1.EMPNO; (내 답안)
2. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.EMPNO = E2.MGR ORDER BY E1.EMPNO;
3. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.MGR = E2.EMPNO(+) ORDER BY E1.EMPNO; (정답)
4. SELECT E1.EMPNO, E1.ENAME, E2.ENAME AS MANAGER_NAME FROM EMP E1, EMP E2 WHERE E1.MGR = E2.EMPNO ORDER BY E1.EMPNO;

---

### 🔍 상세 해설

- **조인 조건 분석** : 
  * 사원 테이블(E1)의 관리자 사원번호(`MGR`)를 통해 관리자 테이블(E2)의 사원번호(`EMPNO`)를 찾아 이름(`ENAME`)을 매칭하는 셀프 조인 문제임.
  * 결과 테이블에서 매니저가 없는 'MARTIN' 사원도 누락되지 않고 출력되었으므로 `LEFT OUTER JOIN`이 필요함.

- **풀이/매칭 진행 과정** : 
  * Oracle 문법에서 Outer Join 기호인 `(+)`는 데이터가 존재하지 않아 NULL로 채워져야 하는 쪽에 붙임. 매니저 정보가 없는 사원도 살려야 하므로 `E2` 테이블 컬럼에 `(+)`를 붙여야 함.
  * [7369, SMITH] (MGR: 7566) -> E2에서 EMPNO 7566인 JONES 매칭 성공.
  * [7654, MARTIN] (MGR: NULL) -> E2에서 매칭되는 EMPNO 없음. 단, `E2.EMPNO(+)` 조건에 의해 탈락하지 않고 우측 데이터는 NULL 처리되어 정상 출력됨.

- **최종 결과 도출** : 
  * 사원의 관리자 번호로 관리자의 사원번호를 조인해야 하므로 기본 조건은 `E1.MGR = E2.EMPNO`가 됨.
  * 여기에 매니저가 없는 사원까지 누락 없이 표현하기 위해 오른쪽 테이블 컬럼 뒤에 `(+)`를 붙인 **3번**이 최종 정답임.

---

### 💡 핵심 요약 키워드
- **셀프 조인의 방향성** : 사원-관리자 관계 조인 시 기준점은 `사원.MGR = 관리자.EMPNO`가 됨.
- **오라클 Outer Join 기호 `(+)`** : LEFT OUTER JOIN 구현 시, 우측 테이블(NULL로 채워질 대상) 컬럼 뒤에 `(+)`를 추가함.

# 🗂️ 데이터베이스 인덱스(Index) 핵심 종류 요약

## 1. 물리적 구조에 따른 분류

* B-Tree 인덱스 (Balanced Tree Index)
  - 특징: 가장 범용적이고 기본적으로 사용되는 균형 잡힌 트리 구조.
  - 장점: 일치하는 값(=)뿐만 아니라 부등호(<, >)를 사용하는 '범위 검색'에 매우 강함.

* 비트맵 인덱스 (Bitmap Index)
  - 특징: 데이터를 0과 1(비트)로 변환하여 인덱스를 구성.
  - 장점: 컬럼이 가진 값의 종류가 적을 때(예: 성별 남/여, 대구/서울 등) 성능 극대화.
  - 단점: 데이터 수정이 잦으면 성능이 떨어져 대용량 분석용(DW)에 주로 사용.

--------------------------------------------------

## 2. 데이터 정렬 및 저장 방식에 따른 분류

* 클러스터형 인덱스 (Clustered Index)
  - 특징: 인덱스의 리프 페이지가 곧 실제 데이터 페이지 (책 페이지 번호 그 자체).
  - 특징: 실제 데이터가 인덱스 순서대로 물리적으로 정렬되어 저장됨.
  - 개수: 테이블당 딱 1개만 생성 가능 (주로 기본키(PK)가 자동 지정됨).

* 비클러스터형 인덱스 (Non-Clustered / Secondary Index)
  - 특징: 실제 데이터는 두고, 주소록 역할을 하는 별도의 인덱스 페이지를 생성 (책 맨 뒤 '찾아보기').
  - 특징: 데이터 자체는 물리적으로 정렬되지 않음.
  - 개수: 테이블당 여러 개 생성 가능.

--------------------------------------------------

## 3. 컬럼 구성에 따른 분류

* 단일 컬럼 인덱스 (Single-Column Index)
  - 하나의 컬럼만 지정해서 만든 가장 단순한 인덱스.

* 결합 인덱스 (Composite / Concatenated Index)
  - 두 개 이상의 컬럼을 합쳐서 하나의 인덱스로 만든 것.
  - ⚠️ 주의점: 조건절(WHERE)에 반드시 '첫 번째로 지정한 컬럼'이 들어가야 인덱스가 작동함.

--------------------------------------------------

## 💡 시험장 3초 암기 가이드

| 인덱스 종류 | 핵심 키워드 | 한 줄 요약 |
| :--- | :--- | :--- |
| B-Tree | 기본값 / 범위 검색 | 일치 검색 + 범위 검색 둘 다 만능 |
| 비트맵 | 값의 종류가 적음 | 성별, 지역 등 도메인이 작을 때 유리 |
| 클러스터형 | 테이블당 1개 / 물리 정렬 | 책 번호 그 자체, 속도 가장 빠름 |
| 비클러스터형 | 테이블당 여러 개 / 별도 주소록 | 책 뒤의 찾아보기, 부담 없이 여러 개 생성 |
| 결합 인덱스 | 여러 컬럼 조합 | 첫 번째 컬럼이 조건절에 무조건 필수 |
