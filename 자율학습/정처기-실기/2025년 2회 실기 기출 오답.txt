

문제

다음 내용이 설명하는 용어를 영어로 쓰시오.

1. 비동기식으로 웹 페이지의 일부 콘텐츠만 리로드하는 방식이다.
2. 자바스크립트와 XML을 이용한다.
3. 필요한 데이터만 서버에 요청하여 받고, 클라이언트에서 데이터를 업데이트하는 기법이다.
4. HTML만으로 어려운 작업을 웹페이지에 구현 가능하게 하는 기법이다.

보기

* REST
* Fetch API
* AJAX
* JSON-RPC
* GraphQL
* WebSocket
* SOAP

정답

AJAX

문제 해설

AJAX(Asynchronous JavaScript And XML)는 웹 페이지 전체를 새로고침하지 않고 필요한 데이터만 서버에 요청하여 화면 일부만 동적으로 변경하는 기술이다.

기존 웹 애플리케이션은 사용자가 요청을 보낼 때마다 전체 페이지를 다시 로드해야 했지만, AJAX는 JavaScript를 이용하여 서버와 비동기 통신을 수행하므로 사용자 경험이 크게 향상된다.

문제의 핵심 키워드인 "비동기", "JavaScript", "XML", "부분 갱신"이 모두 AJAX의 특징이다.

현재는 XML 대신 JSON을 많이 사용하지만 AJAX라는 용어는 그대로 사용되고 있다.

──────────────────────────────

REST 해설

REST(Representational State Transfer)는 웹 API를 설계하기 위한 아키텍처 스타일이다.

특징

* 자원(Resource)을 URL로 표현
* HTTP 메서드 사용
* 클라이언트와 서버 분리

예시

GET /users/1
POST /users
DELETE /users/1

REST는 API 설계 방식일 뿐 웹 페이지 일부를 갱신하는 기술이 아니다.

──────────────────────────────

Fetch API 해설

Fetch API는 JavaScript에서 서버와 비동기 통신을 수행하기 위한 최신 API이다.

예시

fetch("/users")
.then(response => response.json())
.then(data => console.log(data));

Fetch API는 AJAX를 구현하는 방법 중 하나이다.

관계

AJAX = 개념
Fetch API = AJAX 구현 기술

따라서 정답은 Fetch API가 아니라 AJAX이다.

──────────────────────────────

JSON-RPC 해설

JSON-RPC는 JSON 기반의 원격 프로시저 호출(Remote Procedure Call) 프로토콜이다.

특징

* 원격 서버의 함수를 호출
* JSON 형식 사용
* API 통신에 활용

예시

{
"jsonrpc": "2.0",
"method": "getUser",
"params": [1],
"id": 1
}

비동기 화면 갱신 기술이 아니므로 정답이 아니다.

──────────────────────────────

GraphQL 해설

GraphQL은 API 질의(Query) 언어이다.

특징

* 필요한 데이터만 조회 가능
* 오버페칭 감소
* 언더페칭 감소

예시

{
user(id: 1) {
name
email
}
}

데이터 조회 방식에 대한 기술이지 AJAX를 의미하지 않는다.

──────────────────────────────

WebSocket 해설

WebSocket은 서버와 클라이언트가 지속적으로 연결되어 실시간 양방향 통신을 수행하는 기술이다.

특징

* 실시간 채팅
* 주식 시세
* 게임 서버

예시

const socket = new WebSocket("ws://localhost:8080");

AJAX는 요청-응답 방식이고, WebSocket은 연결을 유지하며 양방향 통신을 수행한다는 차이가 있다.

──────────────────────────────

SOAP 해설

SOAP(Simple Object Access Protocol)는 XML 기반 웹 서비스 프로토콜이다.

특징

* XML 사용
* 엄격한 표준 제공
* 기업 시스템 연동에 사용

예시

[soap:Envelope](soap:Envelope)
[soap:Body](soap:Body)
</soap:Body>
</soap:Envelope>

XML을 사용하지만 웹 페이지 일부를 비동기 갱신하는 기술은 아니다.

──────────────────────────────

핵심 정리

AJAX
→ 비동기 웹 통신 기술

Fetch API
→ AJAX를 구현하는 최신 JavaScript API

REST
→ API 설계 방식

JSON-RPC
→ 원격 함수 호출 프로토콜

GraphQL
→ API 질의 언어

WebSocket
→ 실시간 양방향 통신 기술

SOAP
→ XML 기반 웹 서비스 프로토콜

시험 암기

비동기 + JavaScript + XML + 부분 화면 갱신 = AJAX

Fetch API는 AJAX를 구현하는 도구일 뿐 정답은 AJAX이다.

[문제]

데이터베이스 물리 설계 시 레코드 접근 방법에는 순차 접근, [ ① ] 접근, 해싱 접근 방법 등이 있다.

이 중 [ ① ] 접근 방법은 레코드의 키 값과 주소 포인터를 쌍으로 구성한 별도의 자료 구조를 사용하여 검색 속도를 향상시킨다.

이 자료 구조를 통해 키 값을 기준으로 원하는 레코드를 빠르게 찾을 수 있을 때, 빈칸 ①에 들어갈 용어는 무엇인가요?

[정답]

인덱스 (또는 색인)

---

[문제 해설]

이 문제는 데이터베이스에서 원하는 데이터를 빠르게 찾기 위해 사용하는 별도의 자료 구조가 무엇인지 묻는 기출문제입니다.

핵심 힌트는 키 값과 주소 포인터를 쌍으로 구성한 별도의 자료 구조라는 점입니다.

책의 맨 뒤에 있는 찾아보기를 떠올리면 이해하기 쉽습니다. 책 내용을 처음부터 끝까지 다 읽지 않아도, 특정 단어(키 값)와 그 단어가 있는 페이지 번호(주소 포인터)가 적힌 찾아보기를 보면 원하는 내용을 바로 찾을 수 있습니다.

이처럼 검색 속도를 올리기 위해 주소록처럼 따로 만들어둔 구조를 인덱스 또는 색인이라고 부릅니다.

---

[추가 개념 정리]

시험에 자주 나오는 레코드 접근 방법 3가지도 명칭 위주로 간결하게 정리해 드릴게요.

1. 순차 접근: 저장된 순서대로 처음부터 차례차례 읽어가는 방식입니다.
2. 인덱스 접근: 이번 문제의 정답으로, 키 값과 주소가 담긴 인덱스를 보고 원하는 곳으로 바로 건너뛰는 방식입니다.
3. 해싱 접근: 해시 함수라는 공식을 이용해 키 값을 입력하면 저장 주소가 바로 튀어나오게 만드는 방식입니다.

적어주셨던 간접이라는 표현은 시험에서 오답 처리되니, 반드시 인덱스라는 정확한 용어로 암기해 주세요!

이번엔 정답을 아주 정확하게 맞히셨네요! 라운드 로빈(Round Robin) 스케줄링 계산 문제는 중간에 삐끗하면 숫자가 완전히 틀어지는데, 11.75를 한 번에 골라내신 걸 보니 스케줄링 메커니즘을 확실하게 이해하고 계신 것 같습니다.

이전 피드백을 반영해서, 이번에도 **마크다운 기호 없이** 줄바꿈과 띄어쓰기만으로 가독성을 꽉 잡아서 문제와 풀이 과정을 정리해 드릴게요.

---

[문제]

위 표와 같은 프로세스들이 순서대로 준비 큐에 도착했을 때, 라운드 로빈 스케줄링을 사용할 경우 평균 대기 시간(ms)을 계산하시오. (시간할당량은 4ms, 컨텍스트 스위칭 시간은 무시한다.)

* P1: 도착 시간 0, 실행 시간 8
* P2: 도착 시간 1, 실행 시간 4
* P3: 도착 시간 2, 실행 시간 9
* P4: 도착 시간 3, 실행 시간 5

---

[정답]

11.75 (또는 11.75ms)

---

[문제 해설 및 풀이 과정]

이 문제는 시간할당량인 4ms씩 프로세스들이 번갈아가며 CPU를 차지하는 과정을 시간순으로 추적해야 합니다. 전체적인 실행 흐름(간트 차트)을 먼저 그려보면 계산이 아주 쉬워집니다.

1. 시간대별 프로세스 실행 흐름 (0ms ~ 26ms)

* 0ms ~ 4ms: P1이 먼저 도착해서 4ms 동안 실행됩니다. (P1 남은 시간: 4)
이 사이에 P2(1ms), P3(2ms), P4(3ms)가 순서대로 준비 큐에 들어와 대기합니다.
* 4ms ~ 8ms: 큐의 다음 차례인 P2가 4ms 동안 실행되어 완전히 종료됩니다. (P2 남은 시간: 0)
* 8ms ~ 12ms: 다음 차례인 P3이 4ms 동안 실행됩니다. (P3 남은 시간: 5)
* 12ms ~ 16ms: 다음 차례인 P4가 4ms 동안 실행됩니다. (P4 남은 시간: 1)
* 16ms ~ 20ms: 한 바퀴 돌아서 다시 P1 차례입니다. 남은 4ms를 모두 실행하고 완전히 종료됩니다. (P1 남은 시간: 0)
* 20ms ~ 24ms: P3 차례입니다. 4ms 동안 실행됩니다. (P3 남은 시간: 1)
* 24ms ~ 25ms: P4 차례입니다. 남은 시간이 1ms뿐이므로 1ms만 실행하고 종료됩니다. (P4 남은 시간: 0)
* 25ms ~ 26ms: 마지막으로 남아있던 P3이 남은 1ms를 실행하고 완전히 종료됩니다. (P3 남은 시간: 0)

2. 프로세스별 종료 시간 및 대기 시간 계산

대기 시간을 구하는 공식은 [종료 시간 - 도착 시간 - 실행 시간]입니다.

* P1 대기 시간: 종료(20) - 도착(0) - 실행(8) = 12ms
* P2 대기 시간: 종료(8) - 도착(1) - 실행(4) = 3ms
* P3 대기 시간: 종료(26) - 도착(2) - 실행(9) = 15ms
* P4 대기 시간: 종료(25) - 도착(3) - 실행(5) = 17ms

3. 평균 대기 시간 계산

네 프로세스의 대기 시간을 모두 더한 뒤, 프로세스 개수인 4로 나눕니다.

* (12 + 3 + 15 + 17) 나누기 4 = 47 나누기 4 = 11.75ms

따라서 최종 정답은 11.75가 됩니다.

디자인 패턴 정리 

[1. Facade (퍼사드 패턴)]
키워드: 복잡한 서브 시스템 통합, 단순한 인터페이스 제공, 결합도 낮춤

[2. Adapter (어댑터 패턴)]
키워드: 인터페이스 호환성 확보, 구조 변환, 기존 코드 재사용

[3. Decorator (데코레이터 패턴)]
키워드: 동적인 기능 확장, 상속 대신 위임 사용, 원래 코드 수정 없음

[4. Proxy (프록시 패턴)]
키워드: 대리 객체, 접근 제어, 가상 프록시/원격 프록시/보호 프록시
