"데이터 품질 문제를 발견하고 수집 파이프라인을 개선했습니다."
ValuePick은 주식 가치 투자 지표(PER, PBR 등)를 계산해서 저평가 종목을 발굴하는 서비스인데, 지표 계산 결과에서 PER이 -13000이 넘거나 PBR이 1000을 초과하는 극단값이 다수 발견됐습니다.
원인을 추적해보니 스팩(SPAC)과 리츠(REITs) 종목이 수집 단계에서 걸러지지 않고 DB에 들어오고 있었습니다. 스팩은 실제 사업이 없는 페이퍼컴퍼니라 재무제표상 자본이 거의 없어 BPS가 극소값이 되고, 결과적으로 PBR/PER 계산값이 비정상적으로 튀는 구조였습니다.
처음에는 지표 계산 단계에서 음수 PER이나 극단값을 null 처리하는 방식을 고려했지만, 이는 증상만 가리는 것이고 근본 원인은 수집 대상 자체가 잘못된 것이라 판단했습니다.
해결 방법으로 ISIN 코드 패턴 분석도 시도했지만 일반 주식과 구분이 불가능했고, 최종적으로 KRX API 응답의 종목명 기반 키워드 필터링을 수집 단계에 적용했습니다. 스팩은 종목명에 항상 "스팩" 또는 "기업인수목적"이 포함되고, 리츠도 "리츠"가 포함되는 규칙이 있어 신규 상장 종목에도 자동으로 적용됩니다. 오탐 가능성이 있는 메리츠금융지주, 블리츠웨이엔터테인먼트 같은 종목은 화이트리스트로 관리했습니다.
결과적으로 2654건에서 2559건으로 95개 비적격 종목이 수집 단계에서 완전히 차단됐고, 이후 재무 지표 계산 및 Read API까지 별도 필터링 없이 깨끗한 데이터가 흐르도록 구조를 개선했습니다.

# 환율 처리 로직 면접 설명

---

## 상황 설명 (STAR 기법)

**"어떤 문제가 있었나요?"**

> DART API에서 수집한 재무데이터 중 일부 외국 기업의 재무수치가 USD, JPY 등 외화로 저장되어 있었습니다. PER, PBR 같은 지표를 계산할 때 주가는 항상 KRW인데 재무수치는 외화여서, 그대로 계산하면 완전히 잘못된 지표값이 나오는 문제가 있었습니다.

---

## 해결 방법 설명

**"어떻게 해결했나요?"**

> 세 가지 포인트로 설계했습니다.

**1. 통화 정보 기반 동적 환율 적용**
```java
String currency = financial.getCurrency() != null ? financial.getCurrency() : "KRW";
double fxRate = resolveExchangeRate(company.getCorpName(), currency);

long netIncome = toKrw(financial.getNetIncome(), fxRate);
```
> 재무제표 엔티티에 저장된 `currency` 필드를 읽어서 KRW가 아닌 경우에만 환율을 곱해 변환합니다. KRW면 `fxRate = 1.0`이 반환되어 값이 그대로 유지됩니다.

**2. null 안전 처리**
```java
// currency가 null이면 KRW로 간주
String currency = financial.getCurrency() != null ? financial.getCurrency() : "KRW";

// 재무수치가 null이면 0 처리
private long toKrw(Long amount, double fxRate) {
    if (amount == null) return 0L;
    return Math.round(amount * fxRate);
}
```
> 데이터 수집 과정에서 누락될 수 있는 필드를 방어적으로 처리했습니다.

**3. 환율 조회 실패 시 해당 기업 스킵**
```java
private double resolveExchangeRate(String corpName, String currency) {
    try {
        return exchangeRateApiService.getRateToKrw(currency);
    } catch (Exception e) {
        log.warn("환율 조회 실패 → 지표 계산 스킵: {} currency={}", corpName, currency);
        throw new IllegalStateException("환율 조회 실패: " + currency, e);
    }
}
```
> 환율 조회에 실패했을 때 `fxRate = 1.0`으로 fallback하지 않고 의도적으로 예외를 던집니다. 잘못된 환율로 계산된 지표가 저장되는 것이 더 위험하다고 판단했기 때문입니다. 상위 호출부에서 catch해서 해당 기업만 스킵하고 나머지는 계속 처리합니다.

## 예상 꼬리 질문 & 답변

**Q. 환율 조회 실패 시 왜 1.0으로 fallback하지 않았나요?**
> 잘못된 지표값이 DB에 저장되면 투자자가 그 데이터를 신뢰하고 판단할 수 있습니다. 데이터가 없는 것보다 틀린 데이터가 더 위험하다고 판단해서 스킵을 선택했습니다.

**Q. 환율 API가 자주 실패하면 어떻게 할 건가요?**
> 현재는 단건 스킵으로 처리하고 있고, 향후 개선 방향으로 두 가지를 고려하고 있습니다. 첫째로 환율 데이터를 주기적으로 DB에 캐싱해서 API 장애 시에도 사용할 수 있게 하는 방법, 둘째로 재시도 로직(`@Retryable`)을 적용하는 방법입니다.

**Q. 주가는 왜 환율 변환을 안 하나요?**
> 한국 주식시장(KRX) 주가는 항상 KRW로 제공되기 때문입니다. 재무수치만 외화로 표기되는 경우가 있어서 재무수치만 변환 대상입니다.

기술문제 발생 -> 해결 답변

문제 : PER PBE ROE 너무 큰 값의 범위로 인한 오류 탐색

면접 답변 예시:

"주식 재무지표 계산 서비스를 개발하면서 데이터 정합성과 수학적 예외처리 문제를 경험했습니다.

DART API에서 재무제표를 수집해 PER, ROE, PBR 같은 지표를 계산하는 로직을 구현했는데, 일부 종목에서 ROE가 -130,000% 같은 극단적인 값이 DB에 저장되는 문제가 발생했습니다.

처음엔 계산 버그라고 생각해서 공식을 검토했는데, 공식 자체는 맞았습니다. 원인은 두 가지였습니다.

첫 번째는 DART API의 CFS/OFS 데이터 혼합 문제였습니다. DART는 연결재무제표(CFS)와 별도재무제표(OFS)를 함께 반환하는데, 저희 코드가 어떤 계정은 CFS에서, 어떤 계정은 OFS에서 가져와서 ROE를 계산할 때 연결 순이익 / 별도 자본 처럼 서로 다른 기준의 값을 섞어 계산하고 있었습니다. 이 부분은 fsDiv를 일관되게 선택하도록 로직을 수정했습니다.

두 번째는 자본잠식 기업의 수학적 예외였습니다. 수년간 적자가 누적된 기업은 자본총계가 거의 0에 수렴하는데, 이 상태에서 ROE = 순이익 / 자본 을 계산하면 분모가 극소값이 되어 결과가 수만 퍼센트로 폭발합니다. 이건 계산이 틀린 게 아니라 지표 자체가 의미없어지는 상황이었습니다.

실제 금융 데이터 서비스들도 자본잠식 기업에는 ROE, PBR을 N/A 처리합니다. 그래서 자본총계가 0 이하인 경우 해당 지표를 null로 저장하도록 예외처리를 추가했습니다.

이 경험을 통해 비즈니스 도메인 지식이 없으면 기술적으로 올바른 코드도 잘못된 결과를 낼 수 있다는 걸 배웠습니다."

포인트는 "버그인 줄 알았지만 알고 보니 도메인 문제였다" 는 흐름으로 가는 게 면접관 입장에서 가장 인상적입니다.

기술문제 발생 -> 해결 답변

문제 : Top100 score를 어떻게 만들었나

PER 순위 50등 → (999 - 49) / 999 * 25 ≈ 23점
PBR 순위 200등 → (999 - 199) / 999 * 25 ≈ 20점
ROE 순위 10등 → (999 - 9) / 999 * 25 ≈ 24점


면접 설명 스크립트
"오늘은 밸류픽 프로젝트에서 주식 종목 랭킹 기능인 Top100 스코어링 시스템을 설계하고 구현했습니다.

문제 정의
기존에 PBR, PER, ROE 같은 재무 지표는 계산해서 저장하고 있었는데, 이 수치들을 종합해서 어떤 종목이 저평가·고수익인지 순위를 매기는 기능이 없었습니다. 단순히 PBR만 낮거나 ROE만 높은 종목을 보여주는 건 편향될 수 있어서, 세 지표를 균형 있게 반영하는 점수 체계가 필요했습니다.

설계 결정: 백분위 랭킹 방식 채택
구간 점수제(예: PBR 1 미만이면 30점)를 먼저 검토했는데, 문제는 PBR 0.5와 0.8을 똑같이 취급한다는 점이었습니다. 그래서 전체 종목 중 상대적 위치를 기반으로 한 백분위 방식을 선택했습니다.

PBR·PER: 낮을수록 좋아서 오름차순 정렬 후 역순위
ROE: 높을수록 좋아서 내림차순 정렬 후 역순위
각 지표를 0~25점으로 정규화 후 합산, 총 100점 만점
구현
Top100Service에서 StockIndicator 테이블의 전체 데이터를 JOIN FETCH로 N+1 없이 한 번에 로드하고, 자바 메모리 내에서 랭킹 계산 후 상위 100개를 Top100 테이블에 저장했습니다. Top100Scheduler로 매일 오후 5시 자동 실행되도록 했고, 같은 날 중복 계산을 막는 멱등성 처리도 포함했습니다.

코드 리뷰 및 개선
구현 후 코드 리뷰를 통해 여러 문제를 발견하고 개선했습니다.

데이터 정확성: 조회 쿼리에 baseDt 필터가 없어서 과거 날짜 데이터가 응답에 섞이는 문제를 발견하고, 최신 날짜 기준 조회 쿼리를 별도로 추가했습니다.
성능: STOCK_PRICE 테이블 조인 시 상관 서브쿼리가 행마다 반복 실행되던 것을 GROUP BY 방식으로 교체해 쿼리 횟수를 줄였습니다.
안정성: null 지표를 0으로 치환하던 로직이 자본잠식 종목을 오히려 최고점으로 만드는 버그가 있어, Double.MAX_VALUE로 교체해 최하점 처리했습니다.
결과적으로 설계 → 구현 → 코드리뷰 → 버그 수정 사이클을 한 번 완성했습니다."
